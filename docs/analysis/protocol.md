# XuanXue 多 Agent 协作协议

> 版本：5.0.1
>
> 最后更新：2026-09-06
>
> 状态：Active — 补充 `AGENTS.md` 与 Plan Protocol v2.2，不替代二者

## 1. 权威顺序

协作和实施发生冲突时按以下顺序解释：

1. 仓库根目录 `AGENTS.md`；
2. `.Codex/project-config.md`；
3. `docs/product/README.md` 及其引用的正式产品规范；
4. 本协议；
5. 经用户批准的单阶段 v2.2 计划；
6. 执行器临时判断、旧文档和当前遗留代码。

旧 `docs/project-story.md`、外部 Raw、P1 审计历史用于追溯决策形成过程，不能覆盖现行规范。

## 2. 角色与责任

### 用户

- 批准产品方向、边界和最终验收；
- 对重大取舍、个人数据测试和 Git 提交作最终授权；
- 可以在任何尚未实施的阶段继续讨论并改变想法。

### Codex

- 负责代码与文档勘探、产品设计、架构判断、歧义消除和风险裁决；
- 负责把已经批准的单阶段范围写成 v2.2 计划；
- 独立复核 Claude 的 result、diff、自动化测试和浏览器证据；
- 发现非轻量返工时形成收敛计划，不把判断责任推给执行器；
- 未经用户明确授权不提交、推送、合并或删除用户数据。

### Claude

- 只执行已经通过门禁且由用户授权执行的 v2.2 计划；
- 严格遵守 allowed、forbidden、known_dirty 和任务依赖范围；
- 运行计划要求的验证并生成 result/checkpoint；
- 在 `plan_amendments` 中如实记录偏差，不静默扩展范围；
- 默认不提交 Git。

角色分工不是“Codex 永远不能改文件”或“Claude 可以自行决定产品规则”。文档纠正等经用户明确授权的限定任务可以由 Codex 直接完成；产品代码的大型实施默认交由 Claude 按计划执行。

## 3. 产品决策与实施必须分离

每个功能至少区分：

- 产品决策是否批准；
- 当前代码是否实施；
- 规则和来源是否核验；
- 是否批准向普通访客公开。

`Approved` 产品文档不等于 `Implemented`，测试通过不等于来源真实，页面可访问不等于公开批准。当前统一状态见 `docs/product/README.md`。

尚未形成工具契约时，可以继续调查和讨论，但不得生成包含猜测规则的代码计划。

## 4. 标准工作流

### 阶段一：调查

Codex 读取代码、现行规范、历史证据和 Git 状态，明确当前事实、影响范围和未知项。能够从仓库查证的问题不转交用户猜测。

### 阶段二：产品讨论与成文

Codex 提供有依据的推荐和取舍。用户逐项批准后写入 `docs/product/`；未批准内容保持 `Pending`，不得伪造为既定规则。

### 阶段三：计划门

只有用户明确要求开始某个实施阶段时，Codex 才：

1. 输出歧义点与假设清单；
2. 读取项目配置、通用规范和对应工具契约；
3. 生成单阶段 v2.2 YAML；
4. 由执行器运行计划门禁校验。

不得把多个未讨论工具塞进一份大计划，也不得用计划替代产品契约。

### 阶段四：执行

Claude 通过 `/plan-execute <计划文件路径>` 执行。计划必须按 `audit / docs / code / test / user-gate / verify` 拆分，精确声明修改范围、禁止范围、验收条件和测试命令。

### 阶段五：独立审查

Codex 至少检查：

- result 与 `plan_amendments`；
- 每一行 diff 是否有计划依据；
- 是否修改范围外文件或覆盖用户既有改动；
- 类型检查、测试、lint、构建、乱码与 `git diff --check`；
- UI 任务的 320、360、390、414 CSS 像素和文本缩放浏览器证据；
- 产品决策、实现、来源核验和公开状态是否仍被正确区分。

执行器自报成功不能替代 Codex 独立审查。

### 阶段六：用户验收与 Git

Codex 提交审查报告并等待用户确认。只有用户明确批准后才决定如何提交；提交、推送、合并分别需要与用户授权范围一致。

## 5. 计划漂移与返工

- 计划内的安全等价调整写入 `plan_amendments`，由 Codex 裁决是否接受；
- 改变产品规则、公开范围、数据生命周期或文件边界的调整必须停下并重新取得用户批准；
- 同类偏差重复出现时更新正式规范或项目配置，不在每份计划中重复打补丁；
- 非轻量返工应形成独立收敛计划，不在原任务中无限扩展；
- 历史计划因新规范过期时保留原文件并标记 `On hold` 或 `Superseded`，不得静默执行。

## 6. 文档同步

| 变更类型 | 必须检查 |
|---|---|
| 产品方向、输入、输出或边界 | `docs/product/README.md` 与对应产品契约 |
| UI 组件或响应式规则 | `docs/design-system.md` |
| 架构或运行环境 | `.Codex/project-config.md`、必要的 ADR 与阶段路线图 |
| 阶段状态 | `docs/project/stage-roadmap.md` |
| 协作流程 | `AGENTS.md`、本协议和项目配置 |
| 公开功能状态 | 工具状态目录、README、首页/导航/SEO/PWA/API/历史/导出的一致性证据 |

文档同步是对应任务的验收条件，但不能在代码尚未实施时把目标规范写成当前完成状态。

## 7. 验证与编码

- 中文文件按 UTF-8 无 BOM 处理；
- 含中文修改后执行 `AGENTS.md` 规定的乱码检测；
- 提交前至少通过 `git diff --check`、`npm run typecheck`、`npm run test` 和 `npm run build`；
- 文档任务还应检查相对链接、状态枚举、过时引用和“已批准/已实施”混淆；
- 自动化测试不能替代来源审计或真实浏览器验收。

## 8. 当前阶段约束

当前只整理待提交文档及过时说明，包含项目故事正文，不启动业务实施：

- 不生成或执行代码实施计划；
- 不修改产品代码和用户数据；
- 已获批契约保留 `Approved` 决策状态，未实施记为 `Not started` 或实际实施状态，不因代码未整改而倒写为 `Pending`；旧 P2 保持 `On hold`；
- 独立六爻等无契约范围不创造规则，也不借已批准工具恢复；
- 架构演示、截图、校验产物和本地配置不纳入待提交集合；
- 文档整理和验证不授权暂存、提交、推送或合并，后续操作仍由用户明确决定。
