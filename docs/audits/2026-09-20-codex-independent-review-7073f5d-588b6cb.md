## 2. 阻断项

### P1：内部验证权限缓存未绑定账号

`middleware/tool-availability.global.ts` 的客户端允许值只按 `toolId` 缓存。白名单账号 A 获得 `bazi: true` 后退出，再在同一 SPA 登录非白名单账号 B，`authStatus` 会重新变为 `authenticated`，中间件会复用 A 的允许值放行 B。`useAuth` 没有清理 `tools:internalAccess`，现有测试只覆盖退出后的 `guest`，没有覆盖 A→B。

结果历史接口另有服务端白名单校验，因此历史读写仍会拒绝 B；但八字页与客户端计算能力会被错误开放。修复应把缓存绑定到可信 `accountId`，并在恢复、登录、注册、退出、会话过期和换账号时失效。

### P1：Nitro 数据库插件并不会等待 `initDb()`

`server/plugins/database.ts` 声称 Nitro 运行时会等待 async 插件，但当前安装的 Nitro 2.13.4 在 `node_modules/nitropack/dist/runtime/internal/app.mjs` 的 `runNitroPlugins()` 中直接调用 `plugin(nitroApp)`，没有 `await`。因此首个请求可能在 sql.js 初始化、建表或锁获取完成前进入，触发 `System not ready — database unavailable`；初始化 Promise 的异步拒绝也不经过该同步 `try/catch`。

修复不能继续依赖 async Nitro plugin 返回值；应建立真正可等待的启动门，或让所有数据库入口等待同一个初始化 Promise，并为初始化失败提供确定的启动失败行为。

### P1：chunked 正文上限仍在完整缓冲之后检查

`server/utils/bounded-json-body.ts` 先调用 H3 `readRawBody()`，之后才执行 `Buffer.byteLength()`。H3 2.x 的 `readRawBody()` 会把所有 chunk 收集后 `Buffer.concat()`，没有传入上限。因此缺少 `Content-Length` 的超大请求仍会先占用完整内存，再返回 413；本次修复只解决了状态码与字段校验，没有消除单请求内存耗尽风险。

测试使用预制的大字符串 mock `readRawBody()`，只能证明读完后返回 413，不能证明流式限流。需要在读取 Node/Web stream 时累计字节并在超过上限时停止读取、销毁请求或由可信反代设置硬上限。

### P1：陈旧实例锁接管存在双持有者竞态

`server/utils/instance-lock.ts` 用 `wx` 创建新锁是原子的，但陈旧锁路径不是：两个进程可同时在 `open(..., 'wx')` 得到 `EEXIST`，同时读取到死亡 PID，然后各自用普通 `writeFileSync` 覆盖锁文件并继续启动。两者都会认为自己持锁，sql.js 多实例整库覆盖风险重新出现。

需要用原子 rename、带唯一 token 的抢占协议，或先原子移除并循环重新执行 `wx` 获取；锁身份也应使用不可复用的随机 token，而不只依赖 PID。现有测试仅覆盖单进程陈旧锁接管，未覆盖并发争用。
