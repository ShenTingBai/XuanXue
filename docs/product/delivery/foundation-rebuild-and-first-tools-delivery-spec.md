# 基础重建与首批工具交付规范

> 状态：Approved — 六个阶段均已由用户逐项审阅批准
>
> 版本：1.0.0
>
> 最后更新：2026-09-07
>
> 适用范围：XuanXue 账号、会话、本人档案、游客草稿、生肖、八字基础排盘、结果历史及其首轮全链路验收
>
> 文档性质：已批准的交付边界与阶段顺序；不是实施计划、数据库迁移脚本或上线结论
>
> 文档入口：[XuanXue 产品规范索引](../README.md)

## 1. 文档目的

本文把已经分散在产品总纲、数据生命周期规范和单项工具契约中的决定，收束为首批可实施的六阶段路线。后续讨论和计划必须先查本文，不得重复询问已经固定的账号方式、游客能力、档案边界、保存行为、旧数据库处置和首批工具顺序。

本文只确定交付顺序和每阶段的最小闭环。更完整的领域能力仍以对应单项契约为准；本文缩小首批交付范围时，不代表被推迟的能力已经实施、核验或获准公开。

## 2. 已锁定的总体决定

1. 产品采用游客优先路径。公开且已通过准入的工具允许游客临时使用，登录只用于保存和跨设备延续。
2. 账号 `Account`、本人档案 `SelfProfile`、当次草稿 `ToolDraft`、授权凭证 `ConsentReceipt` 和结果历史 `ResultHistory` 必须分离。
3. 一个账号可以没有本人档案，最多只能有一个本人档案；不建设亲友档案。
4. 注册只创建账号和当前会话，不创建本人档案，也不进入强制建档向导。
5. 登录或注册不自动迁移游客草稿。档案带入、保存档案和保存结果分别由用户主动发起。
6. 结果默认不保存。任何页面加载、计算成功、登录恢复或档案带入都不能自动创建历史。
7. 旧数据库不迁移、不推断、不删除。它只作为离线、只读备份保留，不提供旧账号登录、认领、查询或兼容入口；新模型使用干净的新数据库结构。
8. 首批只打通生肖与八字基础排盘。其他候选工具保持既定围栏，不因本路线自动扩展或恢复。
9. 六个阶段必须依次完成。前一阶段未通过工程、浏览器和用户验收时，后一阶段不得以“代码已经存在”为理由提前开放。

## 3. 第一阶段：安全收口

### 3.1 目标

先阻止旧实现继续写入不符合新规范的数据，并把工具公开能力改为可统一审计的服务端与客户端围栏。

### 3.2 必须完成

- 停止所有工具的自动历史写入；进入页面、自动恢复、生成结果和登录状态变化均不得触发保存。
- 保留旧历史数据原样，不迁移、不清洗、不删除；旧历史入口在新流程中隐藏。
- 历史创建默认拒绝。后续只有同时满足“工具获准创建历史、用户已登录、用户明确确认保存”时才能放行。
- 工具目录统一控制 `reviewStatus`、`exposure`、`computePolicy` 和 `historyPolicy`。首页、导航、SEO、直接路由、计算接口、历史及导出均从这些能力状态得出，不在页面中另写绕过规则。
- 客户端与服务端同时执行围栏。直接访问地址或直接调用接口不能绕过目录状态。
- 认证、本人档案和结果历史接口使用禁止持久缓存的响应策略；Service Worker 不得缓存这些接口的请求或响应。
- 普通日志、错误日志和安全日志不得记录出生资料、凭证明文、原始会话令牌、完整请求体或结果正文。

### 3.3 不属于本阶段

- 不迁移或删除旧数据库；
- 不重做工具页面视觉；
- 不恢复、扩展或核验其他候选工具；
- 不在本阶段创建新的历史记录模型。

### 3.4 验收门槛

从页面、直接路由和直接接口三条路径验证：不能自动创建历史，不能绕过计算与历史围栏，敏感接口响应不会进入浏览器持久缓存。

## 4. 第二阶段：账号与会话

### 4.1 账号模型

账号至少包含：

- 不可修改的唯一昵称；
- 带随机盐的登录凭证哈希；
- 账号状态；
- 已满十四周岁确认时间；
- 隐私规则版本和服务规则版本；
- 创建与更新时间。

昵称同时是登录标识，长度为 2–20 个字符，只允许中文、字母、数字、下划线和连字符。昵称不是真实姓名，不进入任何工具计算；第一版不提供修改昵称。

登录凭证在界面可称为“密令”或“密码”，长度为 8–64 个字符，允许字母、数字和符号，不设置强制混合字符类别。凭证不自动去除首尾字符。第一版不绑定邮箱或手机号，也不提供找回流程。

### 4.2 注册与登录

- 服务端必须校验并记录已满十四周岁声明、隐私规则版本、服务规则版本和确认时间；客户端勾选不能代替服务端校验。
- 注册成功只创建 `Account` 和当前 `Session`。
- 浏览器只通过 `HttpOnly` Cookie 使用会话；生产环境启用 `Secure`，并使用 `SameSite=Strict`。
- 注册和登录响应不得返回原始会话令牌。
- 认证状态使用“恢复中、游客、已登录”三态，恢复完成前不闪现错误入口，也不错误跳转。
- 认证相关状态变更请求执行同源校验；全部认证响应禁止持久缓存。

### 4.3 会话行为

- 每台设备拥有独立会话，新登录不使其他设备自动退出。
- 普通退出只终止当前会话。
- 退出请求失败时不得先把界面伪装为已经安全退出，必须提示用户会话可能仍有效。
- 注销账号使全部会话失效。
- 第一版可以提供“退出所有设备”，但不建设会话设备列表。

### 4.4 工具内认证

游客在工具结果页发起保存时，在当前页面打开登录或注册对话框。认证成功后保留当前草稿和结果，再由用户单独确认保存；认证成功本身不触发任何保存。

对话框复用统一账号表单，并满足焦点约束、Escape 关闭、关闭后焦点返回及移动端近全屏展示。

## 5. 第三阶段：游客草稿与生肖

### 5.1 产品路径

生肖页面只提供两个清晰入口：

1. “查我的生肖”：用户填写完整公历出生日期，得到对应生肖；
2. “认识十二生肖”：不填写个人资料，浏览公共文化内容。

### 5.2 当次草稿

- 初始草稿为空，不使用今天、当前年份或示例值填充。
- 只收集公历年、月、日；不收集姓名、性别、出生时间、地点或现实状态。
- 支持范围为 1901-01-01 至查询当天，并校验真实日历日期。
- 草稿只存在于当前页面内存，不写入 `localStorage`、`sessionStorage`、URL、日志、本人档案或结果历史。
- 刷新、离开或关闭页面后清除草稿和结果。
- 修改任何输入后，旧结果立即标记为过期；系统不静默重新计算。

### 5.3 计算与内容

- 生肖以中国农历正月初一为年份边界，不使用立春。
- 计算在浏览器内完成，出生日期不提交给服务器。
- 第一版不提供生肖结果保存或服务器历史。
- 删除人格断言、运势评分、配对、幸运物、逐月运势、守护佛等内容，只保留可核对规则和经治理的文化资料。
- 规则、来源台账和独立黄金样例通过前，个人查询能力不得进入公开状态。

### 5.4 年龄边界

个人查询前的十四周岁确认只存在于页面状态。明确未满十四周岁时不能提交个人日期计算，但仍可浏览“认识十二生肖”等公共文化内容。

## 6. 第四阶段：本人档案

### 6.1 首批字段

第一批 `SelfProfile` 只实现完整出生日期字段组：

- `accountId`；
- 原始历法；
- 原始年、月、日；
- 农历闰月状态；
- 规范化公历日期；
- 转换规则版本；
- 用户确认时间；
- 档案版本、创建时间和更新时间。

数据库必须保证一个账号最多对应一份本人档案。昵称、凭证、会话、工具结果和历史记录不属于 `SelfProfile`。出生时间、地点和传统排盘参数等字段在后续八字能力确有需要时再分阶段加入，不进入本阶段。

### 6.2 档案工作流

- 不强制建档；独立档案页从账号菜单进入。
- 支持公历和农历输入；选择农历时必须明确闰月状态。
- 页面同时展示用户原始表达和规范化公历日期。
- 保存前展示新增、修改和保持项；服务端重新校验后原子保存。
- 更新携带档案版本，版本冲突时拒绝静默覆盖。
- 用户可以删除出生日期字段组或整份本人档案，同时保留账号和当前会话。
- 出生日期显示未满十四周岁时，服务端拒绝保存；日志不得出现完整出生日期。

### 6.3 与生肖草稿的关系

- 仅在档案出生日期完整时显示“从本人档案带入 1 项”。
- 带入只复制出生日期到当前草稿，不自动计算或保存。
- 草稿已有不同日期时，替换前明确确认。
- 草稿记录来源；用户修改后来源改为手动输入。
- 用户撤销本次档案带入时，恢复带入前的手动值。
- 游客从生肖结果发起“保存本人资料”时，先完成页内认证，再展示档案差异并单独确认。
- 用户只在页头登录时，不导入当前草稿。

### 6.4 授权凭证

授权凭证只保存用途、数据类别、告知版本、动作和时间，不重复保存出生日期值。

## 7. 第五阶段：八字基础排盘与结果历史

### 7.1 首批能力边界

第一批八字只使用完整出生日期字段组，输出日期层面的可靠部分结果。出生时间、地点和传统排运参数均为空，不设置默认值。

首批结果包含：

- 公历与农历日期对照；
- 年柱、月柱和日柱；
- 三柱天干、地支及基础五行；
- 日干；
- 规则版本、引擎版本、来源集合版本和限制说明。

首批不输出时柱、大运、流年、神煞、日主强弱、喜用神、分数、性格判断或现实预测。

### 7.2 日期边界与候选

八字年柱以精确立春时刻为边界，月柱以十二个“节”的精确时刻为边界。只有出生日期而没有出生时刻时，如果该日期跨越相应边界，系统必须返回“边界不确定”及完整候选，说明可能受影响的年柱或月柱；不得选择零点、正午或其他默认时刻生成伪唯一结果。

普通非边界日期返回 `phase = success`、`successQualifier = partial`；边界日期返回 `phase = success`、`successQualifier = candidate`，同时保留缺少时柱等部分结果说明。候选结果可以按原状态保存。

### 7.3 计算边界

- 页面通过项目领域服务处理 `ToolDraft → 日期规范化 → 历法与三柱适配器 → 带版本结果 → 展示`。
- 页面和组件不得直接调用第三方历法库。
- 游客计算在浏览器内完成，出生日期不因生成结果而提交服务器。
- 用户请求保存时，服务端使用同一领域规则重新计算并核对，不接受客户端提交的任意结果 JSON 作为可信历史。
- 客户端结果与服务端复算不一致时拒绝保存，并保留页面结果及“未保存”状态。

### 7.4 显式保存

保存顺序固定为：

```text
生成结果
  → 未保存
  → 用户点击“保存本次结果”
  → 游客在当前页面完成登录或注册
  → 展示本次保存摘要
  → 用户再次确认
  → 服务端复算并创建不可变快照
  → 已保存
```

保存结果与保存本人档案互不替代。输入改变导致结果过期后不能保存旧结果。重复点击或网络重试使用幂等标识，不得产生重复历史；保存失败时页面结果继续可见，但明确显示未保存。

### 7.5 历史快照与删除

八字快照至少包含：

- 工具、结构、规则、引擎和来源集合版本；
- 原始输入与规范化输入，以及来源、精度和未知状态；
- 结果阶段、成功限定、缺失项和候选原因；
- 用户实际看到的结果与限制说明；
- 生成时间、保存时间和幂等标识。

历史列表使用“八字基础排盘 + 保存时间”等中性名称。打开历史时展示原快照，不按当前规则静默重算；“使用当前规则重新计算”只创建新的当次草稿和结果，不覆盖旧记录。

用户可以删除单条历史，也可以在显示数量后确认清空全部八字历史。删除请求失败时不提前从界面移除记录。

删除本人档案前必须显示仍含旧出生日期的历史数量，并让用户选择保留历史或同时删除。选择保留时明确说明历史快照仍包含保存时的出生日期。注销账号删除新模型中的账号、档案、授权凭证、历史和全部会话，但不触碰离线旧数据库备份。

## 8. 第六阶段：全链路验收与公开门禁

### 8.1 业务链路

验收至少覆盖：

- 游客进入生肖、手动输入、计算、修改后结果过期、刷新后清空；
- 注册、登录、刷新恢复、独立设备会话、当前会话退出、退出失败、会话过期和注销账号；
- 本人档案创建、修改、版本冲突、删除出生日期和删除整份档案；
- 档案带入生肖草稿、替换确认、手动修改和撤销带入；
- 八字日期三柱、普通部分结果、节气边界候选、修改后禁止保存、认证后再次确认、服务端复算和幂等保存；
- 历史原快照打开、按当前规则重新计算、单条删除、清空八字历史及档案删除时的历史选择。

### 8.2 规则与真实性

- 生肖覆盖农历新年前后、闰年、非法日期、1901 年下界和查询当日上界。
- 八字覆盖权威甲子日锚点、公农历转换、普通月与闰月、立春及十二个“节”的精确边界，以及只知道日期时的候选传播。
- 每个黄金样例记录输入、预期结果、来源、规则版本、引擎版本和核验日期。
- 来源账本、独立样例和领域测试没有通过时，对应个人计算保持非公开。

### 8.3 安全与隐私

- 直接路由、直接接口、伪造结果和无权限账号均不能绕过工具能力或数据所有权。
- 认证、档案和历史响应不进入 Service Worker 或浏览器持久缓存。
- 日志检查不出现出生资料、凭证或原始会话令牌。
- 数据删除使用事务；失败时不留下半删除状态，也不在界面伪装成功。

### 8.4 界面与失败状态

- 在 320、360、390、414 CSS 像素宽度和 200% 文本缩放下完成全部关键流程。
- 认证对话框验证键盘路径、焦点约束、Escape、焦点返回和移动端展示。
- 断网、重复点击、服务端复算不一致、保存失败、删除失败和会话中途过期均提供明确、可恢复的状态。
- 不通过禁用缩放、隐藏溢出或删除错误提示制造表面通过。

### 8.5 状态判定

某一阶段只有同时具备实现证据、自动化验证、真实浏览器证据、必要的来源核验和用户确认后，才能从 `Implemented` 更新为 `Accepted`。六个阶段全部通过前，不宣称基础重建完成，也不自动开始下一个候选工具。

## 9. 阶段顺序与计划边界

实施顺序固定为：

```text
R1 安全收口
  → R2 账号与会话
  → R3 游客草稿与生肖
  → R4 本人档案
  → R5 八字基础排盘与结果历史
  → R6 全链路验收与公开门禁
```

每个阶段分别完成歧义清单、v2.2 实施计划、执行结果、Codex 审查、浏览器验收和用户确认。不得把六个阶段合成一份大计划，也不得因为本规范已经 Approved 就跳过单阶段授权。
