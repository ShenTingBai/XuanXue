# 工具统一体验与内容治理规范

> 状态：Approved — 用户已审阅批准
>
> 版本：1.4.0
>
> 最后更新：2026-09-07
>
> 适用范围：基于 XuanXue 现有工具、页面、组件和领域代码的公开试运行治理、本地打磨、纠错与持续迭代
>
> 文档性质：跨工具产品、内容、交互与工程契约；不是实施计划，也不表示当前代码已经符合本文
>
> 文档入口：[XuanXue 产品规范索引](README.md)

## 1. 文档目的

本文固定 XuanXue 第一版受治理基线中所有工具共同遵守的产品行为和工程边界，解决下列问题：

1. 一个工具页面应按什么顺序帮助用户理解、输入、生成和查看结果；
2. 每条公开内容怎样区分生成方式、知识性质、证据状态和用户影响；
3. 一个工具满足什么条件才允许公开；
4. 输入变化、计算失败、部分结果和历史恢复怎样使用一致状态；
5. “今天”、时区、随机结果和规则版本怎样保持可追溯、可复现；
6. 保存、历史、导出、删除和规则升级后怎样保护用户数据；
7. 专业术语、婚恋、健康、财务等内容怎样避免误导；
8. 来源链接、古籍引用、现代解释和开源数据怎样完成核验与版权记录；
9. 哪些能力应由公共组件统一，哪些领域展示必须保留独立；
10. 移动端、可访问性、自动化测试和真实浏览器验收怎样成为公开门槛；
11. 未通过审核、暂停或退休的工具怎样安全退出公开路径。

XuanXue 已有可运行代码、页面、组件、数据库和测试。本文不是从零设计新项目，也不授权整体重写。“第一版”特指本轮打磨后首次满足真实性、可解释性、隐私、移动端与工程验收要求的公开基线。

本文不证明任何命理、占卜、生肖、星座或日期对照中的传统规则具有现实预测能力。传统文献只能证明某种概念、分类或做法曾存在，不能自动证明其科学有效性或对当前用户现实生活的准确性。

## 2. 适用范围、层级与优先级

### 2.1 适用对象

本文适用于：

- 当前和未来所有交互式工具页面；
- 工具相关的输入、计算、结果、来源、保存、历史、导出和错误状态；
- 首页中引用工具规则或生成每日内容的模块；
- 用户档案向工具当次草稿复制数据的过程；
- 工具目录、状态页、SEO、PWA 元数据和最近使用记录；
- 工具领域模块、共享类型、服务端接口、数据库和测试。

本文不要求登录、注册、隐私政策、关于页和普通文化文章使用完整工具结果模板，但这些页面仍须遵守真实性、隐私、移动端和可访问性原则。

### 2.2 规范层级

产品规范按以下顺序解释：

1. 全局产品原则；
2. 本文的工具统一体验与内容治理规范；
3. 用户档案与数据生命周期规范；
4. 单项工具产品与领域契约；
5. 实施计划；
6. 代码和测试。

单项工具可以在本文允许范围内采用更严格限制，但不得降低本文的公开准入、真实性、隐私或可访问性要求。

### 2.3 与设计系统的关系

现有 docs/design-system.md 继续作为墨韵视觉语言、颜色、字体和基础样式参考。若其固定间距、评分组件、MethodologyNote、历史自动保存模板或其他规定与本文冲突，以本文的产品和交互合同为准，后续必须通过专门实施同步设计系统。

本文不授权本轮讨论直接修改现有 UI。信息层级和组件职责确定后，具体视觉实现仍须在相应实施计划中复用现有设计资产并完成浏览器验收。

### 2.4 当前运行环境

XuanXue 当前运行环境统一分类为 `public_preview`。它只表示系统客观上可由互联网访问，不表示已经满足正式生产、安全、隐私、来源或内容验收资格。运行环境事实与文档边界见 [ADR-2026-09-04-002](../decisions/ADR-2026-09-04-002-public-preview-runtime-and-document-boundary.md)。

公开试运行中的未审核工具必须同时受页面和服务端围栏约束；“未主动宣传”不能作为降低公开准入要求的理由。

## 3. 已批准的核心原则

1. 产品定位为透明、可解释、可验证边界的传统文化互动与自我探索工具，不是现实预测服务。
2. 可复算不等于真实有效，有古籍来源不等于经过现代科学验证。
3. 任何结果必须能说明使用了哪些输入、规则、来源、版本和时间上下文。
4. 未知信息保持未知，不猜测、不默认补齐、不从其他字段暗中推断。
5. 所有公开结果先帮助普通用户理解，再提供专业细节。
6. 不输出用户可见的 0–100 运势分、人格分或其他伪精确评价。
7. 不依靠页脚免责声明为前文的确定性预测、高影响建议或虚构个性化兜底。
8. 计算、保存档案、保存结果、导出和内容偏好是不同动作。
9. 结果生成后冻结输入、时间、规则和来源版本；后续变化不得静默改写。
10. 随机互动必须由用户主动触发，说明随机来源并保存原始过程。
11. 来源、规则和限制进入正常阅读流，不再使用悬浮“注”功能。
12. 统一公共生命周期和治理能力，不把所有领域结果强制渲染成同一模板。
13. 移动端和可访问性是公开准入条件，不是功能完成后的附加优化。
14. 不能通过 CSS 隐藏、只改宣传文案或增加免责声明伪装完成治理。
15. 未达标工具先围栏，宁可少量工具可靠公开，也不保留表面完整的功能集合。

## 4. 统一页面信息结构

所有公开交互式工具遵守以下语义顺序：

### 4.1 工具说明

必须说明：

- 工具解决什么问题；
- 采用哪一种体系或口径；
- 需要哪些输入；
- 可以生成哪些内容；
- 明确不生成哪些现实结论；
- 内容属于计算、传统分类、文化资料还是随机互动。

### 4.2 本次操作

包含：

- 当次输入草稿；
- 本人档案可以复制的相关字段；
- 每组字段的用途、必要性和保存状态；
- 时间、地点、历法和精度；
- 缺失字段的影响；
- 计算按钮和输入错误。

复制本人档案只填充当次草稿，不自动计算、不自动保存结果、不修改本人档案。

### 4.3 核心结果摘要

摘要优先回答普通用户最关心的有限问题，不使用无法解释的专业术语堆叠，不包含现实预测、吉凶分数或人格判决。

摘要必须与本次实际输入和结果精度一致。部分结果、候选结果或日期已过期时，应在摘要之前显示明确状态。

### 4.4 通俗解释与详细结果

通俗解释先说明“这是什么、怎样得到、有什么作用、不能说明什么”，再提供领域细节。

各工具可保留独有的四柱表、卦象、日历、图表和文化内容，不要求视觉完全一致。没有内容的分区不得渲染空卡片。

### 4.5 依据与范围

作为普通页面内容展示：

- 本次使用的关键输入；
- 关键规则和规则版本；
- 来源及核验状态；
- 项目自行选择或合成的部分；
- 流派差异；
- 结果限制；
- 可访问的权威或正式来源链接。

此区域取代 MethodologyNote 和“注”按钮。

### 4.6 本次结果操作

根据工具合同提供：

- 返回修改；
- 重新生成；
- 保存本次结果；
- 导出结果卡片；
- 查看历史；
- 删除历史；
- 以历史输入重新探索。

不可用操作应说明原因；不能让用户点击后才发现结果尚未生成、输入已经改变或当前工具禁止保存。

### 4.7 响应式语义顺序

桌面端可以增加左右侧栏、锚点导航或多栏视觉布局，但 DOM 阅读顺序仍保持上述六段。移动端采用单列阅读流，不为了复用桌面布局打乱语义或让用户左右寻找结果。

## 5. 内容治理模型

### 5.1 单一内容记录

每个可独立展示、保存或导出的内容单元，都应能映射到以下内部记录：

| 字段                 | 含义                     |
| -------------------- | ------------------------ |
| contentId            | 稳定、唯一的内容标识     |
| formationMethod      | 内容怎样形成             |
| knowledgeNature      | 内容属于什么知识性质     |
| sourceStatus         | 来源核验状态             |
| personalizationLevel | 个性化依赖程度           |
| actionRisk           | 对现实行动的影响风险     |
| inputReferences      | 实际使用的输入字段       |
| ruleReference        | 对应规则标识             |
| sourceReferences     | 对应来源标识             |
| ruleVersion          | 生成时采用的规则版本     |
| plainExplanation     | 面向普通用户的解释       |
| limitations          | 适用范围和不能推出的结论 |
| disposition          | 公开处置                 |

页面可以把多个共享同一规则的内容归组展示，但账本中不得为了凑数量合并不同原子结论。

### 5.2 生成方式

至少区分：

- 确定性规则计算；
- 用户提供的随机或外部过程；
- 软件本地模拟随机；
- 按日期固定轮换；
- 编辑性公共文化内容；
- 项目工程合成。

### 5.3 知识性质

至少区分：

- 历法或天文计算事实；
- 传统分类；
- 历史文化资料；
- 规则差异；
- 项目实现规则；
- 文化互动；
- 无法支持的内容。

### 5.4 个性化程度

至少区分：

- 不依赖用户输入的公共内容；
- 只根据当次明确输入进行条件匹配；
- 使用用户主动复制的本人档案字段；
- 依赖用户当次选择的现实语境；
- 无依据的伪个性化。

伪个性化不得公开。

### 5.5 用户影响风险

至少区分：

- 低风险文化认识；
- 中风险性格、人际、学习或工作主题；
- 高风险健康、财务、法律、婚育、灾祸和现实决策。

高风险类别不是通过添加“仅供娱乐”即可获得公开资格。

### 5.6 用户可见标签

内部字段不直接暴露给普通用户。页面统一使用简洁标签：

- 计算结果；
- 传统规则；
- 文化资料；
- 项目整理；
- 随机互动。

“趣味”是体验模式，不是证据等级。趣味内容仍须声明来源、生成方式和限制。

## 6. 内容公开准入门

每项公开内容必须同时通过以下六道门：

1. **产品价值明确**：能回答用户可理解的问题，不是为了填满页面；
2. **输入完整且获得授权**：没有虚构默认值、暗中读取或无关字段；
3. **生成过程可追溯**：能回链输入、规则、版本和代码；
4. **证据真正支持内容**：来源直接支持该传统概念或规则；
5. **表达不超过证据**：传统分类不被扩写成现实事实；
6. **用户影响可以接受**：不会诱导高风险决策或伤害人格尊严。

最终处置只有：

- 直接公开；
- 限定语境后公开；
- 延期或隐藏；
- 退出产品。

无法通过的内容不得通过模糊措辞、免责声明、CSS 隐藏或归类为娱乐而保留在生产结果中。

## 7. 统一结果状态

公共状态由阶段、成功限定、结果新旧和失败类别四个互不替代的维度组成，并允许附加领域失败详细代码。单项工具不得把这些字段压缩成 `success_unique`、`success_boundary`、`failed` 等另一套并列总状态：

```ts
interface ToolResultState {
  phase: 'idle' | 'editing' | 'ready' | 'processing' | 'success' | 'failure'
  successQualifier?: 'unique' | 'partial' | 'candidate' | 'empty'
  freshness?: 'current' | 'stale'
  failureCategory?:
    | 'invalid_input'
    | 'missing_required_input'
    | 'unsupported_input'
    | 'engine_error'
    | 'network_error'
  failureDetailCode?: string
}
```

`successQualifier` 只在 `phase = success` 时存在；`freshness` 只在页面仍持有结果时存在；`failureCategory` 只在 `phase = failure` 时存在。`failureDetailCode` 由单项工具定义，用于表达 `UNSUPPORTED_DATE`、特定依赖失败等领域细节，但不得替代公共失败类别。

### 7.1 核心阶段

工具会话使用单一 phase：

- idle：尚未开始；
- editing：正在填写或修改；
- ready：输入已满足当前计算门槛；
- processing：正在生成；
- success：形成可展示结果；
- failure：本次生成失败。

页面不得用多个互相矛盾的布尔变量隐式组合状态。

### 7.2 成功限定

success 必须进一步声明：

- unique：形成唯一结果；
- partial：形成可展示但不完整的结果；包括输入精度只支持部分结果，或日期对照等已批准契约中部分子项处理失败。必须说明完整性分母、缺失项与限制，不能把失败子项隐藏；
- candidate：边界或规则差异导致多个候选；
- empty：合法执行，但没有可展示匹配项。

empty 不等于 failure。

单项工具可以只使用上述枚举的子集，不能新增 complete、failed 等同级值。可选解释缺失、字库能力、流程步骤、取字失败和导出失败分别记录，不自动改写计算结果状态；例如姓名的字形待选发生在生成前，不等于 `successQualifier = candidate`。日期对照、姓名和测字的领域映射见对应契约。

### 7.3 失败原因

`failureCategory` 至少区分：

- invalid_input；
- missing_required_input；
- unsupported_input；
- engine_error；
- network_error。

错误信息必须说明用户能否修正、怎样修正，以及输入是否被保留。

### 7.4 输入与结果关系

结果必须标记：

- current：结果对应当前输入；
- stale：输入已修改，结果尚未更新。

用户在生成后修改任意参与计算的字段时：

- 保留旧结果；
- 显示“输入已修改，结果尚未更新”；
- 展示旧结果使用的输入摘要；
- 禁止保存和导出旧结果；
- 允许恢复旧输入；
- 用户主动重新生成后才产生新结果。

不自动重新计算，不因修改输入清空已生成结果。

## 8. 时间、时区与日期

### 8.1 三类时间不得混用

#### 纯日期

出生日期、日期对照查询日、生肖年份归属和首页“今天”等，使用明确的年、月、日或 YYYY-MM-DD 表达。不得为了存储方便先转换成 UTC Date，再让系统时区改变日历日期。

#### 领域时间

出生时刻、节气交接、换日、真太阳时和星体位置等，必须同时考虑本地日期、时间、地点、精度和对应工具采用的规则。

#### 系统时间戳

记录创建、结果生成、会话和日志使用 UTC ISO 时间。系统时间戳只回答“何时发生”，不得直接代替用户选择的领域日期。

### 8.2 第一版“今天”

第一版仅支持中国大陆场景，首页今日内容、默认查询日期、今日生肖关系和跨日检测统一按 Asia/Shanghai。

用户设备时区不得暗中改变产品中的“今天”。历史出生时间仍按用户填写的当地民用时间和出生地点交给具体工具处理，不把所有历史日期粗暴转换成当前东八区时间戳。

### 8.3 显式时间上下文

需要当前时间的领域函数必须接收显式上下文，至少包含：

- asOfDate；
- generatedAt；
- timeZone；
- ruleVersion。

领域引擎内部不得自行调用 new Date() 决定今天、当前年或日干。

### 8.4 结果冻结和跨日

结果生成后冻结当次时间上下文。页面跨越中国时间午夜时：

- 已生成结果仍属于原日期；
- 显示日期已经变化；
- 用户主动重新生成后才得到新日期结果；
- 保存记录和历史不得静默变化。

首页尚未形成用户结果的公共每日内容，可以在跨日后页面重新获得焦点时明确刷新。

### 8.5 工具边界

生肖、八字、节气和公历当前年使用的边界可能不同。各工具合同必须明确使用公历元旦、农历正月初一、立春还是精确节气时刻，不能共享一个模糊 currentYear。

## 9. 随机性与可复现性

### 9.1 随机分类

#### 用户提供过程

用户现实投掷硬币、输入数字或提供其他外部结果，系统只记录并解释该输入。

#### 软件本地模拟

由用户主动点击后在浏览器本地产生，必须明确称为“本地模拟随机”，不得暗示物理投掷、超自然感应或现实预测。

第一版可以优先使用浏览器内置 Web Crypto，不引入第三方依赖；无论底层实现如何，都不得把技术随机性包装成神秘能力。

#### 日期固定轮换

同一日期按固定规则映射相同内容，应称为“按日期固定轮换”，不能称为用户抽签或个性化结果。

### 9.2 随机交互要求

- 页面加载不得自动随机；
- 重新抽取必须由用户主动操作；
- 系统记录每一步原始随机结果；
- 历史恢复使用保存的原始结果，不重新抽取；
- 测试通过注入固定随机序列完成；
- 不使用“运行一百次大概出现两种值”作为主要正确性证明。

### 9.3 复现等级

结果声明一种复现方式：

| 类型         | 复现条件                                     |
| ------------ | -------------------------------------------- |
| 确定性结果   | 相同输入、时间上下文、规则和来源版本         |
| 随机来源结果 | 相同原始随机记录、时间上下文、规则和来源版本 |
| 日期轮换内容 | 相同日期和内容目录版本                       |

## 10. 统一结果信封

一次成功生成应形成统一结果信封，领域结果作为其中一部分：

### 10.1 结果身份

- resultId；
- toolId；
- resultSchemaVersion；
- formationMethod；
- phase；
- successQualifier；
- freshness；
- failureCategory 和可选的 failureDetailCode。

### 10.2 生成上下文

- generatedAt；
- asOfDate；
- timeZone；
- 日期和时间精度；
- 随机来源及原始记录；
- 用户当次选择的规则分支。

### 10.3 规则凭证

- ruleVersion；
- sourceSetVersion；
- 使用的 ruleId；
- 使用的 sourceId；
- 来源核验状态；
- 项目合成说明。

### 10.4 内容快照

- 本次实际参与计算的输入；
- 领域结果；
- 通俗解释；
- 内容性质标签；
- 限制说明。

结果信封不得复制整个本人档案，只保存或展示本次实际使用的字段。

## 11. 保存与历史

### 11.1 生成不等于保存

- 所有结果默认不保存；
- 生成成功不得自动请求历史保存接口；
- 游客结果只存在当前页面，可以按合同导出；
- 登录用户主动点击“保存本次结果”后才能创建历史；
- 保存结果不修改本人档案；
- 保存失败不影响当前结果展示，并明确显示未保存状态。

### 11.2 工具历史策略

每项工具合同必须声明：

- create_allowed：允许符合条件的登录用户主动创建历史；
- read_only：停止创建新历史，但允许按治理规则读取和删除既有历史；
- disabled：不提供服务器历史创建或读取能力。

“结果仅存在当前页面”是未保存结果的生命周期，不是第四种历史策略。游客临时结果以及历史策略为 `disabled` 的工具结果都可以只保留在当前页面。

公共知识浏览、首页每日内容和示例不得保存为本人历史。合婚第一版禁止服务器保存对方资料和结果。

### 11.3 保存前告知

保存确认至少说明：

- 将保存的输入类别；
- 将保存的结果内容；
- 将保存时间和规则版本；
- 是否包含敏感字段；
- 可以怎样查看和删除；
- 不会更新本人档案。

一次点击“确认保存”构成当前结果的明确主动保存操作，不以一次隐私政策同意替代该操作。

### 11.4 不可变快照

历史记录保存完整结果信封和保存时间。档案修改、来源修订和规则升级不得改写旧快照。

### 11.5 历史行为

第一版至少支持：

- 按工具筛选；
- 查看安全摘要和保存时间；
- 打开完整结果快照；
- 删除单条；
- 删除某工具全部记录；
- 删除全部历史；
- 以历史输入重新探索。

打开历史只读取快照。“以此输入重新探索”只把输入复制到当前草稿，用户主动确认后再按当前规则生成。

### 11.6 重复保存

- 同一次生成拥有稳定 resultId；
- 同一 resultId 重复保存只产生一条记录；
- 网络失败重试不得产生重复；
- 修改输入并重新生成后产生新 resultId；
- 不因内容相同自动合并两次真正独立的探索。

## 12. 规则升级与历史兼容

每份结果至少保留：

- resultSchemaVersion；
- ruleVersion；
- sourceSetVersion。

规则升级后：

- 默认展示旧结果快照；
- 标明“由旧版规则生成”；
- 不静默重算；
- 兼容时可以提供“使用当前规则重新生成”；
- 重新生成的结果先保持未保存；
- 用户主动保存后成为另一条历史；
- 无法完整解析的旧结构仍须提供可读快照、版本说明和删除能力。

第一版已经批准旧数据库不迁移、不推断、不删除。旧数据库退出在线写入与产品访问路径后，只作为离线只读备份保留；新模型使用干净的新数据库结构，不为旧账号、测试数据和旧历史建设兼容入口。

## 13. 导出

### 13.1 导出与保存分离

- 导出不会创建服务器历史；
- 服务器保存成功不得用“图片已保存”表示；
- 图片下载成功统一表达为“图片已下载”；
- stale、processing、failure 结果不得导出。

### 13.2 结果卡片

第一版保留图片结果卡片，至少包含：

- 工具名称；
- 核心结果摘要；
- 生成日期；
- 内容性质；
- 简短限制说明；
- 规则版本或可追溯标识。

来源名称可以显示，长链接保留在页面正常信息层，不塞入不可点击的图片。

### 13.3 隐私

- 默认隐藏完整出生日期、地点等敏感输入；
- 用户可以主动选择包含本次输入详情；
- 合婚导出前额外提示可能包含他人信息；
- 导出预览必须准确显示将被写入文件的内容。

### 13.4 第一版非目标

第一版不建设 PDF、Word、JSON 数据包、公开分享链接和第三方社交平台直传。后续存在明确用户价值时再独立设计。

## 14. 术语解释

每个普通用户可能不理解的专业术语在第一次出现时回答：

1. 它是什么；
2. 本次怎样得到；
3. 在本工具中用于什么；
4. 它不能说明什么。

完整解释还应包含规则、来源和流派差异。

例如“日主”应解释为八字传统体系对出生日天干的称呼，后续传统分类以它为参照；不得直接扩写成用户性格、职业、婚姻或未来判断。

术语解释就地提供，不强迫用户先阅读巨大词典；同时在“依据与范围”提供可浏览索引。不得只用另一组专业术语解释当前术语。

## 15. 敏感和高影响内容

### 15.1 低风险内容

可以在来源与规则达标后公开：

- 历法、干支、生肖、星座日期区间；
- 传统分类名称；
- 输入和规则之间的可复算关系；
- 历史文化解释；
- 不指向现实结果的反思问题。

### 15.2 中风险内容

性格倾向、人际主题、婚恋相处、学习工作反思、宜忌和流年趣味解释，只能在下列条件下公开：

- 使用“在该传统体系中通常解释为”等限定表达；
- 不使用注定、一定、即将等确定语气；
- 不猜测用户已婚、恋爱、工作或求学；
- 需要现实语境时由用户当次主动选择；
- 不形成高影响行动指令；
- 明确不是现实事实或预测。

### 15.3 禁止个性化生成的高风险内容

第一版禁止：

- 疾病诊断、治疗、寿命和死亡判断；
- 血光、灾祸、流产和生育能力；
- 克夫、克妻、克父母、孤寡等人格伤害或关系判决；
- 投资、借贷、担保和签约决策；
- 法律诉讼结果；
- 考试必过、求职必成、升职或失业；
- 断言第三人是小人或会欺骗用户；
- 以化解为由引导捐血、购买物品或实施危险行为。

这些内容不得通过页脚免责声明、娱乐标签或委婉改写继续作为个人结论。历史文化材料可以介绍旧式说法，但必须去个性化、说明时代语境并避免复述不必要的伤害性断语。

## 16. 来源、规则与版权

### 16.1 四层来源

必须区分：

| 层级               | 作用                             |
| ------------------ | -------------------------------- |
| 原始文献           | 证明传统概念或说法确实存在       |
| 现代学术或权威整理 | 解释版本、历史流变和争议         |
| 项目规则           | 说明项目采用哪一种计算或映射方式 |
| 工程实现           | 指向函数、常量、测试和版本       |

“有古籍来源”只能证明传统说法存在，不能证明现实预测能力。

### 16.2 来源状态

`sourceStatus` 只表达证据能够支持到什么程度：

- verified_primary：已核对原始文献和具体位置；
- verified_secondary：由可信现代资料直接支持；
- implementation_only：只能证明项目这样实现；
- disputed：不同版本或流派存在差异；
- unverified：存在引用但尚未完成核验；
- no_source：没有来源。

verified_primary 和 verified_secondary 可以作为公开来源；disputed 必须说明差异；implementation_only 只能称为项目规则；unverified 和 no_source 不能支撑个人解读。

`sourceReviewStatus` 单独表达人工核验流程，只允许 `unreviewed / in_review / approved / rejected`。`in_review` 不能写入 `sourceStatus`，`approved` 也不能替代 `verified_primary` 或 `verified_secondary`。工具自身的 `reviewStatus` 仍使用第 20 章的独立状态，不与来源审核混用。

### 16.3 来源记录

每个来源至少记录：

- sourceId；
- 名称；
- 作者或责任机构；
- 年代；
- 采用版本；
- 出版或发布机构；
- 出版年份；
- 卷、章、页或稳定定位；
- 来源类型；
- 原文、转述或项目解释；
- 稳定链接；
- 访问日期；
- 版权或许可证状态；
- sourceStatus；
- sourceReviewStatus；
- 支持的 ruleId 和 contentId。

“同上”“百度百科综合整理”“民间说法”不得成为正式来源记录。

### 16.4 规则记录

每条规则至少记录：

- ruleId；
- 输入字段；
- 计算步骤；
- 中间值；
- 输出字段；
- 采用的传统分支；
- 对应来源及位置；
- 项目自行选择或合成部分；
- 争议和其他流派；
- 独立样例；
- 测试；
- 规则版本。

### 16.5 版权

- 古籍原文与现代点校、注释、翻译、白话解读、版式、扫描图片和数据库整理分开判断；
- 只摘取说明规则所必要的短句；
- 标明作品、作者、版本和位置；
- 通俗解释由项目自行撰写；
- 不复制现代商业网站的大段解释；
- 开源数据记录仓库、版本和许可证；
- 未核实权利状态时不得宣称“公共领域”；
- 权威链接必须直接支持对应规则，不能只链接搜索结果或泛化页面。

### 16.6 法律参考边界

本地开发和公开试运行阶段仍以以下现行正式文本作为最低设计参考：

- [《中华人民共和国著作权法》— 中国人大网](https://www.npc.gov.cn/c2/c30834/202011/t20201119_308796.html)：第二十四条规定适当引用等权利限制情形仍须指明作者或名称、作品名称，并且不得影响作品正常使用或不合理损害权利人权益；
- [《中华人民共和国个人信息保护法》— 中央网络安全和信息化委员会办公室](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)：第五至第七条规定合法、正当、必要、诚信、最小范围和公开透明原则，第十四至十七条规定知情同意、撤回和告知要求，第二十八至三十条规定敏感个人信息处理边界，第四十五至四十八条规定查阅、复制、更正、删除和解释等权利。

本文是产品设计约束，不构成项目已经满足公网运营全部法律义务的结论。未来进入部署、上线、备案或商业运营阶段，必须针对当时功能、数据流、运营主体和现行规则重新进行专项合规审查。

八字四柱、易经卦象、日期对照日历、星座图表和生肖文化展示继续独立，只接收规范化数据，不自行读取档案、自动保存或创造免责声明。

## 18. 移动端规范

### 18.1 基本门槛

所有公开工具必须在以下宽度完成全流程：

- 320 CSS px；
- 360 CSS px；
- 390 CSS px；
- 414 CSS px。

同时满足：

- 页面主体无横向自由滚动；
- 不禁用浏览器缩放；
- 200% 文字缩放后仍可阅读和操作；
- 标题、解释、来源和按钮可以自然换行；
- 关键触控目标采用项目统一的至少 44px 尺寸；
- 固定或吸底内容不遮挡正文；
- 错误不会只短暂闪现；
- 展开内容不使用容易裁剪的固定 max-height；
- 长网址、干支组合和版本号可以安全断行；
- 颜色不是成功、失败、吉凶和分类的唯一表达。

### 18.2 间距

固定 p-8 不是移动端硬标准。容器内边距应随可用宽度变化，保留墨韵留白但确保 320px 下正文具有可读宽度。

长文本与操作按钮在窄屏可以上下排列。不得通过缩小正文、强制单行或截断标题勉强容纳。

### 18.3 横向滚动

只允许真正无法合理纵向表达的高密度表格或图形局部横向滚动，并满足：

- 滚动限制在组件内部；
- 页面本身不横向滚动；
- 显示可左右滑动提示；
- 提供等价文字摘要；
- 普通段落和表单不得横向滚动。

### 18.4 导出

导出使用专门版式或导出状态样式，不把整个页面中的标题、按钮和 inline-flex 元素强制设为不换行。

## 19. 可访问性

### 19.1 页面和表单

- 每页具有唯一 h1 和顺序合理的标题；
- 每个输入具有可见 label；
- 用途、帮助和错误通过明确关系关联控件；
- 必填、选填和错误不只依赖颜色；
- 占位符不充当字段名称；
- 提交失败保留输入；
- 第一个错误可获得焦点或由错误摘要引导；
- 加载和保存状态通过适当状态区域宣布；
- 原生按钮不重复实现浏览器已经支持的键盘行为。

### 19.2 弹窗与抽屉

- 打开后焦点进入；
- Escape 在内部任意可操作位置关闭；
- Tab 不进入背景；
- 关闭后焦点返回触发按钮；
- 背景不可交互并锁定滚动；
- 只有正文区域滚动；
- 移动端使用适合窄屏的抽屉或接近全屏布局；
- 历史条目使用普通列表中的按钮或链接，不错误使用 listbox。

### 19.3 图表

- 卦象、五行图、星盘和其他视觉结果提供等价文字；
- 颜色同时配合文字、符号或形状；
- 不通过评分环和柱长表达无法验证的好坏；
- 动画遵循减少动态效果设置；
- 文字替代传达核心意义，不机械朗读全部装饰节点。

## 20. 工具状态与安全退出

### 20.1 四维状态

#### 审核状态

- unreviewed；
- in_review；
- approved；
- suspended；
- retired。

#### 访问方式

- public；
- internal；
- status_only。

#### 计算策略

- enabled；
- blocked。

#### 历史策略

- create_allowed；
- read_only；
- disabled。

首页可见不等于规则已批准。工具只有在 approved、public、enabled 且对应历史策略正确时，才属于正式公开功能。

四个字段固定命名为 `reviewStatus`、`exposure`、`computePolicy` 和 `historyPolicy`。运行环境使用独立的 `runtimeEnvironment`，不得把 `public_preview` 写入工具的 `exposure` 字段。

### 20.2 单一状态来源

工具目录是客户端和服务端共同使用的状态来源，必须控制：

- 首页和导航；
- SEO 和 PWA；
- 直接路由；
- 新结果生成；
- 历史写入；
- 最近使用；
- 历史入口；
- 导出；
- 示例和推荐。

本章描述目标实现；当前代码仍只有 `listed / hidden`，两者不能自动等同于 `public / internal`，也不能推断计算或历史策略已生效。[产品规范索引](README.md)集中记录已批准的目标组合与实际目录快照。`internal + enabled` 只允许授权内部验证，exposure 不能被 computePolicy 绕过；产品契约 Approved 也不能直接映射为工具 reviewStatus approved。

### 20.3 退出流程

#### 围栏

停止入口宣传、直接路由、新计算和新历史。

#### 盘点

记录问题、规则、来源、依赖、历史和重建价值。

#### 裁决

选择整改后公开、内部保留或正式退出。

#### 清理

处理路由、领域引擎、组件、测试、文档、元数据和历史兼容。

不能一隐藏就直接删除全部代码，也不能长期保留可绕过的半公开状态。

### 20.4 状态页

状态页按实际原因显示：

- 规则与来源整理中；
- 维护中；
- 已停止提供。

说明当前状态、原因类别、历史影响、用户可执行操作和更新时间；不承诺虚假发布日期。

## 21. 测试与公开验收

### 21.1 五层证据

#### 来源核验

人工确认版本、位置、原文、流派、版权和项目采用理由。自动化测试不能替代。

#### 独立规则样例

每条关键规则提供已知输入、传统步骤、预期中间值、预期结果、来源位置和适用边界。样例不得从当前程序输出反向复制。

#### 领域单元测试

覆盖历法、干支、日期边界、输入精度、时间时区、固定随机序列、候选结果、规则版本和非法输入。

#### 产品合同测试

所有工具声明输入、用途、精度、形成方式、内容性质、来源状态、用户风险、保存历史策略、规则版本和公开状态。

#### 真实用户流程

覆盖游客浏览、临时输入、主动生成、结果理解、来源查看、登录保存、历史查看、再次探索、删除、错误恢复和会话过期。

### 21.2 自动化内容门禁

自动检查可以拦截：

- 公开工具缺少来源标识；
- 用户可见 0–100 运势评分；
- 虚构默认出生信息；
- 自动保存；
- 合婚服务器历史写入；
- 未声明规则版本；
- 正式来源含“同上”“百度百科综合整理”等占位式描述；
- implementation_only 冒充古籍来源；
- 未 approved 工具配置为 public；
- 红色高风险词未进入人工审阅。

词语扫描只作为报警器，不能替代语境审查。

### 21.3 时间和随机测试

- 使用注入时钟或固定时间上下文；
- 覆盖中国时间 23:59、00:00 和 UTC 日期不同；
- 覆盖春节、立春、节气、闰年和工具声明的边界；
- 纯日期计算在 UTC 与 Asia/Shanghai 环境不漂移；
- 随机测试使用固定序列和合法范围性质测试；
- 历史恢复不重新随机。

### 21.4 最低工程验证

每项实施仍必须遵守项目 AGENTS.md，包括：

- git diff --check；
- 乱码检测；
- npm run typecheck；
- npm run test；
- npm run build；
- 涉及 UI 时的真实浏览器移动端证据。

构建和测试通过只能证明工程基线满足，不能单独证明传统规则和内容真实性。

## 22. 单项工具公开准入清单

一个工具只有全部满足以下条件，才能设置为 approved + public + enabled：

- [ ] 产品用途和用户价值明确；
- [ ] 单项工具合同已经用户批准；
- [ ] 输入、精度、缺失降级完整；
- [ ] 没有虚构默认输入；
- [ ] 关键计算可以回链 ruleId；
- [ ] 来源核验到版本和位置；
- [ ] 文案没有超过证据；
- [ ] 高风险内容已删除或阻断；
- [ ] 普通用户能够理解摘要；
- [ ] 结果包含时间、规则和来源版本；
- [ ] 保存、历史和删除符合本文；
- [ ] 自动化测试通过；
- [ ] 320、360、390、414 和 200% 缩放通过；
- [ ] 键盘和状态提示通过；
- [ ] 用户完成体验验收；
- [ ] 设计文档、代码和测试一致。

缺少任意一项，不得因页面可运行或测试数量较多而公开。

## 23. 第一版非目标

本文不要求第一版建设：

- 微服务或 Spring Boot 独立后端；
- 平台 AI 和服务器托管 API Key；
- 万能配置驱动页面渲染器；
- 复杂内容管理后台；
- 灰度发布平台；
- 亲友档案；
- 合婚服务器历史；
- PDF、Word 和公开分享链接；
- 未成年人监护人授权体系；
- 公网上线、应用上架和备案方案；
- 一次性重做全部视觉设计；
- 一次性让所有现有工具重新公开。

## 24. 当前实现差距

已确认的跨工具差距包括：

1. 工具页面重复维护自动保存、历史恢复和错误状态；
2. 历史表缺少结果结构、规则和来源版本；
3. 服务端接受客户端任意结果 JSON，缺少单项工具合同校验；
4. 历史缺少单条删除、全部删除和幂等保存；
5. 合婚会保存他人资料；
6. 多个领域模块内部读取设备当前时间；
7. 首页日期轮换内容使用 UTC 日期，可能与中国当天错位；
8. 随机过程缺少统一原始记录和复现合同；
9. MethodologyNote 使用固定最小宽度和展开高度，并且来源信息不在正常阅读流；
10. 设计系统固定 p-8 规则在 320px 下压缩正文；
11. 导出逻辑强制大量文字不换行；
12. 评分环和运势柱仍把工程分数展示给用户；
13. 现有来源多为引用声明，没有完成版本和规则映射核验；
14. 多处传统断语被直接表达为健康、婚恋、财务和灾祸结论；
15. 当前工具状态只有 listed / hidden，不能表达审核、计算和历史策略；
16. 现有大量测试验证内部一致性，不能替代来源真实性审查。

上述条目是实施输入，不表示本文批准立即改动代码。每项改造仍须按迭代计划拆分、执行、审查和验收。

## 25. 与其他正式规范的关系

### 25.1 用户档案与数据生命周期产品规范

该规范负责账号、本人档案、当次草稿、用途告知、授权、保存、删除和数据安全边界。本文负责这些能力进入工具后的统一产品行为。

该契约负责八字输入、历法、时间、四柱、派生规则、内容取舍和领域测试。与本文冲突时，采用更严格且不突破本文底线的规定。

### 25.3 生肖与星座工具产品与领域契约

该契约已经规定两个轻量工具不自动计算、不自动保存服务器历史、删除人格与运势结论，并使用独立领域模型。本文提供其页面状态、内容标签、来源、移动端和公开门禁。

### 25.4 日期对照工具产品与领域契约

该契约已经规定“查看某一天”和“按事项比较日期”双入口、事项映射、规则冲突、来源核验、结果信封、零服务器历史、浏览器本地导出与公开试运行围栏。两个入口及其事项、子类型和传统背景字段独立准入；日期对照已批准的目标组合为 `reviewStatus = in_review`、`exposure = internal`、`computePolicy = enabled`、`historyPolicy = disabled`，尚未落实为旧目录的四维字段，不得因为页面或引擎存在而视为已批准公开。

## 26. 后续顺序

当前书面规范完成阶段性收口后：

1. 不立即生成一份包含全部工具的大型实施计划；
2. 已形成契约的首页和工具不再视为“尚未讨论”；后续按当前规范和阶段范围逐项实施、核验或继续封存，不在本文预设下一项开发顺序；
3. 尚未形成获批契约的决策记为 `Pending`；已有 Approved 契约但来源未核验的工具保留决策状态，分别登记来源进度和围栏，不把来源缺口倒写成产品决策未批准；
4. 只有对应产品契约获得批准后，才按工具或基础能力拆分可验收迭代；
5. 每个未来迭代明确目标、非目标、文件范围、测试和用户验收；
6. 全部第一版目标完成后执行独立全链路验收。

本文批准的是目标规范，不是“大包一次改完”的授权。
