# 生肖与星座工具产品与领域契约

> 状态：Approved — 产品决策已逐项经用户审阅批准
>
> 版本：1.1.0
>
> 最后更新：2026-09-04
>
> 适用范围：基于 XuanXue 现有生肖与星座功能的公开试运行治理、本地打磨、纠错与持续迭代
>
> 文档性质：产品、领域、内容与结果契约；不是实施计划，也不表示当前代码已经符合本文

## 1. 文档目的

本文固定 XuanXue 生肖与星座功能第一版受治理基线，作为后续产品设计、领域实现、测试和验收的共同依据。

XuanXue 已有可以运行的页面、计算代码、组件与测试。本文不是从零设计新产品，也不授权整体重写；“第一版”特指本轮打磨后首次满足真实性、可解释性、隐私和工程验收要求的公开版本。

本文解决以下问题：

- 生肖与星座在产品中为什么存在，各自为用户解决什么问题；
- 哪些输入确实是计算所需，哪些字段不得为了“看起来专业”而收集；
- 哪些输出属于可复算事实、传统分类或文化解释；
- 哪些现有内容必须删除，哪些可以重写，哪些应当延期；
- 生肖与八字、星座与占星进阶功能之间如何划清边界；
- 结果失败、临界日期、资料带入、数据保存和移动端体验如何统一；
- 每一项公开结论怎样追溯到规则、版本和来源。

## 2. 已批准的核心结论

1. 首页将两个工具编排为一个轻量分组“生肖与星座”，但保留“查我的生肖”和“查太阳星座”两个直达按钮，不新增中转页。
2. 生肖与星座共享出生日期输入、校验、本人档案显式带入和结果状态规范，但必须使用两个独立领域模型、计算引擎和来源账本。
3. 不得根据一次生日输入自动同时生成生肖与星座；用户选择哪个工具，系统只处理哪个意图。
4. 生肖使用中国农历正月初一作为民俗生肖年界，不使用公历元旦，也不把八字立春年界混入生肖计算。
5. 星座第一版仅提供西方热带黄道体系下的大众太阳星座日期查询，不公开月亮星座、上升星座和完整星盘。
6. 两个工具均允许游客使用，不强制登录，不自动计算，不自动保存本人档案，不保存服务端结果历史。
7. 结果以可复算字段和中性文化说明为主体，不输出人格定论、命运预测、吉凶分数、幸运物或关系成败结论。
8. 生肖婚配、星座配对等简化结论不得恢复；合婚属于独立工具，不能只凭生肖或太阳星座下结论。
9. 所有公开字段必须声明内容类别、计算规则或内容来源、版本和适用边界；尚未完成来源核验的内容不公开。
10. 现有“墨韵”视觉风格继续保留；本轮允许重组信息层级和交互，不以全面换肤为目标。
11. 原悬浮“注”功能不再保留；来源、规则和边界改为页面正常信息层中的“依据与范围”。
12. 当前错误或无法支撑的代码与测试必须真正退出生产路径，不能只通过 CSS 隐藏。

## 3. 产品定位与用户价值

### 3.1 共同定位

生肖与星座不是“预测命运”的双工具，也不是把两种文化体系混合为一个人格判断器。它们在 XuanXue 中承担两个轻量入口：

- 用户有明确意图时，可以按公开规则查询自己的生肖或大众太阳星座；
- 用户出于兴趣时，可以认识两套文化分类体系的规则、边界和常见文化表达；
- 用户能够看到结果如何得出、采用了什么口径，以及哪些内容只是传统或现代文化解释。

首页建议文案：

> 根据出生日期查询民俗生肖或大众太阳星座，并了解各自采用的历法与文化分类。

首页不得使用“揭示你的真实性格”“预测命运”“找到命定伴侣”等无法验证的承诺。

### 3.2 生肖模块定位

模块名称为“生肖文化”，包含两个用户意图：

- 查我的生肖；
- 认识十二生肖。

“查我的生肖”回答一个边界明确的问题：按中国农历年界，这个公历出生日期属于哪个农历干支年和生肖。

“认识十二生肖”提供不依赖个人资料的公共文化内容，例如十二生肖次序、地支对应、六十年循环基础、经核验的历史材料与民间故事。

### 3.3 星座模块定位

模块名称为“星座文化”，第一版包含：

- 查我的太阳星座；
- 认识十二星座；
- 了解本工具采用的热带黄道日期表和临界日期处理方式。

第一版只回答大众日期表口径下的太阳星座查询问题，不把简化结果包装成完整占星分析。

## 4. 首页信息架构与路由

首页使用同一视觉分组展示“生肖与星座”，但提供两个独立操作：

- “查我的生肖”进入 `/tools/shengxiao`；
- “查太阳星座”进入 `/tools/constellation`。

不新增 `/tools/zodiac` 等中转路由，避免用户为了完成一次简单查询多走一步。

两个工具页底部可以使用弱链接互相引导，但不得在用户提交一次日期后自动计算另一个体系，也不得把两个结果并列成所谓“东西方人格交叉验证”。

## 5. 内容真实性分类

每项公开内容必须归入以下类别之一：

| 类别       | 定义                                         | 展示要求                                 |
| ---------- | -------------------------------------------- | ---------------------------------------- |
| 可复算事实 | 可以由明确输入、确定规则和版本重复计算       | 展示输入口径、规则版本和结果             |
| 传统分类   | 来源于特定传统体系的分类或对应关系           | 明确“传统分类”，列出来源和流派边界       |
| 文化解释   | 历史、文学、艺术、民俗或现代占星文化中的解释 | 说明出处或采用的内容体系，不写成个人事实 |
| 民间故事   | 流传故事、传说或习俗                         | 明示“民间故事”，不得伪装成历史事实       |

以下内容不得进入上述类别并公开：

- 由随机数、日期种子或任意权重生成的个人运势；
- 不能指出具体来源或计算规则的人格判断；
- 把传统分类直接转换为现实中的健康、财富、婚姻或职业结论；
- 用“古籍有云”替代可定位的书名、卷次、章节或页码；
- 为填补缺失输入而暗中使用当前日期、默认时刻、默认地点或示例资料。

## 6. 共享输入与数据生命周期

### 6.1 最小输入

两个第一版个人查询只需要完整公历出生日期：年、月、日。

不得要求以下无关字段：

- 姓名或“真实姓名”；
- 性别；
- 出生时刻；
- 出生地点；
- 婚恋、职业、学业等个人状态。

出生年份用于校验支持范围、与本人档案一致地带入完整日期，并为未来规则升级保留明确输入；不是为了推断年龄、身份或人生阶段。

### 6.2 输入组件

两个页面复用标准化的 `BirthDateInput` 交互契约：

- 采用适合移动端的年月日选择器；
- 只能提交真实存在的日期；
- 闰年二月二十九日按公历规则校验；
- 不允许未来日期；
- 支持范围为 1901 年至查询当日；
- 不让用户同时填写公历和农历；
- 生肖所需农历日期由系统从公历自动换算。

### 6.3 游客与本人档案

游客可以直接输入日期并查询完整的第一版结果。登录不是计算前置条件。

登录用户可以主动点击“从本人档案带入”：

- 本人档案有完整出生日期时，显式填入当前表单；
- 本人档案缺少日期时，不报错、不跳转，继续允许用户临时填写；
- 带入后的日期仍然只是当前表单值。

用户修改带入日期时：

- 当前结果按修改后的日期计算；
- 本人档案保持不变；
- 页面不得自动询问或暗示必须覆盖档案；
- 如未来提供“更新本人档案”，必须是独立、明确的保存操作，并在保存前展示差异和征得确认。

### 6.4 不保存原则

两个工具第一版均遵守：

- 不自动保存输入；
- 不自动更新本人档案；
- 不向服务端写入查询历史；
- 不提供服务端历史记录列表；
- 刷新后允许清空本次结果；
- 页面不得为了生成结果调用历史保存 API。

因此两个工具第一版的 `historyPolicy` 均为 `disabled`。结果只保留在当前页面属于未保存结果生命周期，不是另一种历史策略。

理由是两个查询确定、廉价且可重复计算，保存完整出生日期与结果历史没有必要性。

### 6.5 本地导出

若保留本地导出，默认生成“隐私文化卡片”：

- 可以包含生肖或太阳星座、相关基础分类、采用的规则版本；
- 不包含完整出生日期；
- 不包含昵称、账号标识、本人档案标识；
- 导出在客户端完成，不以服务端保存为前提。

第一版没有明确用户价值时，可以不增强导出能力，但不得为导出引入结果历史。

## 7. 共享结果状态与失败契约

两个领域服务统一使用全局 `ToolResultState`，不得把阶段、成功限定和失败原因压缩成另一套总状态：

| `phase`      | 限定字段                                                                      | 含义                       | 页面行为                               |
| ------------ | ----------------------------------------------------------------------------- | -------------------------- | -------------------------------------- |
| `idle`       | 无                                                                            | 尚未提交                   | 只展示输入和规则摘要，不展示默认结果   |
| `editing`    | 无                                                                            | 正在填写或修改             | 保留草稿并进行字段校验                 |
| `ready`      | 无                                                                            | 输入已完整且可提交         | 允许用户主动生成                       |
| `processing` | 无                                                                            | 正在生成                   | 禁止重复提交，保留输入                 |
| `success`    | `successQualifier = unique`                                                   | 得到唯一结果               | 展示结果、解释、规则与来源             |
| `success`    | `successQualifier = candidate`                                                | 太阳星座日期表临界日       | 展示主结果、相邻候选和临界说明         |
| `failure`    | `failureCategory = invalid_input`                                             | 日期格式或日历合法性错误   | 指向具体字段，不调用引擎               |
| `failure`    | `failureCategory = unsupported_input`、`failureDetailCode = UNSUPPORTED_DATE` | 日期真实存在但超出支持范围 | 说明当前支持范围，不进行近似计算       |
| `failure`    | `failureCategory = engine_error`                                              | 换算或计算引擎异常         | 说明未能生成，允许重试，不返回替代结果 |

生肖的农历新年边界按具体日期确定，不使用候选限定。`successQualifier = candidate` 仅用于第一版太阳星座日期表的临界日。

禁止的隐式行为：

- 日期缺失时使用今天；
- 年份缺失时使用当前年；
- 把示例生肖或星座当作用户结果；
- 失败时返回随机内容；
- 把输入错误统一伪装成“系统繁忙”；
- 规则升级后静默重算旧结果；
- 在浏览器或服务端日志中记录完整出生日期或本人档案对象。

## 8. 生肖历法与年界规则

### 8.1 生肖年界

民俗生肖查询采用中国农历正月初一 00:00 作为新生肖年的开始，时间口径为中国标准时间。

生肖页面不提供“春节/立春”切换。一个普通查询工具应采用清晰稳定的单一口径，而不是把不同用途的规则交给不了解领域的用户自行选择。

### 8.2 与八字年柱的关系

八字模块的年柱采用精确立春节气作为边界。生肖与八字处于立春至农历新年之间时，可能出现不同年份归属。

页面必须解释：

> 本页按农历正月初一判断民俗生肖；八字年柱按精确立春判断。两者服务于不同的文化与术数用途，因此可能出现不同结果，并不代表其中一个计算错误。

用户需要判断八字年柱时，应进入八字工具。生肖页面不得自行实现一个简化的立春八字年柱结果。

### 8.3 换算边界

领域引擎必须返回所用农历年的公历起止日期，使用户可以理解结果边界。超出已验证换算范围时返回 `failureCategory = unsupported_input`、`failureDetailCode = UNSUPPORTED_DATE`；换算异常时返回 `failureCategory = engine_error`，并使用领域详细代码说明失败位置。

禁止用公历年份对 12 取模作为农历换算失败的后备结果。

## 9. 生肖结果数据契约

### 9.1 第一层：基础结果

第一层必须优先展示用户能理解和核验的内容：

- 用户输入的公历日期；
- 换算后的农历日期；
- 农历干支年；
- 生肖动物；
- 对应地支；
- 该生肖农历年的公历开始日期与结束日期；
- 规则版本与来源入口。

### 9.2 第二层：进阶传统分类

进阶区域可折叠展示：

- 年干阴阳；
- 年干五行；
- 年支五行；
- 六十甲子纳音。

字段命名必须准确：

- 现有 `ANIMAL_WUXING` 对应的是地支五行，用户界面应写“年支五行”或“生肖所对应地支的传统五行”，不能写成“你的生肖五行”；
- 纳音是六十甲子的传统分类，不代表个人整体五行强弱，也不能直接推出喜用神、性格、职业或命运；
- 年干五行、年支五行和纳音是三个不同概念，不能合并成一个“命中属性”。

### 9.3 建议结构化输出

生肖领域服务至少返回：

```ts
interface ShengXiaoResult {
  phase: 'success'
  successQualifier: 'unique'
  freshness: 'current'
  inputDate: string
  lunarDate: string
  lunarYear: number
  ganZhiYear: string
  animal: string
  earthlyBranch: string
  stemElement: string
  branchElement: string
  yinYang: string
  naYin: string
  yearBoundary: {
    startDate: string
    endDate: string
    timezone: 'Asia/Shanghai'
  }
  ruleVersion: string
  sourceRefs: string[]
}
```

类型示例用于约束职责，不要求实施时逐字采用这些英文命名；但不得删除状态、年界、规则版本和来源引用。

## 10. “认识十二生肖”公共文化内容

公共文化内容不需要输入个人资料，可以展示：

- 十二生肖固定次序；
- 生肖与十二地支的对应；
- 生肖年份示例和六十甲子循环基础；
- 来源明确的历史记载；
- 明示为民间故事的生肖传说；
- 来源明确的文学、绘画、雕塑、邮票或节俗材料。

用户浏览另一个生肖时，只切换公共文化内容，不得创建虚构个人上下文。尤其不得自动产生：

- 代表出生年并把它当作用户出生年；
- 对应纳音并把它当作用户纳音；
- 用户年龄；
- 用户性格、运势或婚配结果。

### 10.1 文化形象

现有“生肖性格优点/缺点”必须退出。可替换为“文化形象”，但每条内容必须关联具体的故事、成语、文学、艺术或研究来源。

表达应是：

> 在某一故事或文化表达中，某动物常被塑造成……

不得表达为：

> 属某生肖的人天生……

不得再用正面、负面性格清单对用户贴标签。生肖自我测评等互动不进入第一版。

## 11. 地支关系与年度关系

### 11.1 公共关系图谱

在来源逐项核验后，可以保留中性的“地支关系图谱”，展示三合、六合、冲等传统分类。

该图谱：

- 只说明传统分类结构；
- 不判断情侣、夫妻、朋友或同事是否合适；
- 不输出成功率、分数、“中吉”或最佳/最差对象；
- 不把某一组地支关系当作完整合婚结论。

现有 `SANHE_GROUPS` 与 `LIUHE_PAIRS` 可以在核验后进入新领域数据；冲、害、刑、破必须分别核验，不得因为结构相似就一次性视为已验证。

### 11.2 年度地支关系

第一版可以保留一个默认收起的“年度地支关系”区域，内容限于：

- 查询日期所属的当前农历干支年；
- 用户出生农历年的地支；
- 二者命中的、已经核验来源的传统关系；
- 计算基准日、当前农历年起止日期、规则版本。

当前年必须由显式传入的 `asOfDate` 按中国农历年界计算，领域逻辑内部不得任意读取 `new Date().getFullYear()`。

若命中多种关系，客观列出全部；若未命中本页支持的关系，写“未命中本页列示的关系”，不得写“平”。

该区域不得使用红色/绿色表达危险或吉利，不得输出年度总运、事业、财富、感情、健康、每月走势或行动建议。

## 12. 生肖必须删除、延期与保留的内容

| 现有或候选内容                       | 第一版决定                     | 理由                           |
| ------------------------------------ | ------------------------------ | ------------------------------ |
| 公历转农历、干支年、生肖、地支       | 保留并纠错                     | 可复算事实                     |
| 年干阴阳、年干五行、年支五行、纳音   | 保留并准确命名                 | 传统分类，可查表复算           |
| 十二生肖次序和地支对应               | 保留                           | 公共文化基础                   |
| 来源核验后的历史与民间故事           | 保留并分类                     | 文化学习价值                   |
| 生肖人格优缺点                       | 删除；可重写为文化形象         | 不能把群体刻板印象当个人事实   |
| 生肖婚配、最佳/忌配、分数与成功率    | 删除                           | 规则过度简化并误导关系决策     |
| 三合、六合、冲等地支关系             | 仅作为公共图谱，逐项核验       | 分类不等于现实关系结论         |
| 年度地支关系                         | 限定保留                       | 只展示客观关系，不生成运势     |
| 年度与每月 0–100 分、旺平弱          | 永久移除现有逻辑               | 工程权重和种子不是真实规则     |
| 事业、财富、感情、健康预测和建议     | 删除                           | 无法由生肖基础规则推出         |
| 幸运数字、幸运颜色、幸运物、宜忌颜色 | 删除                           | 来源和作用链不成立             |
| “幸运方位”                           | 删除；核验后可改为地支传统方位 | 方位对应不等于能带来好运       |
| 个性化“化太岁”及操作建议             | 退出结果页                     | 涉及宗教民俗与功效暗示         |
| 个性化“本命佛”                       | 完全退出第一版                 | 当前经文归因和功效承诺不能成立 |

### 12.1 “化太岁”边界

未来如有充分研究价值，可将其作为独立的宗教民俗史或文化文章重新审计，说明不同传统、地区和机构的差异。不得向个人提供“消灾”“转运”等效果承诺，也不得在生肖结果中给出仪式或消费引导。

### 12.2 “本命佛”边界

现有生肖—佛菩萨映射、功效说明和经文归因不能继续公开。当前所称《佛说大乘无量寿庄严清净平等觉经》依据，在可检索经文中不能支撑该映射和相关功效承诺。

未来若重新研究，只能以宗教史、民俗传播或现代文化现象为题，经过独立来源审计后发布；不能恢复个性化护佑、消灾、延寿、化血光、旺事业等承诺。

## 13. 太阳星座采用的体系

### 13.1 单一公开口径

第一版采用西方热带黄道十二宫的大众日期表，不向用户提供体系切换。

它不等同于：

- 恒星黄道体系；
- 印度占星体系；
- 国际天文学联合会划分的实际星座边界；
- 蛇夫座或所谓十三星座日期表。

页面必须说明：热带黄道星座是把黄道划分为十二个等长 30° 区段的占星文化体系，并不等于现代天文学中的实际星座范围。占星属于文化与信念体系，本工具不把它表述为经过科学验证的人格测量或未来预测。

### 13.2 第一版计算含义

第一版结果应准确命名为：

> 按本工具采用的热带黄道大众日期表查询太阳星座。

它不是基于精密天文星历计算太阳黄经的完整本命盘结果。采用的日期表必须版本化，边界和限制对用户可见。

## 14. 太阳星座日期与临界日

### 14.1 唯一日期

不在日期表临界日的合法日期返回 `phase = success`、`successQualifier = unique`，展示唯一太阳星座。

### 14.2 临界日期

处于本工具声明的相邻星座临界日期时返回 `phase = success`、`successQualifier = candidate`：

- 仍按当前日期表给出主结果；
- 同时列出相邻候选；
- 解释不同年份的太阳换座精确时刻可能有差异；
- 说明若未来需要精确判断，应使用可靠星历并补充年份、准确时刻与时区信息。

不得：

- 创造“混合星座”或“交界人格”；
- 让用户根据哪段性格更像自己来选择结果；
- 暗中用固定日期表伪装为天文精确计算；
- 在未来升级精密星历后静默覆盖旧版本结果口径。

## 15. 太阳星座结果数据契约

### 15.1 基础结果

第一版可以展示：

- 用户输入的公历日期；
- 采用的体系：热带黄道；
- 主太阳星座；
- 临界日时的相邻候选；
- 当前日期表版本；
- 规则版本和来源入口。

### 15.2 传统和现代分类

在来源核验完成后，可以展示：

- 四元素：火、土、风、水；
- 三模式：本位、固定、变动；
- 二分法：阳性、阴性；
- 传统宫主星；
- 现代对应行星。

原“守护星”统一改为更准确的“传统宫主星”和“现代对应行星”，不得写成某颗行星真实地保护用户。

天蝎座、水瓶座、双鱼座必须明确传统与现代体系的区别：

其他星座按所采用体系显示单一或一致的对应关系，但仍必须在来源账本中声明口径。

## 16. 星座文化形象与自我反思

### 16.1 文化形象

可以保留十二星座文化形象，但必须从直接人格断言改成对特定现代占星文化体系的项目原创摘要。

合格表达：

> 在本页采用的现代占星文化叙述中，某星座常被赋予……的形象。

不合格表达：

- “你天生就是……”；
- “你的真实内心……”；
- “你的最大缺点……”；
- “你一定适合某职业或某类伴侣”。

十二星座应使用统一的结构和相近篇幅，不能对部分星座堆砌赞美、对另一些星座集中负面标签。内容必须由项目重新撰写，不复制商业网站受版权保护的长段落。

### 16.2 轻量反思提示

第一版可以在文化形象之后提供纯文本反思问题：

- 哪些描述与你的真实经历相符？
- 哪些描述并不符合你？
- 你的成长经历、环境和主动选择是否能提供更具体的解释？

第一版不提供按钮、表单、分数、保存、报告或档案写入。用户觉得“很准”也不能作为占星有效性的证明。

## 17. 星座高级能力的输入事实

月亮星座、上升星座和完整星盘属于占星领域，可以作为未来独立迭代研究，但不能使用当前简化算法继续公开。

### 17.1 月亮星座

未来最低需要完整公历日期。若用户不知道出生时刻：

- 应计算该自然日覆盖的完整时间范围；
- 全天月亮都在同一星座时，才可以返回唯一结果；
- 当天跨越星座时，返回候选范围；
- 出生地点可帮助确定时区和自然日边界。

不得仅凭出生年份计算月亮星座。

### 17.2 上升星座

未来必须要求：

- 完整出生日期；
- 尽可能准确的出生时刻；
- 出生城市，用于时区和地理位置处理。

用户不知道出生时刻时，上升星座不可计算；不得猜测或补默认值。

### 17.3 完整星盘

未来只有在具备以下条件后才进入实现计划：

- 可靠星历；
- 时区与历史时区处理；
- 地理坐标；
- 明确宫制；
- 可重复的黄金样例；
- 对误差、未知时刻和边界情况的结果契约。

## 19. 领域与页面架构

### 19.1 可以共享的能力

两个工具只共享以下基础设施：

- `BirthDateInput`；
- 公历日期合法性和支持范围校验；
- “从本人档案带入”的显式交互；
- 统一结果状态与通用错误表现；
- 来源入口和移动端基础组件。

### 19.2 必须分离的领域

生肖领域负责：

- 公历转农历；
- 正月初一生肖年界；
- 干支、生肖、阴阳、年干/年支五行与纳音；
- 年度地支关系；
- 生肖公共文化数据；
- 生肖来源登记。

西方星座领域负责：

- 热带黄道大众日期表；
- 临界日期候选；
- 元素、模式、阴阳和宫主星分类；
- 星座文化形象；
- 星座来源登记。

不得为了“统一”而合并为一个生肖/星座结果对象、一个运势引擎或一套共同的性格标签。

### 19.3 页面职责

页面只负责：

- 呈现输入；
- 调用对应领域服务；
- 根据结构化状态渲染结果；
- 展示解释、来源和边界；
- 处理本次会话中的用户交互。

页面不得：

- 自行计算生肖、干支或太阳星座；
- 为浏览项创建代表年份；
- 拼装随机人格、运势或建议；
- 自动保存结果或档案；
- 在失败后切换到近似算法。

### 19.4 内容与算法分离

文化说明使用按稳定键索引的内容登记表，不写入计算函数。计算引擎返回字段和引用 ID，展示层再从经审核的内容库读取说明。

这使规则测试、内容审校、来源更新和界面编排可以分别进行，避免修改文案意外改变计算结果。

## 20. 来源与版本治理

### 20.1 来源记录结构

每个正式来源记录至少包含：

```ts
interface SourceRecord {
  sourceId: string
  title: string
  locator: string
  linkOrEdition: string
  supportedClaim: string
  sourceStatus:
    | 'verified_primary'
    | 'verified_secondary'
    | 'implementation_only'
    | 'disputed'
    | 'unverified'
    | 'no_source'
  sourceReviewStatus: 'unreviewed' | 'in_review' | 'approved' | 'rejected'
  adoptedAt?: string
  ruleVersion?: string
}
```

`locator` 必须尽量精确到卷、章、页、条款或网页小节。一个来源只支持它实际覆盖的结论，不能因为一本古籍提到生肖，就让它替整页现代婚配文案背书。

### 20.2 规则版本

以下内容必须独立版本化：

- 公历—农历换算规则或依赖版本；
- 生肖年界规则；
- 六十甲子与纳音表；
- 地支关系表；
- 太阳星座日期表；
- 星座分类和宫主星体系；
- 文化内容版本。

结果页面展示面向用户的简短版本，内部记录完整版本标识。规则更新不得静默改变已有导出或历史快照的含义。

### 20.3 页面呈现

每个结果页使用正常文档流中的“依据与范围”区域，至少解释：

- 采用的体系；
- 计算边界；
- 结果不代表什么；
- 主要来源；
- 规则版本。

不恢复悬浮“注”按钮，不使用会在移动端遮挡、溢出或引发自由缩放的弹层实现。

## 21. 现有实现审计与整改边界

以下是制定本契约时确认的现有实现问题。实施前仍需以当时分支代码定位为准，但不得偏离本契约裁决。

## 22. 隐私与日志边界

虽然第一版只处理出生日期，仍按个人信息最小化原则实施：

- 不因查询要求用户注册；
- 不把出生日期添加到 URL、埋点、报错文本或普通日志；
- 不向第三方分析服务发送完整出生日期；
- 前端异常日志和服务端日志不得包含完整表单或本人档案对象；
- 不建立生肖或星座查询历史表；
- 不以“改善体验”为由默认保存日期；
- 用户主动使用本人档案时，沿用《用户档案与数据生命周期产品规范》的授权、保存和删除边界。

## 23. UI、移动端与可访问性

### 23.1 信息层级

保留现有墨韵视觉语言，结果内容按以下顺序组织：

1. 输入与当前采用的体系；
2. 核心唯一结果或临界候选；
3. 用户能理解的简短解释；
4. 可折叠的进阶分类或文化内容；
5. 依据与范围；
6. 另一个工具的弱链接。

信息层级可以调整，既有 UI 不构成继续展示错误内容的理由。

### 23.2 移动端

必须在 320、360、390、414 CSS 像素宽度验证：

- 页面没有横向溢出；
- 日期选择器不会超出视口；
- 主按钮、档案带入按钮和返回操作不会重叠；
- 长星座名称、干支、纳音、边界日期和来源链接可以自然换行；
- `successQualifier = candidate` 的双结果在窄屏仍能分辨；
- 依据与范围处于正常文档流，不使用固定最小宽度的浮层；
- 200% 文本缩放后内容不遮挡、不丢失；
- 不通过禁止用户缩放来掩盖布局问题。

### 23.3 可访问性

- 所有输入具有可见标签和错误关联；
- 按钮可以键盘聚焦和触发；
- 展开区域有明确状态；
- 成功、警告与失败不只依赖颜色区分；
- 支持 `prefers-reduced-motion`；
- 链接文本能说明将打开的依据，不使用孤立的“点击这里”。

## 24. 验收标准

### 24.1 生肖规则

- 1901 年至查询当日的合法日期均能进入声明的支持路径；
- 每个农历新年前一天、当天、后一天均有边界测试；
- 至少覆盖立春至农历新年之间生肖与八字年柱可能不同的样例；
- 六十个干支年和十二个生肖—地支对应全部覆盖；
- 年干阴阳、年干五行、年支五行完整覆盖；
- 六十甲子纳音完整覆盖；
- 当前农历年在年界前后计算正确；
- 已支持的年度地支关系组合全部测试；
- 换算异常时不回退公历取模或默认生肖；
- 核心结果与 GB/T 33661—2017、中国香港天文台公农历对照表和一个独立日历引擎进行交叉核对。

### 24.2 太阳星座规则

- 支持范围内所有合法日期均能按已声明日期表分类；
- 十二星座各至少有一个非临界代表日期黄金样例；
- 日期表声明的全部临界日期均返回 `phase = success`、`successQualifier = candidate`；
- 闰年二月二十九日可用，非闰年二月二十九日被拒绝；
- 未来日期被拒绝；
- 元素、模式、阴阳和宫主星表完整覆盖十二星座；
- 天蝎、水瓶、双鱼的传统与现代对应明确区分；
- 第一版结果对象不含月亮、上升、宫位、相位和星盘字段。

### 24.3 禁止内容

生产页面、领域输出、客户端数据、服务端响应和本地导出均不得出现：

- 生肖或星座个人运势分数；
- 事业、财富、感情、健康预测；
- 幸运数字、幸运颜色、幸运日期、幸运物；
- 生肖或星座配对成败、分数与最佳/忌配；
- 直接人格优缺点和确定性人格断言；
- 个性化本命佛、化太岁功效与操作建议；
- 今日宜忌；
- 用缺失输入推算的月亮、上升或星盘；
- 失败后生成的随机或默认个人结果。

### 24.4 数据生命周期

- 游客可以完成两个第一版查询；
- 首次打开不跳转登录、不自动计算；
- 登录用户只能通过主动操作带入本人档案日期；
- 本人档案无日期时仍可临时输入；
- 修改带入日期不更新本人档案；
- 生成结果不触发任何服务端历史写入请求；
- 页面不存在生肖/星座结果历史入口；
- 若提供本地导出，默认不包含完整出生日期和账号信息；
- 正常日志和异常日志不记录完整出生日期。

### 24.5 来源与说明

## 25. 实施边界与推荐迭代顺序

本文不直接授权一次性修改全部代码。后续应拆成可独立审查、可回退的小迭代：

1. 建立来源账本、规则表和黄金样例，先解决“什么才是正确结果”；
2. 重构共享日期输入、状态和显式档案带入，不改变两个领域的独立性；
3. 收口生肖核心查询，删除自动保存、伪运势和错误个人化内容；
4. 重建生肖公共文化和年度地支关系；
5. 收口太阳星座核心查询和临界日期；
6. 重写星座文化形象，移除简化高级占星和伪运势；
7. 完成移动端、可访问性、来源展示和全链路验收。

每个迭代在生成实施计划前都要重新核对当前代码、依赖、测试基线和已验证来源。不得把本节当作可直接执行的 YAML 计划。

## 26. 第一版之外

以下内容不进入本规范第一版：

- 月亮星座、上升星座、完整星盘、宫位、相位和行运；
- 生肖或星座互动自我测评；
- 生肖或星座关系匹配；
- 基于可靠行运体系的娱乐性趋势内容；
- 个性化太岁或宗教民俗建议；
- 生肖、星座结果云端历史；
- AI 解读；
- 境外出生地点与历史时区体系。

未来加入这些能力时，必须重新完成产品价值、必要输入、数据最小化、规则来源、错误状态和验收标准讨论，不能从当前隐藏代码直接恢复。

5. 核对现有《三命通会》引用卷次，不允许继续使用错误的“卷三·论生肖”笼统注释；
6. 为十二生肖文化形象逐条确定历史、文学、艺术或民俗来源；
7. 固定太阳星座大众日期表版本、临界日清单和对用户的精度说明；
