## 1. 文档目的

本文是 XuanXue 现有 `zeji` 模块第一版打磨的正式产品与领域规范。用户可见名称统一为“日期对照”；`zeji` 仅作为内部模块标识和旧路由兼容名。后续页面、领域模块、服务端接口、来源账本、导出组件和测试必须与本文保持一致。

本文解决以下问题：

- 日期对照究竟帮助用户做什么；
- 单日资料浏览和事项比较如何共用同一领域模块；
- 第一版候选事项如何按证据选择首批公开范围；
- 日期和事项如何输入；
- 宜忌记录如何形成五种比较状态；
- 什么内容属于历法事实、传统分类或项目处理；
- 来源尚未核验、部分日期失败或规则被撤回时如何降级；
- 当前公开服务器与本地开发环境如何执行不同访问边界；
- 当前页结果、重新比较和本地导出如何避免制造推荐含义；
- 日期事实、事项和传统背景如何分别获得公开资格；
- 什么条件全部通过后，对应能力才可以进入公开试运行。

本文不负责直接修改代码，不替代来源专项审计，也不构成对任何择日传统有效性的现实承诺。

## 2. 已批准的核心结论

1. 用户可见名称为“日期对照”，不是“最佳吉日推荐器”；内部模块标识继续使用 `zeji`。
2. 日期对照是第一版候选增强功能，不是第一版交付的阻塞项；证据链未闭合时继续保持内部状态。
3. 同一领域模块提供“查看某一天”和“比较一件事”两个独立入口，未开放入口完全不出现。
4. 产品分为日期事实、事项对照和传统背景三层；三层以及每个事项、每个背景字段分别获得公开资格。
5. 工具只说明指定资料和规则如何记录日期，不预测事情能否成功。
6. 八类事项进入审计池；首批只开放通过全部门槛的两至三类，不预先承诺具体名单。
7. 安葬延期；求医从产品、规则、接口和测试中真实删除。
8. 事项使用“现代分组 + 白话子类型 + 传统术语回显”；宜忌采用受控精确术语映射，禁止自由文本和字符串包含匹配。
9. 领域层保留“宜项匹配、宜忌并见、忌项匹配、未明确记录、数据不可用”五种内部状态；用户界面使用白话标题和解释。
10. 删除全部 0—100 分、排行、阈值、最佳日期、强制前五名和“吉日推荐”。
11. 十二值、天神、黄黑道和二十八宿只能作为独立传统背景；未分别通过文献、解释和实现核验的字段不显示，也不参与事项状态。
12. 单日查看只输入一个公历日期并自动换算农历，可查询已核验资料范围内的过去、今天或未来日期。
13. 事项比较输入事项、必要子类型、开始日期和结束日期；默认今天起三十个自然日，可切换六十日、九十日或自定义范围，最大九十日。
14. 两个入口都不需要姓名、性别、出生信息、地点、时刻或本人档案。
15. 所有日期按 `Asia/Shanghai` 解释；页面不得依据设备时区改变查询含义。
16. 用户必须主动查看或比较；修改输入后旧结果进入 `stale`，不得自动重新计算。
17. 任何日期计算失败都必须显式返回；禁止捕获异常后跳过日期。
18. 列表是事项比较的主要阅读方式，默认按日期升序；日历只承担日期定位和范围概览。
19. 来源、映射、规则、提供器和结果都必须带版本；依赖库是实现提供器，不是传统依据。
20. 第一版不创建服务器历史；结果只保留在当前页面，游客和登录用户能力一致。
21. 导出只生成用户主动选择的一至五个完整日期的本地 PNG 比较卡片，不截取整个页面、不上传服务器。
22. 部分失败允许导出成功日期，但页面和图片都必须披露本次范围的数据缺口。
23. 当前服务器属于 `public_preview` 环境；未宣传不等于私有。
24. 日期对照当前为内部审核功能，普通公开访客不能调用尚未批准的能力。
25. 第一版采用 Nuxt 3 模块化单体，由服务端统一计算和围栏，不拆 Spring Boot 后端、微服务或 AI 服务。
26. 文献存在性、术语映射、程序实现和公开批准是四个独立状态；“来源已核验”不得写成“预测能力已验证”。
27. 自动化、Codex 内置浏览器、用户真实手机和公开环境复验全部通过后，对应能力才可以公开。

## 3. 当前实现审计

本节记录本文制定时的实现事实，用于明确整改起点，不表示批准保留现有行为。

### 3.1 当前领域引擎

`composables/useZeJi.ts` 当前：

- 在客户端组合式函数中直接调用 `lunar-javascript`；
- 使用事项关键词的相等或字符串包含匹配；
- 将十二值、天神和宜忌匹配合成为 0—100 分；
- 使用 65 分作为推荐阈值；
- 将推荐日期按分数降序排列并保留前十五名；
- 按完整公历月份处理，而不是按用户精确选择的起止日期处理；
- 捕获单日异常后直接跳过该日期；
- 非法事项返回空结果，而不是明确拒绝输入。

这些行为均不符合本文。

### 3.2 当前事项和传统文案

`constants/zeji.ts` 当前：

- 包含十类事项，其中安葬和求医不属于第一版公开范围；
- 多个关键词重复；
- 将近义词、相关仪式和不同事项混入同一关键词数组；
- 将“破土”混入修造；
- 将“求嗣”等扩展内容混入祭祀；
- 将“订盟”混入会友；
- 使用“百事吉”“万事不宜”“成事可期”等未经逐条核验的强断语；
- 虽然注释承认评分是开发者合成，页面仍把评分作为用户结论展示。

### 3.3 当前页面与用户流程

`pages/tools/zeji.vue` 当前：

- SEO 和页面文案宣称“推荐”“最佳日期”；
- 用户选择事项后立即调用历史保存；
- 没有独立的开始比较动作；
- 无推荐日期时仍按分数回退展示前五名；
- 详情继续显示评分和吉凶等级；
- 历史恢复会把旧结果重新放回交互页面；
- 导出使用整个结果容器截图；
- 来源通过浮动 `MethodologyNote` 展示。

### 3.4 当前保存、状态与依赖

- 通用 `/api/divinations` 接口接收客户端提交的 `result_data`，没有择日领域级重算和结构验证；
- 工具目录只有 `listed / hidden`，且择日当前为 `listed`；
- 状态页只能显示统一的“功能整理中”；
- 隐藏工具历史会被列表过滤，无法表达只读历史；
- `package.json` 使用 `lunar-javascript` 的 `^1.7.7` 范围，`package-lock.json` 当前解析到 1.7.7；
- 现有测试主要验证结构、分值范围和表项存在，不是来源真实性测试。

## 4. 产品定位与用户价值

### 4.1 用户可见名称与正式定位

导航、首页、页面标题和导出使用“日期对照”。公开说明为：

> 查看某一天的传统历法记录，或按事项比较近期日期；每条公开内容都说明资料、规则、版本和已知限制。

“择日”只作为传统文化类别说明、搜索辅助词和内部模块含义，不能作为“系统替用户挑选吉日”的承诺。

### 4.2 双入口

同一领域模块提供两个入口：

1. `date_lookup`：查看某一天，回答该日的历法事实以及已经独立核验的传统记录；
2. `activity_compare`：比较一件事，回答指定资料中是否直接记录了用户所选事项。

两个入口共用日期事实提供器、来源注册表、传统字段目录和版本体系，但分别获得公开资格。某个入口没有通过时完全不出现，不显示禁用卡片、完成百分比或虚假日期。

### 4.3 能够回答的问题

- 某一公历日期对应什么农历、星期、干支或节气事实；
- 某一日期的资料中是否明确记录了所选事项；
- 该事项出现在宜项、忌项、两者、两者皆无，还是当天资料不可用；
- 某项展示来自哪条原始记录、项目映射和规则版本；
- 为什么某一日期被归入当前内部状态；
- 哪些事项和传统背景已经公开，哪些仍在审核或已撤回。

### 4.4 不能回答的问题

- 哪一天客观上最好；
- 选择某日是否保证成功；
- 某日能否决定婚姻、经营、学业或其他现实结果；
- 哪一天比其他日期高多少分；
- 用户应当服从哪一天；
- 未经来源支持的“诸事皆宜”或“万事皆凶”；
- 传统记录是否已经获得科学有效性验证。

### 4.5 使用边界

日期对照是传统文化资料浏览和信息比较，不替代现实安排、专业意见、安全判断、医疗判断、法律判断或财务判断。结果不得写成行动命令。

页面在开始比较附近显示通用边界：

> 本工具只对照传统资料中的日期记录，不判断事情能否成功。请优先考虑现实安排、安全条件和专业意见。

## 5. 第一版候选事项目录

### 5.1 八类审计池

以下八类只获得进入审计池的资格，不代表全部进入第一批公开范围：

| 事项分组   | 产品含义                   | 子类型原则                             |
| ---------- | -------------------------- | -------------------------------------- |
| 婚礼与嫁娶 | 查询婚礼、嫁娶相关传统记录 | 只映射经核验的正式术语                 |
| 开市与开业 | 查询经营开始相关传统记录   | 开市、开业不得因现代近义自动合并       |
| 搬迁与入住 | 用户友好的上层分组         | 移徙、入宅等传统术语必须保留独立子类型 |
| 出行       | 查询出行事项记录           | 不扩展旅游、远行等未核验同义词         |
| 修造与动土 | 用户友好的上层分组         | 修造、动土必须独立；破土不得自动并入   |
| 祭祀       | 查询祭祀事项记录           | 不自动扩展祈福、求嗣或其他仪式         |
| 会亲友     | 查询会亲友事项记录         | 不自动映射订盟                         |
| 入学       | 查询入学事项记录           | 不自动扩展为考试、升学或学业运势       |

### 5.2 首批选择原则

首批只公开同时通过来源、映射、实现、风险表达和体验门槛的两至三类事项。首批名单不能凭当前代码是否已有数据、事项是否热门或依赖库返回次数决定。

八类事项分别按以下维度审计：

1. 是否有明确文献版本和规则定位；
2. 当前提供器输出能否与固定样本对账；
3. 现代名称与传统术语之间是否不存在未说明歧义；
4. 用户据此作出高风险现实决定的可能性；
5. 普通用户是否能理解结果和限制。

“会亲友”和“入学”可以优先进入审计，但不预先获得公开资格。婚礼、开市、搬迁、修造等高影响事项不得只因来源存在就优先公开。

### 5.3 延期事项

安葬第一版不提供入口、计算、示例或导出。恢复前必须单独完成来源、敏感表达、用户意图、现实风险和公开验收。

### 5.4 删除事项

求医从第一版产品合同中正式删除：

- 不显示入口；
- 不保留计算映射；
- 不生成结果；
- 不进入示例、SEO 或推荐；
- 不以隐藏开关继续作为可恢复公开能力；
- 测试必须断言它无法被提交。

医疗行为不应因为日期对照结果被提前、延迟或取消。

### 5.5 禁止自由文本

第一版不允许用户输入任意事项名称。自由文本会导致未知映射、隐含同义词和无法审计的解释，不符合可追溯要求。

## 6. 事项定义、映射与现实边界

### 6.1 结构化定义

每个事项或子类型必须具有结构化定义：

```ts
interface ActivityDefinition {
  activityId: string
  publicName: string
  subtypeId?: string
  publicDescription: string
  sourceTerms: string[]
  mappingVersion: string
  sourceIds: string[]
  sourceTextStatus: 'unverified' | 'in_review' | 'confirmed' | 'disputed' | 'rejected'
  mappingReviewStatus: 'unreviewed' | 'in_review' | 'approved' | 'rejected'
  implementationStatus: 'not_started' | 'in_progress' | 'passed' | 'failed'
  publicStatus: 'internal' | 'public' | 'suspended' | 'retired'
  boundaryTextId: string
  note: string
}
```

要求：

- `activityId` 和 `subtypeId` 是稳定标识，不使用用户可见名称充当主键；
- 页面先显示现代分组，再在存在实质差异时要求选择白话子类型；
- `publicDescription` 解释用户实际准备做什么，不要求用户先懂传统术语；
- `sourceTerms` 只包含已经逐条审核的精确术语，并在提交前回显；
- 每个术语可追溯到来源和映射版本；
- 禁止 `includes`、单字命中、模糊包含和运行时猜测同义词；
- 相似事项没有审核依据时保持分离；
- 未批准事项不能通过直接构造请求绕过页面提交。

例如“搬迁与入住”必须让用户区分“搬运物品或迁移住所”和“正式进入新居居住”，再分别对照已经核验的“移徙”或“入宅”；不能把多个术语一次塞入关键词数组。传统术语的精确定义仍以专项来源审计为准，本文示例不替代该审计。

### 6.2 事项相关现实提醒

事项比较除通用边界外，还显示固定、非个性化的现实提醒：

| 事项类别   | 必须覆盖的现实因素                     |
| ---------- | -------------------------------------- |
| 出行       | 天气、交通、证件、健康与安全情况       |
| 开市或经营 | 市场、合同、许可、财务与经营风险       |
| 搬迁与入住 | 房屋安全、合同、物业、交通与入住条件   |
| 修造与动土 | 施工许可、结构安全、天气与专业工程判断 |
| 婚礼       | 双方意愿、关系沟通、家庭与场地安排     |
| 入学       | 招生、考试、报到要求与学校正式通知     |

提醒由产品固定维护，不读取用户档案、不猜测用户处境、不使用恐吓语气，也不以“仅供娱乐”替代具体边界。导出卡片保留所选事项对应的简短提醒。

## 7. 双入口输入契约

### 7.1 查看某一天

`date_lookup` 只收集一个公历日期：

- 用户通过标准日期选择器输入公历日期；
- 系统自动换算农历，不要求用户重复填写公历和农历；
- 可以查看过去、今天或未来；
- 可选最小和最大日期必须来自已经验证的历法资料覆盖范围，并在页面明确显示；
- 来源专项审计完成前不在本文猜测具体起止年份；
- 用户必须主动点击“查看这一天”，初始不自动计算。

### 7.2 比较一件事

`activity_compare` 只收集：

- 事项；
- 必要时的白话子类型；
- 开始日期；
- 结束日期。

事项初始为空，不默认选择婚礼或其他事项。开始日期默认为中国标准时间下的今天，结束日期默认为开始日期后二十九日；页面不因默认日期自动开始比较。

范围提供三十日、六十日、九十日和自定义选择，并满足：

- 起始日期不得早于中国标准时间下的今天；
- 结束日期不得早于开始日期；
- 范围包含开始日和结束日；
- 最大九十个自然日；
- 超出范围时明确报错，不静默截断；
- 服务端重新验证所有限制。

### 7.3 共同禁止输入

两个入口都不收集：

- 姓名或昵称；
- 性别或传统性别参数；
- 出生日期、出生时刻和出生地点；
- 当前所在地；
- 婚姻、工作、学习或家庭状态；
- 他人资料。

日期对照不依赖本人档案，也不显示“使用已保存资料”。

### 7.4 时间口径

所有“今天”、日期边界、查询条件和结果生成时间均按 `Asia/Shanghai` 解释。设备时区只影响浏览器显示环境，不改变领域日期。

## 8. 用户工作流与页面状态

### 8.1 查看某一天流程

```text
进入日期对照
→ 选择“查看某一天”
→ 选择公历日期
→ 点击“查看这一天”
→ 先看日期事实
→ 按需展开已核验的传统记录、解释和来源
```

该入口不产生事项匹配、评分、推荐或行动建议。

### 8.2 比较一件事流程

```text
进入日期对照
→ 选择“比较一件事”
→ 选择已公开事项和必要子类型
→ 确认实际对照的传统术语
→ 确认或修改日期范围
→ 点击“开始比较”
→ 查看完整性摘要与日期列表
→ 可切换日历定位日期
→ 展开某日证据
→ 可选择一至五个完整日期生成本地 PNG
```

### 8.3 页面状态

两个入口的页面运行状态复用公共 `ToolResultState`，不得另建并列总状态：

- `phase = idle | editing | ready | processing | success | failure`；
- `successQualifier = unique | partial | candidate | empty`，仅在 `phase = success` 时存在；
- `freshness = current | stale`，仅在页面仍持有结果时存在；
- 逐日处理状态、`successfulDayCount`、`failedDayCount` 和 `failureDetailCode` 说明日期资料完整性，但不能替代公共状态字段。

对日期对照而言，完整范围使用 `phase = success`、`successQualifier = unique`；部分日期资料不可用但仍有可展示结果时使用 `phase = success`、`successQualifier = partial`；本次请求没有形成可用结果时使用 `phase = failure` 并填写公共 `failureCategory`。

公共枚举可被单项工具收窄，不能扩展。第一版单日结果只使用 `unique`，事项比较只使用 `unique / partial`；五种事项匹配状态属于逐日领域结果。完整日期记录存在但没有命中事项，仍是可阅读的对照结果；筛选后列表为空也不把原结果改为失败或另一种成功限定。输入改动使用 `freshness = stale`，不新增一个名为 stale 的阶段。

修改事项或日期只修改草稿。只有用户点击对应提交按钮才请求服务端；不自动计算、不自动保存。

### 8.4 过期结果

结果生成后用户修改输入：

- 保留旧结果，避免内容突然消失；
- 明确显示旧结果采用的原查询条件；
- 标记“输入已改变，当前结果尚未更新”；
- 禁止导出；
- 用户再次主动提交后生成新结果。

## 9. 历法提供器与版本

### 9.1 提供器边界

`lunar-javascript` 或未来替代库只负责提供实现数据。领域服务不得把依赖库名称当成来源证明，也不得因为依赖能够返回某字段就自动将该字段交给页面。

提供器必须封装：

- 公历日期与星期；
- 农历日期；
- 干支字段；
- 每日宜忌；
- 十二值；
- 天神和黄黑道；
- 二十八宿；
- 提供器错误。

页面、匹配器和导出组件不得直接调用第三方依赖。提供器可以在内部返回待审核数据，但只有来源和实现状态允许的字段才能进入公开结果。

### 9.2 版本要求

- 依赖使用精确版本；
- 升级先进入内部审核和回归测试；
- 未审核的新版本不能直接替换公开版本；
- 当前页结果和导出卡片保留生成时的提供器和规则版本；
- 固定版本只代表可复现，不代表正确。

### 9.3 双证据链

日期事实和传统规则必须分别建立证据链：

1. 日期事实证据：国家标准、官方或可靠历法资料，用于核验公历、农历、干支、节气和时间边界；
2. 传统规则证据：古籍版本、卷章、原文与解释，用于说明某种记录或分类在声明资料中如何出现；
3. 项目规则：现代事项、白话子类型、传统术语和五态分类之间的明确映射；
4. 实现提供器：固定版本的依赖库或未来替代实现；
5. 验证证据：固定日期、边界日期、合成冲突和独立对账样本。

不得把这些层级合写为一句“依据古籍和算法”。官方历法资料只能核验日期事实，不能自动证明每日宜忌；古籍存在只能证明相关传统记录存在，不能证明其科学预测能力。

### 9.4 四层核验状态

每项公开结论分别记录：

- `sourceTextStatus`：文献原文和版本定位是否确认；
- `mappingReviewStatus`：现代事项、白话解释和传统术语的映射是否批准；
- `implementationStatus`：程序是否按声明规则通过测试；
- `publicStatus`：该能力当前是否允许普通访客使用。

四项不能相互替代。原文确定但解释有争议时，只能在明确的文化资料语境中展示原文，不得参与事项匹配；程序正确但来源不明时仍不得公开；来源和映射完成但代码未验收时也不得公开。

## 10. 五种比较状态

每个日期针对所选事项只能形成以下状态之一：

### 10.1 宜项匹配

经批准的事项术语至少一项出现在当日宜项，且没有出现在当日忌项。

### 10.2 宜忌并见

经批准的事项术语同时在当日宜项和忌项命中。系统如实展示冲突，不自行消解，不隐藏其中一边。

### 10.3 忌项匹配

经批准的事项术语至少一项出现在当日忌项，且没有出现在当日宜项。

### 10.4 未明确记录

当日宜忌数据完整可用，但没有命中该事项的任何已批准术语。

它不等于“普通”“中性”“适合”或“不适合”。

### 10.5 数据不可用

当日数据缺失、依赖异常、结构不符合合同或来源状态不允许使用。

它不等于“未明确记录”。

### 10.6 用户可见白话文案

内部状态名用于领域模型、测试和规则文档，不能直接承担普通用户的主要解释：

| 内部状态   | 用户可见标题             | 必须说明                                 |
| ---------- | ------------------------ | ---------------------------------------- |
| 宜项匹配   | 资料中列有“宜”           | 当天“宜”记录包含所选事项，不预测现实结果 |
| 宜忌并见   | 资料中同时出现“宜”和“忌” | 如实保留冲突，不由系统消解               |
| 忌项匹配   | 资料中列有“忌”           | 当天“忌”记录包含所选事项，不形成行动命令 |
| 未明确记录 | 资料没有提到这项         | 不代表适合，也不代表不适合               |
| 数据不可用 | 本日资料暂不可用         | 当前没有形成完整、可核对的结果           |

每张结果卡首层使用“白话标题 + 一句形成说明 + 查看证据操作”。不得只展示印章、单字吉凶或内部状态名。

## 11. 匹配算法

匹配器只接受：

- 已验证的当日宜项数组；
- 已验证的当日忌项数组；
- 已批准的 `ActivityDefinition`；
- 明确的匹配规则版本。

处理顺序：

1. 对原始条目执行有限、可审计的空白和重复清理；
2. 使用完整术语精确匹配；
3. 分别记录宜项命中和忌项命中；
4. 根据两组命中形成五种状态之一；
5. 输出命中的原始条目和映射标识。

禁止：

- 模糊包含；
- 单字命中；
- 未记录的同义词替换；
- 十二值、天神或二十八宿对宜忌状态加权；
- 分数、权重和阈值；
- 在没有命中时按其他字段强行选出日期；
- 用默认优先级消解宜忌冲突。

## 12. 结果数据契约

两个入口共享结构化来源信息，但使用不同结果信封，避免单日浏览被强行伪装成事项比较：

```ts
interface ResultProvenance {
  providerName: string
  providerVersion: string
  ruleVersion: string
  sourceSetVersion: string
  sourceIds: string[]
  sourceStates: Array<{
    sourceId: string
    sourceStatus:
      | 'verified_primary'
      | 'verified_secondary'
      | 'implementation_only'
      | 'disputed'
      | 'unverified'
      | 'no_source'
    sourceReviewStatus: 'unreviewed' | 'in_review' | 'approved' | 'rejected'
    verifiedFields: string[]
  }>
}

interface ActivityComparisonQuery {
  activityId: string
  subtypeId?: string
  startDate: string
  endDate: string
}

interface DateLookupEnvelope {
  resultId: string
  capability: 'date_lookup'
  query: { solarDate: string }
  timezone: 'Asia/Shanghai'
  generatedAt: string
  phase: 'success' | 'failure'
  successQualifier?: 'unique'
  failureCategory?:
    | 'invalid_input'
    | 'missing_required_input'
    | 'unsupported_input'
    | 'engine_error'
    | 'network_error'
  failureDetailCode?: string
  freshness?: 'current'
  dateRecord?: DateRecord
  provenance: ResultProvenance
  boundaryTextVersion: string
}

interface ActivityComparisonEnvelope {
  resultId: string
  capability: 'activity_compare'
  query: ActivityComparisonQuery
  timezone: 'Asia/Shanghai'
  generatedAt: string
  phase: 'success' | 'failure'
  successQualifier?: 'unique' | 'partial'
  failureCategory?:
    | 'invalid_input'
    | 'missing_required_input'
    | 'unsupported_input'
    | 'engine_error'
    | 'network_error'
  failureDetailCode?: string
  freshness?: 'current'
  requestedDayCount: number
  successfulDayCount: number
  failedDayCount: number
  days: DayComparison[]
  activityVersion: string
  matchingRuleVersion: string
  provenance: ResultProvenance
  boundaryTextVersion: string
}
```

`ActivityComparisonQuery` 只保存服务端已经接受的规范化输入。传统术语、来源状态、匹配状态和结果正文均由服务端按批准目录与规则版本生成，客户端不得提交或覆盖。

以上信封是完成一次请求时的结构约束，不是另一套页面状态机。成功分支必须有 `successQualifier`、`freshness = current` 和对应可用结果，不携带失败类别；失败分支必须有 `failureCategory`，不携带成功限定或伪造的新鲜结果，领域错误使用 `failureDetailCode`。页面编辑、处理中及保留旧结果的 freshness 仍由公共 `ToolResultState` 管理。实施时须以类型与分支测试约束这些字段的互斥关系，不能只依赖可选字段声明。

`DateRecord` 至少包含公历日期、星期、已经核验的农历与干支事实、节气事实、每个传统字段的独立状态、错误代码和对应来源标识。没有通过准入的传统字段不进入公开信封。

每个 `DayComparison` 至少包含：

- 公历日期；
- 星期；
- 农历日期；
- 日期处理状态；
- 五种比较状态之一；
- 命中的宜项；
- 命中的忌项；
- 完整宜项和忌项；
- 已经独立通过准入的传统背景字段；
- 错误原因代码；
- 对应来源和规则标识。

两个结果信封都不得包含评分、排行、最佳标记、推荐布尔值或客户端可以覆盖的来源状态。

## 13. 结果信息架构

页面保持现有墨韵视觉语言，但调整信息层级，不以本文示意替代最终 UI 设计。进入页面后先显示当前已公开的入口；若只有一个入口获得公开资格，直接显示该入口，不展示空壳选项。

### 13.1 单日查看顺序

`date_lookup` 固定阅读顺序为：

1. 用户查询的公历日期与 `Asia/Shanghai` 时间口径；
2. 已核验的公历、星期、农历、干支和节气事实；
3. 已独立通过准入的传统记录；
4. 白话解释；
5. 来源、版本和已知限制。

不得生成事项状态、每日运势、人格判断或行动建议。

### 13.2 事项比较顺序

`activity_compare` 固定阅读顺序为：

1. 查询依据；
2. 完整性与边界；
3. 状态数量与筛选；
4. 日期列表与辅助日历；
5. 选中日期的完整证据；
6. 来源、版本和使用边界；
7. 本地导出和重新比较操作。

### 13.3 查询依据

展示：

- 用户选择的事项和子类型；
- 开始日期和结束日期；
- 总天数；
- `Asia/Shanghai`；
- 生成时间；
- 规则和资料版本。

### 13.4 完整性摘要、排序与筛选

摘要必须显示请求总天数、成功天数、资料不可用天数，以及五种内部状态分别对应的数量。数量是完整性统计，不计算百分比、分数或运势。

日期列表默认且始终可以按公历日期升序阅读，不提供按“宜、忌”或任何隐含好坏排序。允许使用以下中性筛选：

- 全部；
- 资料中列有“宜”；
- 资料中同时出现“宜”和“忌”；
- 资料中列有“忌”；
- 资料没有提到这项；
- 本日资料暂不可用。

每个筛选显示数量，默认选择“全部”。六十日或九十日结果按自然月分组，但不能只保留“最值得关注”的少量日期。

### 13.5 日期列表

列表是主要阅读方式，按公历日期升序排列。每张日期卡片首层只显示：

- 公历日期；
- 星期；
- 农历日期；
- 用户可见白话状态；
- 直接命中的宜项和忌项；
- 展开详情操作。

不得按隐含好坏排序。

### 13.6 日历

日历只用于：

- 定位月份；
- 快速找到某日；
- 查看状态分布；
- 进入日期详情。

日历格不塞入完整宜忌、来源或长解释，不使用大面积红绿颜色表达好坏。五种资料状态使用文字缩写、形状和可读图例共同表达，点击日期后定位到对应列表卡片。移动端不得通过横向拖动整张大日历才能阅读。

### 13.7 日期详情

展开后按顺序显示：

1. 与事项直接相关的宜忌证据；
2. 当前状态如何形成；
3. 当日完整宜项和忌项；
4. 十二值、天神、黄黑道和二十八宿等独立背景；
5. 术语白话解释；
6. 来源和版本。

## 14. 传统背景字段

十二值、天神、黄黑道和二十八宿遵守以下边界：

- 各字段独立展示；
- 不合成为总分；
- 不决定事项比较状态；
- 不互相覆盖；
- 每个字段分别记录文献、解释、实现和公开状态；
- 未通过对应来源和计算核验的字段不进入公开结果；
- 不使用项目自创的吉、凶、上吉、等级或强断语；
- 可以说明“某资料将其归入某类”，不能改写成现实结果。

若第一版只有公历、农历和节气事实通过核验，其余传统背景应继续隐藏，不阻碍事实层单独展示。某个背景字段后来通过验收，只加入“传统背景”解释层，不得改写已经形成的事项状态。

## 15. 术语解释与来源展示

每个专业术语采用三层解释：

### 第一层：当前证据

直接说明该日记录了什么，以及本工具为何显示当前状态。

### 第二层：白话解释

解释术语在本工具采用的资料中表示什么，不把传统分类写成科学事实。

### 第三层：完整证据

展示来源名称、版本、卷章或页码、采用规则、项目映射和依赖版本。

来源信息进入页面正常阅读流。公共产品中删除浮动“注”和 `MethodologyNote` 交互，不通过悬浮层承载核心证据。

每张事项结果卡使用“为什么是这个状态？”展开当前结论的具体证据。页面另提供“查看本工具的规则与来源”，集中展示五态规则、事项审核状态、传统字段状态、版本、限制和变更记录。

来源链接遵守：

- 国家标准和官方历法资料链接到具体页面；
- 古籍存在可靠影像时链接到具体影像、册卷或可定位页面；
- 没有稳定直达链接时使用书名、版本、卷章和页码，不用无关首页冒充；
- 搜索结果页、营销黄历和商业文章不能作为权威入口；
- 依赖库单列为“实现提供器”；
- 页面运行不实时抓取第三方网站，来源网站暂时不可访问不改变已经生成的版本化结果；
- 外部链接不得携带用户查询事项、日期或其他输入参数。

## 16. 完整性、失败与降级

### 16.1 逐日对账

对于任意成功受理的范围：

```text
成功日期数 + 失败日期数 = 请求自然日总数
```

任何日期都不能被静默跳过。

### 16.2 部分失败

如果部分日期失败：

- 使用 `phase = success`、`successQualifier = partial`；
- 显示已处理数量和失败数量；
- 失败日期保留在原时间位置并标为“数据不可用”；
- 所有统计写明基于多少个成功日期；
- 不得输出整个范围“没有匹配日期”的结论；
- 资料不可用日期不能被选择导出；
- 成功日期可以导出，但图片必须披露请求总数、成功数、失败数和“只包含用户主动选择的完整日期”；
- 提供保留原条件的重新尝试。

### 16.3 全部失败

- 不展示旧结果为本次结果；
- 保留用户输入；
- 说明失败类别；
- 提供重试；
- 不暴露程序堆栈、服务器路径或依赖内部异常。

### 16.4 无匹配

只有全部日期处理成功时，才能说明：

> 在本次所选日期范围和当前采用的资料中，没有发现所选事项出现在宜项的日期。

不得回退展示“分数最高”的日期。

## 17. 当前页结果、数据库与旧历史

### 17.1 第一版零服务器历史

- 游客和登录用户获得相同的公开查询能力；
- 结果只保留在当前页面运行状态，刷新或关闭页面后需要重新查询；
- 查看日期、比较事项、切换月份、展开证据和导出都不写入数据库；
- 页面不显示“保存本次比较”或“查看保存结果”；
- 自动保存当前实现必须退出；
- 登录状态不改变结果、不创建历史，也不读取本人档案。

### 17.2 后续升级边界

服务器历史不属于第一版。只有真实用户反复提出跨设备查看或长期保存需求，才可以重新讨论：

- 保存目的和最小字段；
- 旧规则、旧来源和来源撤回后的快照行为；
- 删除、导出和保留期限；
- 数据库迁移与账号所有权；
- 用户明确同意和主动保存动作。

在新规范经用户批准前，`historyPolicy` 始终为 `disabled`，不得把本合同旧版本中的保存设计视为待实现功能。

### 17.3 旧 `zeji`（择日）记录

旧记录包含评分、排行和旧推荐结构，属于不兼容历史：

- 不显示旧分数、排名和最佳日期；
- 不静默迁移为新五态结果；
- 不静默重新计算；
- 用户可以删除；
- 必要时只展示旧记录元数据和“不再兼容当前规则”的说明。

## 18. 导出契约

### 18.1 导出对象

第一版只为 `activity_compare` 提供导出。用户从成功或部分成功结果中主动选择一至五个资料完整日期；选择动作只表示“我想导出这些日期”，不表示系统推荐。

可选择四种非错误状态的日期，最终按公历升序导出。点击“选择日期生成比较卡片”后才进入选择状态，平时不在每张日期卡堆放复选框。

### 18.2 专用导出卡片

第一版只支持 PNG，并由结构化结果数据生成独立导出组件。禁止：

- 截取整个页面；
- 截取当前滚动状态；
- 为截图强制全部文字 `nowrap`；
- 把未选择日期一起导出；
- 把账号、档案、内部 ID 或 UI 状态写入图片。

### 18.3 导出内容

必须包含：

- “日期事项对照”标题；
- 事项和子类型；
- 原始日期范围；
- `Asia/Shanghai`；
- 选择的日期；
- 每日用户可见白话状态；
- 直接命中的宜项和忌项；
- 简短形成说明；
- 来源、规则和依赖版本；
- 请求总天数、成功数和资料不可用数；
- 固定使用边界与对应事项的现实提醒。

导出前必须预览。导出不创建服务器历史。

### 18.4 禁止导出

以下状态禁止导出：

- 没有结果；
- `phase = processing`；
- `phase = failure`；
- `freshness = stale`；
- 工具被暂停或来源被撤回；
- 没有选择日期、选择超过五个日期或选择了资料不可用日期。

部分成功结果导出时必须写明：

> 本次范围有 N 天资料不可用，本卡只包含用户主动选择的完整日期。

## 19. 工具、能力与公开试运行状态

### 19.1 当前运行事实

XuanXue 已部署到可被互联网访问的服务器，主要供项目所有者使用和向他人展示，目前未主动宣传。

本文将其定义为 `public_preview`。该定义只表示公开可达事实，不表示系统已经满足正式生产、安全、隐私或来源验收。

### 19.2 四维状态

日期对照与全局工具规范一致，使用：

- 审核状态：`unreviewed / in_review / approved / suspended / retired`；
- 访问方式：`public / internal / status_only`；
- 计算策略：`enabled / blocked`；
- 历史策略：`create_allowed / read_only / disabled`。

### 19.3 日期对照的目标治理状态

已批准的目标围栏组合为（非当前代码快照）：

```yaml
reviewStatus: in_review
exposure: internal
computePolicy: enabled
historyPolicy: disabled
```

能力级目标状态同时为：

```yaml
capabilities:
  date_lookup:
    reviewStatus: in_review
    exposure: internal
  activity_compare:
    reviewStatus: in_review
    exposure: internal
```

上述治理状态是契约目标，不是旧代码或线上部署快照。现有目录仍只有 `listed / hidden`；`internal + enabled` 只允许经过授权的内部验证，不允许普通访客调用。现状、目标与尚未批准的状态切换见[产品规范索引](../README.md)。

联合含义：

- 本地开发环境允许内部计算和验收；
- 公开服务器上的普通访客不能生成结果；
- 首页、导航、SEO、PWA、推荐和最近使用不宣传日期对照；
- 旧直达地址进入真实状态页；
- 服务端接口独立阻止公开调用；
- 不创建正式历史；
- 不通过查询参数绕过内部权限。

### 19.4 能力级公开

日期事实完成验收后，可以先把整体工具与 `date_lookup` 调整为公开，同时保持事项比较内部审核：

```yaml
reviewStatus: approved
exposure: public
computePolicy: enabled
historyPolicy: disabled
capabilities:
  date_lookup:
    reviewStatus: approved
    exposure: public
  activity_compare:
    reviewStatus: in_review
    exposure: internal
```

只有至少一个事项通过四层状态和全部验收时，`activity_compare` 才能公开；页面目录只返回已经批准的事项和子类型。每个传统背景字段也维护独立公开状态。

未公开入口、事项、子类型和背景字段完全不出现，不展示“即将上线”、完成比例或虚构发布日期。服务端仍须拒绝直接构造请求。

### 19.5 来源撤回

来源或规则出现问题时调整为：

```yaml
reviewStatus: suspended
exposure: status_only
computePolicy: blocked
historyPolicy: disabled
```

此时停止对应能力的新计算和导出。某个事项或字段出现问题时优先精确暂停该项，不连带撤回无关的日期事实。第一版不产生任何新服务器历史；若旧系统已经存在遗留记录，按数据生命周期规范单独治理，只保留必要的合规元数据和删除入口，已确认错误或可能造成伤害的旧正文不继续展示。

### 19.6 状态页

状态页必须显示：

- 工具名称；
- 当前状态；
- 原因类别；
- 不可用能力；
- 历史影响；
- 用户当前可执行操作；
- 更新时间。

不得承诺虚假完成比例或发布日期。

### 20.1 页面职责

页面只负责组合组件、呈现状态和转发用户事件，不计算历法、不匹配事项、不生成结论。

### 20.2 前端编排

`useZejiTool` 负责：

- 草稿；
- 公共 `ToolResultState` 及本文第 8.3 节的领域映射；
- 筛选；
- 选中日期；
- 导出选择；
- 请求取消和响应过期保护。

它不负责历法、传统规则、公开资格判断或服务器保存。

### 20.3 服务端领域层

调用顺序：

```text
API 输入验证
→ 工具状态门禁
→ 能力、事项和字段状态门禁
→ 历法提供器
→ 来源状态门禁
→ 精确事项匹配器
→ 比较服务
→ 结果信封
```

每个请求范围内的日期必须返回成功或失败记录。

API 只接受规范化能力标识、公历日期、事项标识、子类型标识和日期范围。客户端不能提交传统术语、来源状态、比较状态或结果正文。`date_lookup` 和 `activity_compare` 共用领域模型与来源注册表，但使用各自的输入和结果合同。

### 20.4 零持久化与本地导出

服务端完成计算后直接返回结构化信封，不调用通用 `/api/divinations` 写入结果。浏览器只根据当前结构化结果生成导出预览和 PNG；图片不上传服务器，登录状态不改变这一流程。

## 21. 来源注册表

每条来源至少记录：

```ts
interface SourceRecord {
  sourceId: string
  title: string
  sourceType: 'primary' | 'secondary' | 'project_rule' | 'implementation'
  edition: string
  locator: string
  quotation: string
  url?: string
  licenseNote: string
  sourceStatus:
    | 'verified_primary'
    | 'verified_secondary'
    | 'implementation_only'
    | 'disputed'
    | 'unverified'
    | 'no_source'
  sourceReviewStatus: 'unreviewed' | 'in_review' | 'approved' | 'rejected'
  verifiedFields: string[]
  ruleIds: string[]
  contentIds: string[]
  scientificValidity: 'not_established' | 'not_applicable'
  reviewedAt?: string
  reviewNote: string
}
```

`verified_primary` 或 `verified_secondary` 必须限定到具体字段和规则，并同时记录 `sourceReviewStatus = approved`；不能因为一本书或一个网站存在，就把全部内容标为已验证。

“已核验”只表示本项目确认了声明版本中的原文、映射和程序实现，不表示传统规则已经获得科学有效性验证。复杂解释存在歧义时必须记录为 `disputed`；不能由 AI、搜索摘要或商业网站替代人工证据复核。

## 22. 隐私、安全与日志边界

日期对照不需要本人档案和敏感出生资料，但公开服务器仍应遵守：

- 不在 URL 中放入结果正文或内部标识；
- 不在分析日志记录完整查询、宜忌正文、账号信息或建立事项兴趣画像；
- 不向客户端暴露服务端堆栈、磁盘路径和环境变量；
- 服务端执行工具状态、范围和事项校验；
- 接口设置合理的速率和请求体限制；
- 排错日志只保留请求标识、能力和规则版本、处理状态、耗时及必要错误代码；
- 游客和登录用户使用相同的公开能力，登录不触发额外读取或保存；
- 导出在当前页面本地生成，不上传图片；
- 公开服务器不能借“未宣传”降低安全要求。

本文不单独批准整个服务器的生产资格。账号、会话、数据库和档案安全仍按独立规范与部署审计执行。

## 24. 移动端与可访问性验收

### 24.1 移动端

必须人工验证 320、360、390、414 CSS 像素宽度：

- 页面无整体横向滚动；
- 日期和状态不重叠；
- 日历不强迫用户横向拖动阅读正文；
- 长宜忌术语和来源可以换行；
- 筛选和日期范围控件不溢出；
- 双入口选择和标准日期选择器不溢出；
- 固定操作不遮挡正文；
- 导出预览适配窄屏；
- 不通过禁止浏览器缩放掩盖问题。

还应验证 200% 文字缩放、400% 页面回流和 500% 压力复验下的阅读与操作，不允许出现浮动“注”导致的文本覆盖、横向自由滑动或禁用浏览器缩放。

### 24.2 可访问性

- 日期状态同时使用文字，不只依赖颜色；
- 日历具有正确名称和键盘导航；
- 日期详情展开按钮可聚焦并表达展开状态；
- 加载、部分失败和错误状态可被辅助技术感知；
- 焦点顺序符合页面阅读顺序；
- 列表与日历提供等价信息入口；
- 导出选择说明“一至五个日期”，错误与控件关联。

### 24.3 三方体验验收

UI 实施后必须分别留下：

1. Codex 使用内置浏览器完成双入口、游客、状态、证据、筛选、日历、导出、键盘和各宽度/缩放组合的可复查记录；
2. 用户在真实手机完成日期选择、三十日浏览、证据展开、PNG 清晰度、错位、溢出和误导性文案检查；
3. 部署后的 `public_preview` 环境复验首页、导航、SEO、PWA、旧链接、API 围栏、服务器时区和来源版本。

自动化通过不能替代 Codex 浏览器验收，Codex 浏览器通过不能替代用户真实手机确认；用户未明确接受时不得标记体验完成。

## 25. 最终验收门禁

日期事实、每个事项和每个传统背景字段分别通过五组门槛：

1. 来源与规则：文献定位、原文、解释、映射、争议、版本和科学有效性边界；
2. 自动化：历法样本、精确匹配、输入、接口、能力围栏、完整性、导出和禁止内容断言；
3. Codex 内置浏览器：真实渲染、游客双入口、交互、错误、键盘、320/360/390/414 和 200%/400%/500% 验收；
4. 用户真实手机：理解、日期选择、长列表、证据、PNG、错位、溢出和误导性文案验收；
5. 公开环境：目录、首页、导航、SEO、PWA、旧链接、API、服务器时区和版本一致性复验。

阶段记录不得合并为一个“已完成”，至少分别保存：

```text
产品决策已批准
来源已核验
代码已实施
自动化已通过
Codex 浏览器已通过
用户手机已通过
公开环境已通过
```

七项不能相互替代。`date_lookup`、`activity_compare`、每个事项和每个传统背景字段分别记录这些状态。

最终结论只有：

### Blocked

对应能力任一硬门槛失败，不得向普通访客生成该能力结果；无关且已经通过的能力不被连带撤回。

### Internal Ready

代码、交互和程序测试通过，但来源或三方体验尚未完成，只允许本地或受控内部测试。

### Approved for Public Preview

来源与规则、自动化、Codex 内置浏览器、用户真实手机和公开环境五组门槛全部通过，对应能力才可以进入公开试运行。

当前日期对照整体结论为：

> Blocked — 可以作为整改中的内部功能继续开发，但尚不具备向普通公开访客生成新结果的条件。

## 26. 推荐迭代顺序

本文批准后不得一次性重写全部日期对照功能。推荐拆分为：

1. 公开入口与服务端状态围栏；
2. 日期事实来源注册表、提供器精确版本和固定历法样本；
3. `date_lookup` 服务端能力、单日浏览页面和独立验收；
4. 八类事项来源与风险审计，确定首批两至三类；
5. 白话子类型、精确映射器和事项能力围栏；
6. 日期范围 API、五态结果、完整性与失败契约；
7. 完整性摘要、日期列表、中性筛选、辅助日历和日期证据；
8. 一至五日专用本地 PNG 导出；
9. 传统背景字段逐项核验和独立接入；
10. 自动化、Codex 内置浏览器和用户真实手机验收；
11. 部署后公开环境复验，再按能力调整公开状态。

每个迭代独立制定实施计划、执行测试、审查结果和验收，不以总测试数量替代本迭代证据。

## 27. 第一版之外

第一版不包含：

- 安葬择日；
- 求医择日；
- 自由文本事项；
- 用户个体八字与日期合成；
- 地点和时刻择吉；
- 时辰推荐；
- 自动推荐一个“最佳日”；
- 服务器历史、跨设备保存和自动保存；
- 多流派切换；
- AI 解读；
- PDF、CSV 或批量导出；
- 亲友资料；
- Spring Boot 独立后端或微服务。

未来功能必须单独讨论，不因本合同存在而自动进入范围。
