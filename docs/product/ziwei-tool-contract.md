> 状态：Approved — 产品决策已批准；代码实施、传统来源核验、公开验收均未开始
>
> 版本：1.0.0
>
> 最后更新：2026-09-06
>
> 适用范围：XuanXue 现有紫微斗数功能的退役整改，以及“紫微斗数·基础命盘”候选的输入、规则、内容、数据、历史、导出、移动端和重新开放验收

## 1. 文档目的

本文固定紫微斗数第一候选版本已经讨论并批准的产品和领域边界，防止后续实施继续沿用当前页面中的模板预测、错误来源声明、自动保存、真太阳时简化处理、大限流年和第三方原生对象直存。

本文是目标契约，不是对现有代码、测试、页面文案或公开能力的背书，也不表示传统来源、算法正确性、隐私安全或移动端体验已经通过验收。

传统资料能够证明某种概念或方法在特定文本、版本或流派中存在，不能证明其具有现实预测能力。第三方库能够证明程序怎样计算，也不能自动成为传统规则的权威来源。

## 2. 核心裁决摘要

1. 第一候选命名为“紫微斗数·基础命盘”，定位为透明、可复算的传统文化规则学习工具，不是完整算命或人生预测产品。
2. 第一候选只形成基础本命盘，不开放大限、流年、流月、现实事件预测或自动综合解读。
3. 排盘引擎精确锁定 `iztro 2.5.8`，项目规则版本为 `ziwei-rule-v1`；不得使用 `^2.5.8` 等范围版本作为公开计算基线。
4. 第一候选固定使用 `algorithm = default`、`yearDivide = normal`、`horoscopeDivide = normal`、`ageDivide = normal`、`dayDivide = forward`、`fixLeap = true`，并采用该版本默认四化表和亮度表。
5. 第一候选不向用户开放流派或规则切换，也不宣称固定配置是所有流派唯一正确的规则。
6. 用户默认填写公历日期，也可主动切换农历；农历输入必须明确普通月或闰月。
7. 时间必须能够唯一落入一个时辰索引；未知时间或跨越多个时辰的范围不生成个性化命盘。
8. 早子时和晚子时分开表达；晚子时采用次日计算规则，同时保留用户原始日期和实际排盘日。
9. 第一候选只接受中国标准时间 `Asia/Shanghai`、`UTC+8` 口径下的输入，不收集出生地点、不计算真太阳时、不支持境外或其他时区出生资料。
10. 第一候选不询问、不保存、不导出传统性别参数；锁定版本源码审计和代表性比对表明，当前允许的基础命盘字段不随该参数变化，实施时仍须以双投影不变量测试持续证明。
11. 游客可以临时生成；页面不自动读取本人档案，不自动计算，不自动更新档案，不自动保存结果。
12. 登录用户只有在主动点击、阅读保存内容并确认后，才能保存不可变的项目结果快照。
13. 服务端保存时必须重新校验并使用同一锁定规则重算，不能信任客户端上传的第三方库原生对象。
14. 默认结果按“结果说明—阅读指引—十二宫传统方盘—宫位资料—完整技术数据”组织。
15. 主盘只展示结构事实和经过核验的术语说明，不生成性格、婚恋、事业、财富、健康或未来断言。
16. 现有“天星图”改名为“星曜分布图”，作为默认折叠的项目拓展可视化，并持续标注“项目可视化·非传统命盘格式”。
17. 导出只允许浏览器本地 PNG；默认生成脱敏分享版，用户主动选择后才生成完整自用版。
18. 第一候选只有 `successQualifier = unique` 才算成功；不支持部分盘、候选盘或空结果。
19. 紫微来源复用全项目 `sourceStatus + sourceReviewStatus` 双状态模型，不建立第二套简化状态。
20. 当前紫微功能继续保持内部封存；只有来源、实现、隐私、自动化、Codex 浏览器和用户真机门禁全部通过后，才成为有限公开预览候选。

## 3. 当前代码审计结论

### 3.1 当前实现位置

现有实现主要分布在：

- `pages/tools/ziwei.vue`：页面状态、输入、计算、自动保存、历史恢复、方法说明、SEO 和导出；
- `components/tools/ziwei/`：输入表单、十二宫方盘、天星图、大限时间线、宫位详情和信息侧栏；
- `composables/useZiwei.ts`：直接调用 `iztro`、生成模板解释、序列化和反序列化第三方对象；
- `constants/ziwei.ts`：星曜和宫位模板解释、组合断语、时辰映射、星图角度和配色；
- `tests/composables/useZiwei*.test.ts`：现有引擎与序列化测试；
- `server/api/divinations/`、`server/database/schema.ts`：通用历史保存和 `ziwei` 类型；
- `constants/tool-catalog.ts` 与相关中间件：当前公开围栏。

### 3.2 已确认的关键问题

1. `package.json` 使用 `^2.5.8`，页面方法说明仍声称 `iztro v2.4.8`，依赖与公开说明不一致。
2. 当前页面把《紫微斗数全书》直接标为“宋代陈希夷撰”，并把现代库实现笼统归因于该书，作者、成书和版本问题没有核验。
3. 当前计算直接返回 `IFunctionalAstrolabe`，页面、组件、历史和测试与第三方对象结构耦合。
4. 当前代码使用经度乘四分钟的简化“真太阳时”修正，但没有完整历史民用时间、均时差和适用范围治理。
5. 当前常量包含领导力、财运、桃花、婚姻、权势、吉凶和命运等级等模板断言。
6. 当前页面包含大限和年龄时间线，超出第一候选批准边界。
7. 现有结果生成后自动调用保存接口，与“默认不保存、主动确认后保存”冲突。
8. 现有历史序列化保留 `decadalRange`、`ages` 等第一候选禁止字段，也没有项目自有版本化结果 DTO。
9. 现有整页截图式导出可能携带敏感输入、隐藏区块和不再允许公开的内容。
10. 现有测试大量证明对象存在、数组合法和往返序列化，不能证明传统来源、规则选择和面向用户内容真实。
11. “天星图”是项目自定义地支角度映射，却容易被理解为传统图式或天文坐标。
12. 当前工具虽已由统一目录封存，但围栏存在不等于上述规则和内容已经整改。

### 3.3 传统性别参数复核

`iztro 2.5.8` 的公开排盘 API 要求传入男或女。锁定版本源码审计和代表性相同日期、相同时辰逐字段比对表明：

- 十二宫、命宫、身宫、五行局相同；
- 主星、辅星、杂曜、亮度和四化相同；
- 差异只出现在长生十二神、博士十二神、大限和年龄等第一候选不采用的字段。

现有测试中名为“男女命宫不同”的用例并未断言差异，只断言两个结果存在，不能作为字段必要性的证据。

因此第一候选取消传统性别参数：

- 页面不询问该字段；
- 本人档案即使保存了相关字段，本工具也不读取；
- 项目 DTO、历史和导出不保存该字段；
- 长生十二神、博士十二神、大限和年龄不进入第一候选；
- 未来开放任何确实依赖该参数的内容时，重新讨论必要性、用途、表达和保存边界。

适配器必须对第三方 API 的必填参数进行工程隔离。第一候选分别以两个库参数生成结果并投影到批准白名单；两个投影完全一致才返回唯一结果，否则以引擎不变量错误停止，不要求用户为第三方 API 的遗留签名补充无效信息。

## 4. 产品定位、用户价值与命名

### 4.1 正式名称

用户可见名称：

> 紫微斗数·基础命盘

页面副标题应说明：

> 按固定版本排出十二宫与星曜结构，帮助初次接触者了解传统术语如何形成。

不使用“紫微算命”“命运推演”“大限流年运势”“人生全解”等名称。

### 4.2 用户可以得到什么

- 看见输入怎样被规范化；
- 看见固定规则生成的十二宫和星曜分布；
- 学会阅读宫位、星曜、四化、亮度和五行局等术语；
- 区分结构结果、传统资料、项目可视化和仍待核验内容；
- 查看规则版本、引擎版本、来源状态和不能推出的现实结论；
- 在主动保存后保留生成时的不可变快照。

### 4.3 明确不回答什么

- 用户真实性格、能力、层次或人生价值；
- 是否结婚、何时结婚、伴侣情况或感情吉凶；
- 学业、就业、职业、财富、投资或健康结果；
- 某年、某月或某阶段将发生什么；
- 哪颗星“保证带来”好运或灾祸；
- 哪个流派或配置“最准”；
- 命盘与科学意义上的因果或预测能力。

```text

    ↓

    ↓
```

## 8. 输入契约

### 8.1 字段清单

| 字段     | 是否必填   | 输入形式                     | 用途                   |
| -------- | ---------- | ---------------------------- | ---------------------- |
| 历法类型 | 是         | 公历／农历，默认公历         | 解释日期输入口径       |
| 出生日期 | 是         | 标准日期组件                 | 转换并形成排盘日期     |
| 闰月状态 | 农历时必填 | 普通月／闰月                 | 处理农历闰月           |
| 时间精度 | 是         | 精确时间／已知时辰／大致范围 | 判断是否能唯一落入时辰 |
| 出生时间 | 按精度必填 | 时间组件、时辰组件或范围组件 | 形成 `timeIndex`       |

不收集：

- 姓名或“真实姓名”；
- 出生地点、经纬度或 GPS；
- 婚恋、学习、工作、健康、财务或家庭信息；
- 性别或传统性别参数；
- 当前年龄、当前问题或个人故事；
- 流派偏好和自定义引擎参数。

### 8.2 日期输入

- 默认公历，不同时显示两套日期输入框；
- 用户切换到农历时，日期组件提供农历年月日和明确闰月选择；
- 农历转换失败不得把原数字继续当作公历；
- 未来日期无效；
- 支持日期范围必须由转换引擎能力和独立黄金样例共同确认，不能从旧表单的 HTML 范围反推；
- 页面同时保留原始历法表达和规范化后的公历、农历结果。

### 8.3 时间精度

允许三种方式：

1. **精确时间**：用户选择小时和分钟；
2. **已知时辰**：用户直接选择早子、丑、寅至亥、晚子中的一个；
3. **大致范围**：用户选择开始和结束时间，且整个范围必须落在同一个时辰索引内。

未知时间、只有“上午／下午／晚上”等跨时辰描述，或者范围跨过任一时辰边界时，第一候选不生成个性化命盘。系统说明需要补充什么，不猜测、不默认子时、不产生候选盘。

### 8.4 时辰边界

统一采用左闭右开区间：

| `timeIndex` | 名称   | 钟表时间         |
| ----------- | ------ | ---------------- |
| 0           | 早子时 | `[00:00, 01:00)` |
| 1           | 丑时   | `[01:00, 03:00)` |
| 2           | 寅时   | `[03:00, 05:00)` |
| 3           | 卯时   | `[05:00, 07:00)` |
| 4           | 辰时   | `[07:00, 09:00)` |
| 5           | 巳时   | `[09:00, 11:00)` |
| 6           | 午时   | `[11:00, 13:00)` |
| 7           | 未时   | `[13:00, 15:00)` |
| 8           | 申时   | `[15:00, 17:00)` |
| 9           | 酉时   | `[17:00, 19:00)` |
| 10          | 戌时   | `[19:00, 21:00)` |
| 11          | 亥时   | `[21:00, 23:00)` |
| 12          | 晚子时 | `[23:00, 24:00)` |

`24:00` 不作为独立输入值，必须表示为次日 `00:00`。

### 8.5 时间口径与地域边界

第一候选把用户输入解释为中国标准时间 `Asia/Shanghai`、`UTC+8` 下的民用钟表时间：

- 不请求出生地点；
- 不根据城市换算经度；
- 不计算真太阳时；
- 不处理境外时区或其他民用时间制度；
- 不把设备当前时区带入出生时间；
- 在输入附近和结果摘要中持续显示该口径。

若用户的出生记录不属于上述时间口径，本版本明确提示不支持，而不是让用户自行猜一个换算结果。

## 9. 固定排盘规则

### 9.1 引擎和配置

```text
engine              = iztro
engineVersion       = 2.5.8
ruleVersion         = ziwei-rule-v1
language            = zh-CN
algorithm           = default
yearDivide          = normal
horoscopeDivide     = normal
ageDivide           = normal
dayDivide           = forward
fixLeap             = true
mutagens            = iztro 2.5.8 default
brightness          = iztro 2.5.8 default
astroType           = heaven/default
engineProjection    = dual-gender-invariant
```

即使大限和小限不进入第一候选结果，仍显式冻结 `horoscopeDivide` 和 `ageDivide`，避免第三方全局配置或未来调用产生不可追踪差异。

项目适配器必须确保每次客户端计算和服务端重算使用同一完整配置，不能依赖其他页面修改后的库级全局状态。

`engineProjection = dual-gender-invariant` 是第三方 API 兼容策略，不是用户字段。适配器分别传入该 API 要求的两个性别参数，随后只投影本文白名单字段；两个投影完全一致才返回结果。任一白名单字段出现差异时，必须以 `engine_error / GENDER_INVARIANT_VIOLATION` 停止，不能静默选择其中一份。

### 9.2 年界和库语义

在 `iztro 2.5.8` 中，`yearDivide = normal` 表示以农历正月初一为年分界；`algorithm = default` 表示该库称为“通行版本”的安星方法。

页面应把它们表达为“本项目固定采用的引擎配置”，不能进一步写成所有传统资料的一致结论。只有完成对应传统来源核验后，才可补充历史依据和流派比较。

### 9.3 晚子时跨日

`dayDivide = forward` 的固定行为是：

- 23:00 至 23:59 判定为晚子时；
- 用户原始民用日期保持不变；
- 排盘日按次日处理；
- 结果同时展示原始输入日、晚子时判定和实际排盘日；
- 不允许在后台静默改变用户看见的原始输入。

示例：

```text
原始输入：2000-01-01 23:30
时辰判定：晚子时
实际排盘日：2000-01-02
规则说明：本版本采用晚子时按次日排盘
```

### 9.4 闰月处理

`fixLeap = true` 的固定行为是：

- 闰月初一至十五按本月处理；
- 闰月十六日起按次月处理；
- 页面为闰月输入显示本次实际采用的月份处理结果；
- 当前证据只足以标记为 `implementation_only`，不能声称是所有流派公认规则。

推荐用户可见说明：

> 本版本采用固定闰月处理规则：闰月初一至十五按本月排盘，十六日起按次月排盘。该规则用于保证结果稳定复算，不代表所有流派的统一处理方式。

闰月十五日晚子时属于日期和闰月边界组合样例，必须以锁定引擎实际行为建立黄金测试，并在升级引擎时专项比较。

### 9.5 不开放规则选择

第一候选不提供：

- 通行／中州切换；
- 正月初一／立春年界切换；
- 晚子时当日／次日切换；
- 闰月修正开关；
- 自定义四化表或亮度表；
- 天盘／地盘／人盘切换。

未来增加任何一种选择都必须形成新规则版本、来源记录、输入说明、结果比较和迁移策略。

## 10. 输入规范化与结果资格

### 10.1 规范化输出

```text
timeName
isLateRatHour
```

### 10.2 成功限定

第一候选只允许：

```text

successQualifier = unique

```

- 日期不完整；
- 时间未知；
- 时间范围跨多个时辰；
- 时间口径不在支持范围；
- 规则配置或引擎版本不匹配。

它们分别进入缺少必填输入、无效输入、超出支持范围或引擎错误。

## 14. 宫位与专业术语解释

### 14.1 六问模板

每个普通用户可能不理解的术语第一次出现时，必须回答：

1. 它是什么；
2. 本次怎样得到；
3. 在当前结构中起什么作用；
4. 用户本次得到的具体结果；
5. 它不能说明什么；
6. 使用哪一版规则和来源。

### 14.2 宫位名称边界

宫位名称是传统分类标签，不是现实事实。例如：

- 出现“夫妻宫”不证明用户已经恋爱或结婚；
- 出现“官禄宫”不证明用户已经工作；
- 出现“财帛宫”不代表财富多少；
- 出现“疾厄宫”不构成健康判断；
- 出现“子女宫”不证明用户有子女。

页面首先解释名称在命盘结构中的位置和传统语境，不据此生成现实断言。

### 14.3 星曜

星曜默认只说明：名称、类别、所在宫位、亮度字段、四化字段和来源状态。第一候选不把星曜自动翻译为性格、职业、财富、疾病、婚姻或事件。

主星、辅星和杂曜的具体传统释义必须逐项进入内容账本。没有通过来源门禁的释义不显示；星曜结构仍可在技术层按 `implementation_only` 展示，但必须说明只证明引擎输出。

### 14.4 五行局

五行局是固定规则产生的传统分类名称，不是分数、人格标签或“五行强弱”。页面说明查得结果和生成位置，不延伸幸运颜色、职业、健康或补救建议。

### 14.5 四化

禄、权、科、忌是固定表映射产生的传统术语：

- 不按“前三个吉、最后一个凶”展示；
- 不使用红绿优劣排序；
- 不推导现实好运或灾祸；
- 显示采用的四化表版本和对应天干规则；
- 来源未核验时只能作为引擎结构字段展示。

### 14.6 亮度

亮度是该排盘体系中的星曜状态分类：

- 不是天文学观测亮度；
- 不是好坏分数；
- 不自动推导“作用更强”或现实影响；
- 显示采用的亮度表版本；
- 表源未核验时标记为引擎实现字段。

### 14.7 命主、身主和组合关系

命主、身主仅进入完整技术数据，不作为新手首页重点，也不生成“你的本质”或“你的身体”解释。

当前代码中的星曜组合断语全部退出第一候选。对宫、三方或组合关系只有在规则稳定、来源到位、能够以结构语言解释且不产生现实预测时，才可逐条进入高级资料。

## 16. 内容性质和真实性边界

页面内容分为：

| 类别           | 允许内容                                       | 禁止扩展               |
| -------------- | ---------------------------------------------- | ---------------------- |
| 输入与计算事实 | 用户原始输入、规范化日期、时辰、配置和引擎输出 | 现实因果和准确率承诺   |
| 传统分类       | 宫位、星曜、五行局、四化等已核验定义           | 自动人格和事件判断     |

| 工程元数据     | DTO、引擎、规则和内容版本                      | 面向用户伪装成玄学含义 |

即使某段传统资料来源真实，也不代表可以直接向具体用户作个性化预测。来源门和产品风险门必须同时通过。

## 17. 来源与内容审核

### 17.1 双状态模型

紫微来源必须复用全项目状态：

```text
sourceStatus:
  verified_primary
  verified_secondary
  disputed
  implementation_only
  unverified
  no_source

sourceReviewStatus:
  unreviewed
  in_review
  approved
  rejected
```

公开规则：

- `verified_primary/verified_secondary + approved`：可用于相应传统术语说明；
- `implementation_only + approved`：只能称为项目规则、引擎行为或项目可视化；
- `disputed + approved`：只能说明争议及项目选择，不能伪装成确定共识；
- `unverified`、`no_source`：不得进入用户解释；
- `sourceReviewStatus = rejected`：不得发布。

### 17.2 来源层级

必须分别记录：

1. 原始文献；
2. 现代学术或权威整理；
3. 项目采用规则；
4. 工程实现与第三方库。

不得使用“古籍记载”“民间说法”“综合网络资料”“同上”作为正式来源。

### 17.3 当前来源裁决

当前页面的以下声明不能继续公开：

> 《紫微斗数全书》（宋代陈希夷撰）

在作者、成书、版本、卷页和具体规则没有完成核验前：

- 不能把该书归为已核验一手来源；
- 不能声称 `iztro` 算法“基于该书”而不提供逐规则证据；
- 宫位、星曜、四化和组合解释分别进入待核验账本；
- `iztro 2.5.8` 只作为工程实现来源。

### 17.4 原子内容账本

每条可见定义或规则至少记录：

- `contentId`、`ruleId`、内容类别和用户可见位置；
- 原始输入、计算步骤和输出字段；
- 来源 ID、版本、作者或责任机构、出版信息和具体位置；
- 原文、项目转述和二者关系；
- 争议、其他规则分支和项目采用理由；
- `sourceStatus`、`sourceReviewStatus` 和权利状态；
- 内容版本、审核人、审核日期和测试引用。

自动化可以检查字段和状态，但不能替代人工核对原文、版本和普通用户能否理解。

## 18. 页面状态、失败与过期结果

### 18.1 公共状态

紫微使用全局 `ToolResultState`：

```text
phase:
  idle | editing | ready | processing | success | failure

successQualifier:
  unique

freshness:
  current | stale

failureCategory:
  invalid_input
  missing_required_input
  unsupported_input
  engine_error
  network_error
```

可以增加领域 `failureDetailCode`，但不得另建一套总状态。

### 18.2 领域失败

至少区分：

- 日期格式或闰月状态无效；
- 日期超出已核验范围；
- 时间缺失；
- 时间范围跨多个时辰；
- 非 `UTC+8` 时间口径；
- 引擎版本或固定配置不匹配；
- 引擎抛错；
- 输出不是十二个唯一地支宫位；
- 命宫、身宫或五行局结构异常；
- 星曜类型、亮度或四化值不在批准枚举；
- 来源或内容记录缺失。

引擎异常必须说明是系统未能生成，不能用“你的资料有误”把责任推给用户。

### 18.3 过期结果

用户修改任何参与计算的输入后：

- 保留旧结果；
- 标记 `freshness = stale`；
- 显示旧结果使用的输入摘要；
- 禁止保存和导出；
- 提供“恢复旧输入”和“按新输入重新生成”；
- 不自动重算，也不立即清空旧结果。

保存、历史加载和导出分别维护自己的处理与失败状态，不能与排盘 `phase` 混为一个布尔值。

### 19.1 游客

## 20. 保存、历史与旧数据

### 20.1 主动保存

目标历史策略在重新开放并完成历史验收后为 `create_allowed`。保存前必须说明：

- 将发送并保存哪些本次输入；
- 将保存哪一版结果快照；
- 包含出生日期和时间等个人资料；
- 不会更新本人档案；
- 用户可以在哪里查看和删除；
- 旧版本不会被静默重算。

用户主动点击“确认保存”后：

1. 客户端发送规范化前后的必要输入和结果身份，不发送可被信任的第三方完整结果；
2. 服务端重新校验字段、精度、日期和固定规则；
3. 服务端使用同一项目计算核心和 `iztro 2.5.8` 重算；
4. 客户端与服务端项目 DTO 一致才保存；
5. 保存项目拥有的不可变结果信封。

保存失败不影响当前结果阅读，页面明确显示“未保存”。同一 `resultId` 重试不得创建重复历史。

### 20.2 快照字段

快照至少包含：

- 记录 ID、结果 ID、工具 ID；
- `ziwei-chart-v1`；
- 生成时间和保存时间；
- 本次实际使用的原始与规范化输入；
- 时间精度、时区、晚子时和实际排盘日；
- `ziwei-rule-v1`、`iztro 2.5.8` 和来源集合版本；
- 本文允许的完整 `ZiweiChartV1`；
- 当时的内容、来源和限制说明；
- 内容撤回或兼容状态。

不保存整个本人档案，不保存 DTO 白名单外的第三方对象字段。

### 20.3 历史列表和打开

默认历史标题：

> 紫微基础命盘 · 2026-09-06 20:15

列表不显示完整出生日期或时间。打开历史只读取原快照，不重新调用引擎。

用户可以：

- 查看生成时输入和版本；
- 删除单条紫微历史；
- 删除全部紫微历史；
- 把历史输入复制为新草稿；
- 主动按当前规则生成一个新结果。

新结果拥有新 `resultId`，不会覆盖旧快照。

### 20.4 旧快照

- 现有自动保存的紫微记录不迁移为可信 `ziwei-chart-v1`；
- 新数据模型实施时按已批准旧数据库重建策略处理；
- 不为旧记录补造来源、规则或版本；
- 若实施阶段保留过渡只读能力，必须明确标为“旧版未核验记录”，只允许删除或导出原始数据，不得恢复为新页面的可信结果；
- 具体数据库重建仍属于破坏性操作，必须再次获得用户对准确路径的明确授权。

### 21.1 通用规则

- 导出不创建服务器历史；
- 导出前提供准确预览；
- `stale`、`processing`、`failure` 或旧版不兼容结果不可导出新格式；
- 失败保留当前结果，不改变保存状态；
- 不提供公开链接、二维码、社交平台直传、PDF、Word、JSON 或批量导出。

### 21.2 默认脱敏分享版

默认 PNG 包含：

- 工具名称；
- 十二宫基础方盘；
- 用户当前主动选择的少量宫位结构；
- 内容性质、非预测边界；
- 规则版本和引擎版本；
- 可选的“星曜分布图”及其非传统格式标记。

默认不包含：

- 完整出生日期和分钟；
- 账号、昵称或历史 ID；
- 完整技术对象和长来源网址。

### 21.3 完整自用版

用户主动选择“完整自用版”后，先预览并提示可能包含出生资料。可以包含本次完整输入、规范化日期、时间口径和完整方盘，但仍不包含本文禁止的预测内容。

### 21.4 文件名

文件名不使用姓名或完整出生资料，例如：

```text
玄道-紫微基础命盘-20260906.png
```

## 22. 模块化单体架构

项目继续采用 Nuxt 3 全栈模块化单体，不新建 Spring Boot 后端、不拆微服务、不接入 AI。

### 22.1 五层边界

1. **输入与规则规范化层**：处理历法、时间精度、时辰、晚子时、闰月和固定配置；
2. **iztro 适配层**：唯一接触第三方 API，把原生对象转换为 `ZiweiChartV1`；
3. **内容与证据层**：管理术语、来源、审核、权利和限制；
4. **页面与状态编排层**：管理草稿、结果状态、方盘、详情、过期、导出和保存动作；
5. **持久化与历史层**：服务端重算、不可变快照、幂等保存、读取和删除。

### 22.2 依赖方向

```text
页面组件
  ↓
页面状态与用例
  ↓
输入规范化 + 项目领域接口
  ↓
iztro 2.5.8 适配器

内容组件 → 内容与证据目录
导出模块 → ZiweiChartV1 + 已审核内容快照
历史模块 → 版本化结果信封
```

页面不直接导入 `iztro` 类型；内容目录不调用排盘引擎；导出不复制计算逻辑；历史读取不触发重算。

### 22.3 客户端与服务端共用核心

- 游客和未保存结果在浏览器本地计算；
- 主动保存时由服务端调用同一无状态项目计算核心；
- 核心接收显式输入和完整规则配置，不自行读取档案、当前时间或环境全局值；
- 客户端和服务端输出同一稳定 DTO；
- 依赖升级必须专项审查变更日志、黄金样例和前后差异。

## 23. UI、移动端与可访问性

### 23.1 视觉边界

保留“墨韵·Ink Resonance”的颜色、字体、留白、卡片质感和现有品牌，不进行整体视觉重设计。允许为了理解顺序、移动端重排和内容真实性调整组件职责。

取消浮动“注”按钮和覆盖式方法说明。来源、规则和边界进入正常阅读流中的简短说明及可展开详情。

### 23.2 桌面端

- 十二宫方盘和当前宫位详情在同一屏宽区域协作；
- 详情不覆盖方盘；
- 技术数据和来源按用户主动展开；
- 星曜分布图保持次级折叠位置。

### 23.3 移动端

- 方盘保持容器内完整，不产生页面级横向滚动；
- 宫位详情在方盘下方进入正常文档流；
- 不使用底部抽屉、悬浮大面板或依赖自由缩放的交互；
- 单元格只保留核心字段，长内容在详情区自然换行；
- 320、360、390、414 CSS 像素均可完成输入、生成、选宫、展开、导出和保存；
- 不禁用浏览器缩放，不使用全局 `overflow: hidden` 掩盖溢出。

### 23.4 可访问性

- 日期、时间精度和时辰均有可读标签和错误关联；
- 宫位方盘具有等价线性文本；
- 选中、四化、亮度和状态不只依赖颜色；
- 所有核心操作支持键盘；
- 处理、成功、失败、保存和导出状态通过状态区域宣布；
- 动画不是理解结果的必要条件，并尊重减少动态效果设置；
- 200% 文字缩放和更高缩放下内容可以重排而不遮挡。

## 24. 自动化测试契约

### 24.1 输入与边界

至少覆盖：

- 公历与农历合法输入；
- 普通月与闰月；
- 闰月十五、十六及十五日晚子时组合；
- 每个时辰的起点、终点前一分钟和跨界范围；
- 早子时、晚子时和公历跨年晚子时；
- 闰年、月末和支持范围边界；
- 未知时间和跨时辰范围；
- 非 `UTC+8` 口径的显式拒绝；
- 输入错误不清空其他字段。

### 24.2 配置冻结

- 依赖解析为精确 `iztro 2.5.8`；
- 每次计算使用完整固定配置；
- 其他测试或页面改变库全局配置后，紫微结果仍不漂移；
- 客户端与服务端对同一输入生成相同 `ZiweiChartV1`；
- 配置或版本不匹配时显式失败。

### 24.3 结构不变量

每个成功结果必须满足：

- 恰好十二个宫位；
- 十二地支唯一且完整；
- 恰好一个命宫和一个身宫位置；
- 宫位名称、天干、地支和星曜类型位于批准枚举；
- 五行局位于批准枚举；
- 四化值只允许禄、权、科、忌或空；
- 亮度值位于批准枚举或明确为空；
- DTO 不包含函数、循环引用、未知字段、大限、年龄和预测内容；
- 星曜分布图和传统方盘引用同一宫位、星曜和选择状态。

### 24.4 黄金样例

黄金样例不能只从当前实现反向生成期望值。至少包括：

- 独立手工推导或经过来源核验的代表性普通日期；
- 公历／农历同一时刻等价样例；
- 早子／晚子跨日样例；
- 闰月前半／后半样例；
- 同一输入分别使用第三方 API 两个性别参数后，批准白名单投影完全一致；
- 长生十二神、博士十二神、大限和年龄确实被白名单剔除；
- 引擎官方文档或源码行为与项目适配器的对照样例；
- 依赖升级前后的冻结回归样例。

来源尚未核验时，工程样例只能证明实现稳定，不能命名为传统正确性样例。

### 24.5 内容和禁止项

自动扫描和合同测试至少检查：

- 分数、准确率和“最强／最弱”排名；
- 性格、婚姻、事业、财富、健康和未来事件断言；
- “一定、注定、必然、保证、改运”等承诺；
- 大限、流年、流月、当前年龄和 `decadalRange`；
- 星座、生肖等第三方附带字段；
- 旧“宋代陈希夷撰”确定性归属；
- 旧“天星图”未带项目可视化边界的名称；
- 未审核内容进入页面或导出；
- `implementation_only` 被写成传统已验证；
- 第三方原生对象被直接保存。

### 24.6 状态、保存和导出

- 修改输入后旧结果进入 `stale`；
- stale 结果不能保存或导出；
- 恢复旧输入和主动重算行为正确；
- 生成成功不调用保存接口；
- 游客生成不产生服务器请求和长期存储；
- 主动保存时服务端重算，DTO 不一致时拒绝；
- 同一 `resultId` 重试幂等；
- 历史打开不重算；
- 删除单条和全部紫微历史准确生效；
- 本地 PNG 不上传，不隐式创建历史；
- 导出预览与实际图片内容一致。

## 25. 三层验收

### 25.1 Claude 自动化执行

实施执行方必须完成：

- 类型检查、领域单元测试、产品合同测试、lint 和生产构建；
- 输入边界、配置冻结、DTO 白名单和客户端／服务端一致性测试；
- 禁止内容、网络、存储、保存幂等和导出测试；
- 中文乱码检测和 `git diff --check`；
- 结果文件如实记录计划偏差。

### 25.2 Codex 独立审查

Codex 必须：

- 审查计划、结果、实际 diff 和每项偏差；
- 复跑关键测试并核对依赖精确版本；
- 使用内置浏览器检查桌面与 320、360、390、414 CSS 像素；
- 检查 100%、200% 文字缩放以及更高缩放时的重排；
- 检查网络、浏览器存储、历史、导出和敏感数据；
- 比对传统方盘与星曜分布图是否使用同一数据；
- 证明旧预测内容、大限时间线和错误来源声明不再泄漏。

执行方自报成功不能替代 Codex 审查。

### 25.3 用户手动验收

用户使用真实手机至少确认：

- 日期、时间精度、时辰和传统参数输入易懂；
- 晚子时、闰月和时间口径提示能被理解；
- 方盘不需要自由缩放或左右拖动页面；
- 点击宫位后详情位置自然、无重叠和遮挡；
- 普通用户能够理解结果是什么、如何形成和不能说明什么；
- 星曜分布图不会被误认为传统图式或天文图；
- 脱敏导出和完整自用导出符合预期；
- 保存前告知、历史读取和删除行为清楚。

任一层未通过，都不能宣称紫微第一候选已经完成。
