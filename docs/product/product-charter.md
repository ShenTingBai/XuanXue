## 1. 总纲的职责

本文是 XuanXue 产品方向和第一版边界的最高产品规范。它回答产品是什么、为谁服务、怎样判断成功、哪些能力可以进入第一版，以及项目采用怎样的工程与发布边界。

本文只表示产品决策已经批准，不表示：

- 当前代码已经按总纲完成；

产品决策、代码实施、来源核验和公开状态继续作为四个独立维度记录。

## 2. 产品定位

XuanXue 是一个面向普通用户的、透明且可验证的传统文化互动探索产品。它使用八字、生肖、太阳星座、日期对照等规则体系作为文化理解和自我观察的材料，帮助用户从轻量体验逐步理解规则、结果与局限；不把传统解释包装成确定的人生预测。

产品核心承诺是：

> 看得懂、说得清、查得到、不骗人。

- **看得懂**：先用普通语言解释，再允许用户按需展开专业术语；
- **说得清**：说明实际使用的输入、规则、时间上下文和缺失条件；
- **查得到**：结果可以追溯到规则版本、内容来源及其核验状态；
- **不骗人**：不虚构个人经历，不把随机内容包装成个性化结论，不用分数制造准确感，不承诺现实事件必然发生。

XuanXue 不是确定性算命服务、专业命理师工作台，也不是只追求工具数量的娱乐集合。更准确的定义是：

> 以传统文化规则为材料，以互动计算为入口，以解释、验证和自我观察为核心的数字文化产品。

适度趣味内容可以存在，但必须如实标识其生成方式和内容性质。娱乐标签不能替代来源、输入、规则和风险边界。

## 3. 目标用户与使用场景

### 3.1 核心用户

第一版主要服务对传统文化感兴趣、缺少专业知识、希望获得易懂且有边界体验的普通用户。产品不要求用户先相信某种世界观。

用户优先级如下：

1. 核心用户：不懂专业术语的普通探索者；
2. 次要用户：知道具体工具名称、希望快速完成一次明确探索的人；
3. 展示对象：关注模块化、规则追溯、数据治理和工程质量的老师、面试官与开发同行；
4. 暂不服务：职业命理师、代客批量排盘者、商业咨询使用者，以及希望把结果用于医疗、投资、法律等高风险决策的人。

### 3.2 三类使用场景

| 场景     | 用户状态                       | 产品应对                                                   |
| -------- | ------------------------------ | ---------------------------------------------------------- |
| 目标明确 | 想使用某个具体工具             | 直接进入对应工具，先说明所需资料、用途和结果边界           |
| 兴趣探索 | 没有明确目标，只想看看         | 提供无需敏感资料的公共文化内容和工具介绍，不强迫注册或建档 |
| 深入理解 | 已获得结果，希望理解术语与依据 | 提供渐进解释、输入凭证、规则版本、来源状态和限制说明       |

两条主路径为：

```text
明确目标 → 进入工具 → 补充必要资料 → 查看并理解结果
兴趣探索 → 浏览文化内容 → 了解工具边界 → 自主决定是否深入
```

两条路径最终都进入“结果—解释—依据—局限”的统一结构，但不会强迫游客注册、建档或保存资料。

## 4. 产品价值与第一版成功标准

### 4.1 用户价值

XuanXue 第一版提供四项核心价值：

1. **可理解**：普通用户不需要预先掌握命理或占星术语；
2. **可解释**：每项结果能够说明输入、形成方式、规则和限制；
3. **不乱猜**：信息不足时提示、降级或停止，不猜测婚恋、职业、学业和家庭状态；
4. **用户可控**：资料可以仅本次使用，保存、更新和删除由用户主动决定。

### 4.2 第一版成功标准

第一版不以注册量、日活或用户主观评价“准不准”作为主要成功标准，而以可理解、可解释、可控制和可演示作为验收目标：

1. 新用户能从首页理解产品性质和责任边界；
2. 游客无需注册或填写敏感资料即可了解产品与公开文化内容；
3. 进入工具前能够理解需要哪些资料、为什么需要以及是否保存；
4. 每个公开结果包含普通语言摘要、实际输入、规则或形成方式、来源状态、缺失条件和限制；
5. 系统不默认补全出生日期、时辰、地点、性别或个人关系状态；
6. 不向用户展示没有可靠意义的综合评分或现实必然性承诺；
7. 用户未主动保存时，资料和结果不进入本人档案或历史；
8. 已保存资料可以按用户选择填入，当次修改不静默覆盖档案；
9. 每个公开工具通过规则、来源、隐私、内容表达和移动端准入检查；
10. 项目文档、模块、测试和验收证据能够让老师或面试官理解关键工程决策。

第一版完成不等于所有已有工具都能打开。第一版至少形成一条经过真实验收的完整用户闭环，并保证每一项公开能力达到统一标准；其余能力可以继续审核、封存或删除。

## 5. 三层产品结构

```text
第一层：公共文化探索
        ↓ 用户主动选择主题
第二层：单目标工具
        ↓ 用户主动同意保存
第三层：个人连续体验
```

### 5.1 公共文化探索

面向游客和初次访问者，不要求登录，不读取个人档案。可以展示可复算日期事实、经过治理的传统文化概念、工具介绍和如实披露生成方式的轻量互动。

这一层不能假装了解用户，也不能输出未经用户资料支持的感情、事业、学业或其他个人判断。现有首页和每日内容必须经过独立契约讨论后再决定保留、改写或删除。

### 5.2 单目标工具

用户主动选择具体工具后，系统才请求该工具真正需要的信息：

- 已保存资料由用户主动选择使用；
- 只补当前工具缺少的必要字段；
- 支持仅本次使用；
- 他人资料默认不保存；
- 输入条件不足时停止或降级；
- 结果遵守统一的结论、解释、依据和限制结构。

这是第一版的产品主体。

### 5.3 个人连续体验

只有登录用户主动保存后才产生，包括本人档案、主动保存的结果、生成时输入快照、档案更新与删除以及后续可能形成的个人探索轨迹。

这一层不得把每次临时输入自动写入档案，不得静默覆盖档案，也不得按新规则静默重算旧历史。

## 6. 功能准入与退出机制

每个工具进入公开第一版前必须通过七项门槛：

1. 对应清晰的用户需求，而不是因为同类网站拥有该功能；
2. 输入字段具有真实计算用途，无效字段删除，缺失字段不默认伪造；
3. 确定性规则可以复算，随机互动如实披露随机过程；
4. 每项公开内容具有明确来源状态，未核验不得写成权威结论；
5. 普通用户能够理解，专业术语具备渐进解释；
6. 数据用途、保存、更新和删除符合用户控制与最小必要原则；
7. 通过规则测试、异常输入、接口围栏、历史治理和真实移动端验收。

工具只能处于以下产品状态之一：

| 状态       | 含义                                                         |
| ---------- | ------------------------------------------------------------ |
| 公开       | 全部公开门槛通过，可以向普通用户提供                         |
| 受限公开   | 只开放已经通过门槛的能力，其他内容不展示                     |
| 内部审核   | 保留代码和测试，但从公开入口、直接计算接口、分享与索引中围栏 |
| 停用或删除 | 缺乏清晰价值、无法治理或维护成本明显超过价值                 |

第一版不是对所有现有功能进行美化后保留，而是逐项决定公开、收缩、继续封存或删除。

## 7. 第一版范围

### 7.1 必须形成的核心闭环

- 首页：说明产品性质，提供公共文化内容和清晰探索入口；
- 生肖：承担低门槛传统文化入口；
- 太阳星座：承担低门槛西方文化入口，并明确不是完整星盘；
- 八字基础排盘：承担深度规则、术语解释和结果凭证试点；
- 用户档案：渐进填写、仅本次使用、主动保存、更新和删除；
- 历史记录：只保存用户主动确认的结果和生成时快照；
- 通用能力：统一内容模板、来源状态、异常处理、公开围栏和移动端体验。

上述项目属于第一版目标，不表示当前实现已经满足目标。

### 7.2 候选功能池

- 日期对照（内部模块标识 `zeji`）；
- 称骨表对照（现有称骨算命退役）；
- 周易卦象阅读（不包含独立六爻排盘）；
- 姓名笔画与五格对照（现有评分式姓名测试退役）；
- 测字双轨候选：了解一个字／一字观照。

上述候选已经形成单项契约，但来源、实施和公开验收仍须分别完成。候选身份不等于当前可以使用，也不表示必须列入第一版；未通过门禁的候选继续封存，不得拖延核心闭环。各工具的目标策略与代码现状统一见[产品规范索引](README.md)。

### 7.3 继续封存

- 八字关系对照（现有评分式合婚退役）；
- 紫微斗数·基础命盘（现有预测功能退役）；
- 梅花易数·起卦演示；
- 独立六爻排盘（尚无恢复契约）。

封存不等于永久删除。八字关系对照、紫微基础命盘和梅花起卦演示均已形成获批契约；继续封存的原因是来源核验、代码实施和公开验收未完成，不再表述为尚未确定产品边界。独立六爻排盘则仍需另立契约，不能借周易卦象阅读或梅花易数恢复。

本节区分的是第一版角色和封存要求，不宣称旧页面已经完成退役或访问围栏。文档批准、实现完成、来源通过和公开许可仍须分别记录。

## 8. 工程形态与发布边界

第一版继续采用 Nuxt 全栈模块化单体：Vue 页面、Nitro 服务端接口、认证和 SQLite 持久化位于同一项目中，并按产品领域拆分模块和数据契约。

第一版明确不做：

- 不新建 Spring Boot 后端；
- 不拆分微服务；
- 不接入由项目承担费用的 AI；
- 不承诺用户自带 API Key；
- 不为展示复杂度而复制或迁移现有规则引擎。

当前服务器环境统一分类为 `public_preview`。它表示系统客观上可以从互联网访问，不表示已完成正式生产、安全、隐私、来源或内容验收。不同工具可以拥有不同的公开状态。

版本状态按以下顺序治理：

```text
内部审核 → 受限公开试运行 → 第一版候选 → 第一版验收完成
```

## 9. 轻量版本与发布治理

### 9.1 产品版本

第一版正式验收前使用 SemVer `0.x` 预览版本。首个经过治理、验证和用户接受的版本基线计划命名为：

```text
0.1.0-preview.1
```

该编号目前只是已批准的目标基线。当前不得据此声称产品已经发布 `0.1.0-preview.1`，也不得在未验收、未获用户授权时修改版本、创建 Git 标签或发布记录。

核心闭环和最终列入第一版的候选能力全部验收后，才可以发布 `1.0.0`。

版本递进遵守以下规则：

- `PATCH`：不改变产品契约的兼容缺陷修复；
- `MINOR`：新增能力或系统性完成一个兼容治理阶段；
- `MAJOR`：正式版本后出现不兼容的数据、规则或公开契约变化；
- `preview.N`：公开试运行阶段的可验收快照。

不是每次提交都升级产品版本，只有形成可验证、可部署的阶段成果时才升级。

### 9.2 五种版本分离

| 版本维度       | 示例                     | 职责                         |
| -------------- | ------------------------ | ---------------------------- |
| 产品版本       | `0.1.0-preview.1`        | 描述整个应用发布状态         |
| 数据库结构版本 | `schemaVersion: 1`       | 管理数据迁移和兼容           |
| 工具规则版本   | `bazi-core@1.0.0`        | 标识结果采用的计算或映射规则 |
| 内容／来源版本 | `source-catalog@2026.09` | 标识引用资料和解释内容       |
| 文档版本       | 见本文头部版本           | 标识产品契约自身修订         |

五种版本不得相互替代。修改解释内容不应伪装成规则变化，数据库迁移也不应静默改变历史结果含义。

### 9.3 发布证据

每个正式版本或预览里程碑至少记录：

- 产品版本、Git 标签、对应提交和发布日期；
- Added、Changed、Fixed、Removed、Security 分类的变更记录；
- 数据库、工具规则、内容和来源版本；
- 公开、受限公开和封存的功能状态；
- 类型检查、测试、lint、构建与必要的文档检查；
- 真实浏览器与移动端验收结果；
- 已知限制和未完成项。

Git 标签只在阶段通过审查并获得用户确认后创建。

### 9.4 轻量工程流程

- `main` 保存经过验收的稳定基线；
- 使用短期 `feat/*`、`fix/*`、`docs/*` 分支；
- 使用 Conventional Commits，并保持一次提交一个明确目的；
- 个人开发不为了形式强制复杂 GitFlow 或每次走 PR；
- CI 目标门禁为类型检查、测试、lint、格式检查、生产构建和必要的文档一致性检查；
- 第一版不引入自动语义发布、多环境发布列车、Kubernetes、微服务版本矩阵或形式化 API 大版本路径。

当前 `package.json` 无产品版本、Git 无版本标签、`CHANGELOG.md` 的未发布 `v1.0.0` 与现行产品范围不一致，CI 也尚未执行生产构建。这些是后续版本治理需要整改的已知事实，不在本文落盘时直接修改。

## 10. 项目价值与展示目标

面向用户，XuanXue 提供低门槛、可理解、可追溯、由用户控制资料的传统文化探索路径。

面向老师和面试官，项目展示开发者如何把早期功能堆叠型项目治理成具有清晰产品边界、模块化架构、数据生命周期、内容真实性机制和完整验收证据的全栈产品。

项目应当能够说明：

- 如何发现虚假个性化、无效输入、随机结果、来源不明、自动保存和移动端问题；
- 为什么停止堆功能，并建立公开准入与封存机制；
- 如何分离输入、可复算事实、传统解释、来源状态和展示文案；
- 如何设计渐进档案、当次使用、主动保存、删除与历史快照；
- 如何使用 Nuxt 完成前后端、认证、数据库、测试和部署闭环；
- 如何用 ADR、产品契约、规则版本、自动化测试和浏览器验收证明决策；
- 为什么暂不引入微服务、Spring Boot 或 AI。

项目演进故事为：

```text
早期工具集合
→ 发现产品与真实性缺陷
→ 建立内容和数据治理
→ 收缩公开范围
→ 完成核心用户闭环
→ 逐项审核扩展能力
```

最终评价标准是：

> 用户能够安全、清楚地使用；开发者能够完整解释每一项重要设计为什么存在。

## 11. 讨论进度与后续边界

截至 2026-09-06，原先约定依次讨论的首页、日期对照、称骨、周易、姓名、测字以及合婚、紫微和梅花均已形成获批契约。原讨论顺序已经履行，不能继续当作尚未开始的任务表；独立六爻排盘仍在封存范围，不属于已批准的周易恢复能力。

当前进行跨文档一致性收口，不启动代码实施。下一步由用户决定何时进入一个具体开发阶段；其范围与验收条件以当时的现行契约及实际代码为依据，不从原讨论先后顺序推导开发顺序。

首批核心闭环不变。候选是否实施或公开仍分别判断，不因为所有候选都有文档就把它们都塞入第一版。进度入口为[产品规范索引](README.md)，未完成事项与进入门槛见[阶段路线图](../project/stage-roadmap.md)。
