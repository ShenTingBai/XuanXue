## 1. 本文要解决的问题

R5 的**产品边界**已经批准，但四份规范之间存在若干互相冲突或未定义的细节。按 AGENTS.md「先想再写，不确定就问」和 Plan Protocol v2.2「先消歧再生成」，这些问题必须在写计划前由用户裁决，不能由计划执行者临时猜测。

### 2.2 现有实现的确切缺陷（与契约 §2 已记录缺陷一致）

- `composables/useBaZi.ts` 第 245–251 行以常量 `DAYS_FROM_EPOCH_TO_1900_01_01 = 693902` 断言「1900-01-01 = 甲子日」。实测依赖库给出 `1900-01-01 = 甲戌`。抽样六组日期（1900-01-01、2000-01-01、1998-05-25、1964-07-14、2004-02-05、2024-06-15）后确认误差恒定：**日干永远正确、日支恒错 2 位（六十甲子位移 10）**。这就是契约 §2.1「干支日锚点错误」的确切形态。
- 更严重的是 `tests/composables/useBaZi.test.ts:775-776` 把错误值写成内联快照（2000-01-01 断言日柱「戊申」，库给「戊午」），旧测试**固化了错误**；R5 不能把旧测试的期望当作基准。
- `composables/useSolarTerms.ts` 用 Meeus 级数 + 牛顿迭代解出节气**瞬时儒略日**，但 `jdToGregorian()`（第 24–42 行）在加 8/24 之后用 `Math.floor(... + F)` **丢弃时刻**，且该函数不返回年份；`getSolarTerm()` 的返回类型就是 `{ month, day }`。年柱/月柱边界因此全是**整日比较**。`getMonthPillar()` 的月干（五虎遁）用**公历年**天干取锚，而非立春校正后的干支年天干，立春前的 1–2 月日期会取错。
- 旧八字测试覆盖面宽但**自证**：全文无外部来源引用，多处只断言"属性存在/区间合法/百分比和为 100"（如 `useBaZi.test.ts:76-88`、`:124-127`、`:322-327`）；`useSolarTerms.test.ts:106-109` 甚至容许节气日期误差 ±1 天；`useBaZi.test.ts:196-222` 把 23:30 子时的日界偏差记为"已知限制"并让它通过。契约 §25.3 明确这类测试"不构成真实性验收"。
- 旧 `divinations` 历史链路**端到端已死**：`divination_results` 表在全仓**没有任何 DDL**；`server/middleware/auth.ts` 从不设置 `context.profileId`（`server/types/h3.d.ts` 自注"仅保留以维持已封存端点编译"），因此三个端点在生产中恒 401；且 11 个工具的 `historyPolicy` 全为 `disabled`，`canCreateHistory/canReadHistory` 恒 false，POST 在解析前即 403。R5 的保存/历史/删除闭环**没有可复用的现存客户端或服务端路径**。
- `components/tools/HistoryModal.vue`（523 行）与 `components/tools/ToolToolbar.vue`（91 行）**零调用点**，且 `tests/pages/tools/history-containment.test.ts` 静态断言 11 个工具页与首页都不再引用 `/api/divinations`。
- 现行 `/tools/bazi` 页面（617 行）**当前完全无法渲染**：它依赖 `useAuth().currentProfile`，而该状态是 `useState('auth:legacy-profile', () => null)` 且**从未被赋值**，所以页面第 132 行恒定跳转 `/login`；同时全局中间件把它重定向到 `/tools/status`。它同时渲染了 R5 的全部禁项：0–100 评分、喜用/忌神、日主强弱、大运/流年预测、婚姻/事业/财富映射、胎元/命宫/身宫。
- `package.json` 中 `lunar-javascript` 写作 `^1.7.7`（范围版本），而契约 §11.1 要求**核心历法依赖不得使用范围版本**。修它需要改 `package.json`，属项目配置明令"不修改、需单独批准"的范围 → 见 D11。

### 2.3 依赖库能力的实测结论（决定 R5 可行性）

`lunar-javascript` 1.7.7 已安装，实测可直接提供 R5 需要的全部历法原语：

| 能力               | API                         | 实测样例                                                                |
| ------------------ | --------------------------- | ----------------------------------------------------------------------- |
| 十二"节"精确时刻   | `Lunar.getJieQiTable()`     | 2000 立春 `2000-02-04 20:40:24`、立秋 `2000-08-07 13:02:59`（含时分秒） |
| 立春年界干支年     | `getYearInGanZhiByLiChun()` | 2000-08-07 → 庚辰                                                       |
| 十二"节"月界干支月 | `getMonthInGanZhiExact()`   | 2000-08-07 → 癸未                                                       |
| 六十甲子日         | `getDayInGanZhi()`          | 1949-10-01 → 甲子；2000-01-01 → 戊午；2026-09-14 → 辛卯                 |
| 子初换日（备用）   | `getDayInGanZhiExact()`     | 与午夜口径在无时刻场景下一致                                            |

**结论：R5 不需要引入新依赖，也不需要新写天文算法即可获得秒级节气时刻。** 但这是**实现工具**，按契约 §24 不能作为规则权威。

**已知实现陷阱（必须由黄金样例钉死）**：`getJieQiTable()` 同名节气会出现**两个 key**——中文名与全大写名分属相邻年份。实测 2000-08-07 视角下 `大雪 = 2000-12-07 03:37:02` 而 `DA_XUE = 1999-12-07 21:47:27`；`冬至 = 1999-12-22` 而 `DONG_ZHI = 2000-12-21`。取值时必须按目标年份显式选择，不能按 key 存在性取值。

### 2.4 A 级来源可得性（决定准入证据是否可完成）

- 香港天文台逐年公历与农历对照表**文本版** `https://www.hko.gov.hk/tc/gts/time/calendar/text/files/T{年份}c.txt` 可直接抓取，含**干支年、农历月日、十二节与十二中气的日期**。实测 T2000c.txt 的 12 个"节"日期（小寒 01-06、立春 02-04、惊蛰 03-05、清明 04-04、立夏 05-05、芒种 06-05、小暑 07-07、立秋 08-07、白露 09-07、寒露 10-08、立冬 11-07、大雪 12-07）与依赖库输出**逐日一致**。
- 该表**不含节气时刻，也不含干支日**。因此：
  - **节气的"落在哪一天"可由 A 级来源核验**——这恰好是 R5 日期级候选规则唯一依赖的事实；
  - 节气**具体时刻**已找到可用的 A 级来源：**日本国立天文台（NAOJ）暦計算室《暦要項》「二十四節気および雑節」**，逐年 HTML 公开，给出每个节气的**太阳黄经与精确到分的时刻（JST）**，按 `UTC+9 → UTC+8` 减 1 小时即得北京时间（实测见 §2.6）；
  - **六十甲子日锚点**的可抓取 A 级来源**仍未落实**（HKO 表不含干支日，NAOJ 暦要項也不列干支日），这是 R5-A 必须先解决的一项，见 §2.7。

### 2.6 节气时刻的 A 级交叉核验（2026-09-14 已实测通过）

用 NAOJ《暦要項》令和 8 年（2026）的十二个"节"（以**太阳黄经**为键，规避页面 Shift_JIS 解码乱码）换算为北京时间后，与依赖库输出逐项比对：

| 节   | NAOJ (JST)           | 换算为北京时间       | 库输出（北京时）     | Δ(分) |
| ---- | -------------------- | -------------------- | -------------------- | ----- |
| 小寒 | 2026-01-05 17:23 JST | 2026-01-05 16:23     | 2026-01-05 16:23     | +0.17 |
| 立春 | 2026-02-04 05:02 JST | 2026-02-04 04:02     | 2026-02-04 04:02     | +0.13 |
| 惊蛰 | 2026-03-05 22:59 JST | 2026-03-05 21:59     | 2026-03-05 21:59     | 0.00  |
| 清明 | 2026-04-05 03:40 JST | 2026-04-05 02:40     | 2026-04-05 02:40     | 0.00  |
| 立夏 | 2026-05-05 20:49 JST | 2026-05-05 19:49     | 2026-05-05 19:48     | −0.27 |
| 芒种 | 2026-06-06 00:48 JST | **2026-06-05** 23:48 | **2026-06-05** 23:48 | +0.35 |
| 小暑 | 2026-07-07 10:57 JST | 2026-07-07 09:57     | 2026-07-07 09:56     | −0.05 |
| 立秋 | 2026-08-07 20:43 JST | 2026-08-07 19:43     | 2026-08-07 19:42     | −0.28 |
| 白露 | 2026-09-07 23:41 JST | 2026-09-07 22:41     | 2026-09-07 22:41     | +0.27 |
| 寒露 | 2026-10-08 15:29 JST | 2026-10-08 14:29     | 2026-10-08 14:29     | +0.28 |
| 立冬 | 2026-11-07 18:52 JST | 2026-11-07 17:52     | 2026-11-07 17:52     | +0.08 |
| 大雪 | 2026-12-07 11:53 JST | 2026-12-07 10:53     | 2026-12-07 10:52     | −0.47 |

结论：

1. **12/12 节气日期一致，最大偏差 0.47 分钟**（NAOJ 只给到分，故 ≤0.5 分即该分辨率下的完全一致）。
2. 依赖库的输出口径**是北京时间（UTC+8）**，不是 JST；实测未发现时区口径错误。
3. **芒种是天然的边界黄金样例**：同一瞬时在 JST 是 6 月 6 日、在北京时间是 6 月 5 日。它证明"边界落在哪一天"**必须**按 `Asia/Shanghai` 判定（治理规范 §8.2），也证明候选生成必须以北京时间为准。
4. 因此 R5-B 的节气时刻维度可以从"无来源的库里数值"升级为"A 级来源可核验"；黄金样例的期望值可以取自 NAOJ，而不是取自依赖库输出（满足契约 §25.1"样例不得从当前程序输出反向复制"）。
5. 待确认项：NAOJ 逐年 HTML 存档覆盖哪些年份（决定黄金样例可取多少个跨年代节气样例）；R5-A 需核对存档页并如实记录覆盖范围。

### 2.7 仍需在 R5-A 解决的一项：六十甲子日锚点

依赖库的日柱口径已用标准儒略日公式自洽校验：`JDN 2451545`（2000-01-01）对应「戊午」（六十甲子第 55 位），与 `index ≡ JDN + 50 (mod 60)`（1 = 甲子）一致；`1949-10-01` 得「甲子」。但**自洽不等于有来源**——契约 §24 要求 A/B 级证据，§25.1 要求"多个跨年代日期"的权威锚点。R5-A 必须落实至少一项可引用的 A/B 级锚点（公开天文历书、学术历表，或可核对的中研院两千年中西历转换类学术工具），否则六十甲子日维度只能标注为 `implementation_only` + 数学自洽，并据此**如实下调准入主张**。

## 3. R5 的必做与禁做边界（从规范直接推出，无歧义）

**必做**：公历/农历对照；年柱、月柱、日柱；三柱天干地支与基础五行；日干；规则/引擎/来源集合版本与限制说明；节气边界候选（立春→影响年柱与月柱；其余十一"节"→影响月柱）；显式保存闭环（生成→未保存→用户点击保存→页内认证→保存摘要→再次确认→服务端复算→不可变快照→已保存）；幂等；历史列表/打开原快照/按当前规则重新计算/单条删除/清空八字历史；删除本人档案时统计并让用户选择历史去留。

**禁做**：时柱、大运、流年、流月、神煞、日主强弱、喜用神/忌神、0–100 分、性格与现实预测；胎元/命宫/身宫；任何默认值（今天、零点、子时、男/女）；自动保存、自动计算、自动带入档案；地方太阳时与历史时区；23:00–23:59 双日界候选（依赖时刻）；在 R5 内把 `bazi` 目录切到 `approved/public/enabled` 或 `historyPolicy=create_allowed`。

## 4. 规范冲突与建议裁决（C1–C14）

### C1 「缺时柱」与「节气边界」争夺同一个 `successQualifier`（必踩）

- 交付规范 §7.2：普通日期 `successQualifier = partial`，边界日期 `successQualifier = candidate`，「同时保留缺少时柱等部分结果说明」。
- 治理规范 §7/§7.2：`successQualifier` 是**单值**枚举，不得新增同级值。

R5 的结果**永远**缺时柱（partial 语义），边界日期又要求 candidate，单字段无法同时承载。

**建议裁决**：`successQualifier` 表达**本次输入不确定性的最强来源**——跨边界取 `candidate`，不跨边界取 `partial`；"缺时柱"不再靠限定词表达，而由领域结果中的独立字段承担（`missingFields: ['hour_pillar']` + `limitationNotes[]` + `completeness: {provided: 3, total: 4}`），并在摘要**之前**显示（治理规范 §4.3）。这样两个规范的字面要求都满足，且 §7.2「必须说明完整性分母、缺失项与限制」有了明确落点。

### C2 快照字段命名两套（蛇形 vs 驼峰）

- 契约 §23.2：`record_id`、`schema_version`、`success_qualifier`、`created_at`…（全蛇形，且**没有** `resultId`）。
- 治理规范 §10.1–10.4：`resultId`、`toolId`、`resultSchemaVersion`、`generatedAt`…（全驼峰，且**没有** `engineName/engineVersion`）。

**建议裁决**：以治理规范的信封（驼峰）作为**领域契约与 API DTO**；数据库列用蛇形；在设计中维护一份逐字段映射表，并让 `record_id` 与 `resultId` 明确**不是**同一概念——`resultId` 是"同一次生成的稳定幂等标识"，随输入改变而改变；`recordId` 是"已保存快照的行标识"。两者都要存，且 `(account_id, tool_id, result_id)` 唯一，这样同时满足契约 §23.2 的字段清单、治理规范 §11.6 的幂等要求与交付规范 §7.5 的"幂等标识"。

### C3 只有一个 `created_at`，却要求三种时间

契约 §23.2 仅 `created_at`；交付规范 §7.5 要求"生成时间、保存时间、幂等标识"；数据规范 §11.2 要求"推演所对应的时间"+"生成时间和保存时间"。

**建议裁决**：快照存 `asOfDate`（推演对应的产品"今天"）、`generatedAt`（结果生成时刻）、`savedAt`（快照落库时刻）；数据库列 `as_of_date`/`generated_at`/`created_at`，其中 `created_at = savedAt` 以兼容契约 §23.2 的字面字段。

### C4 历史标题用生成时间还是保存时间

交付规范 §7.5 写"八字基础排盘 + **保存时间**"；数据规范 §11.5 写"工具名称 + **生成时间**"。

**建议裁决**：列表标题用**保存时间**（交付规范是 R5 的直接依据，且与"列表本身就是保存记录"一致），并在详情中同时展示生成时间；两者差值即"生成后多久才保存"。

### C5 快照里的 `freshness` 语义未定义

契约 §23.2 把 `freshness` 列为历史记录字段；治理规范 §7 说它"只在页面仍持有结果时存在"，§7.4 把 `stale` 定义为"输入已修改、结果尚未更新"。已保存快照的输入不可再变。

**建议裁决**：已保存快照中**不写** `freshness`（列可为 NULL 以兼容字段清单，但语义为"不适用"）；历史页的"输入已过期"是**展示层状态**（因档案或规则已变），不写回快照。

### C6 "按当前规则重新计算"的语义与按钮文案四处不一致

- 契约 §23.2：必须**生成新记录**，不覆盖旧记录。
- 交付规范 §7.5：**只创建新的当次草稿和结果**，不覆盖旧记录。
- 治理规范 §12：可以提供"使用当前规则重新**生成**"，重新生成的结果**先保持未保存**，用户主动保存后成为另一条历史。
- 治理规范 §11.5 / 数据规范 §11.3：把输入复制到当前草稿（"以此输入重新探索"/"使用当前资料重新生成"）。

**建议裁决**：以治理规范为准——按钮语义 = **把旧快照的输入复制成新的当次草稿并生成未保存结果**，绝不自动写历史；用户再主动保存才产生第二条记录。按钮文案统一为「用当前规则重新计算」，并在结果区明示"这是新结果，尚未保存；原记录不变"。契约 §23.2 的"必须生成新记录"解释为"重新计算**不得**改动原记录"，不解释为"必须自动落库"。

### C7 首批输出是否包含十神/藏干/纳音

交付规范 §7.1 用**列举式闭集**定义首批输出（不含十神/藏干/纳音）；契约 §13 的"默认结果"包含十神、藏干、纳音；契约 §29 明确藏干顺序与纳音表的正式来源定位**仍在待审计清单**，而"对应审计未完成时，相关功能必须保持隐藏、降级或候选状态"。

**建议裁决**：R5 严格按 §7.1 闭集，**不输出**十神、藏干、纳音；在设计与计划中显式写明"这是按交付规范 §10 的优先级缩小首批范围，不是契约 §13 失效"。理由：纳入它们会立刻引入未经来源核验的规则表，违反 §29 并把 R5 的来源工作量扩大一倍。

### C8 契约 §27 的验收清单没有阶段标注

§27 收尾句要求"以上标准全部通过"才可标记第一版完成，而其中时柱/五鼠遁、23:00–23:59 双日界、大运、流年、流月、地点、时间四精度在 R5 无输入可测。

**建议裁决**：R5 计划中显式声明"契约 §27 仅 §27.1（除时间精度/子时/地点）、§27.2（除时柱/子夜换日）、§27.3、§27.5、§27.6 适用，其余属第一版全量、不在 R5 判定范围"，并且 R5 不宣称"八字第一版完成"。

### C9 信息架构两套顺序

契约 §22 给 8 项顺序，治理规范 §4.1–4.7 给 6 段顺序且要求 DOM 阅读顺序保持 6 段；治理规范 §2.2 的层级高于单项契约。

**建议裁决**：以治理规范 6 段为 DOM 骨架，契约 §22 的 8 项内容映射进第 3–5 段（四柱结果/怎样看懂/来源与版本），并在页面验收中检查 DOM 顺序而非只检查视觉顺序。

### C10 内容标签两套体系

契约 §4 五类（历法计算事实/传统分类/历史资料/规则差异/工程元数据）与治理规范 §5.6 用户可见五标签（计算结果/传统规则/文化资料/项目整理/随机互动）无映射关系。

**建议裁决**：**内部**内容记录用契约 §4 五类（与八字契约一致），**用户可见**标签用治理规范 §5.6，并在设计中给出映射：历法计算事实→计算结果；传统分类→传统规则；历史资料→文化资料；工程元数据→项目整理；规则差异→（并列展示，标注"规则差异"文字说明，归入传统规则+说明）。R5 实际只会用到"历法计算事实/工程元数据"两类。

### C11 日干 vs 日主

交付规范 §7.1 写"日干"，契约 §13 写"日干作为日主"。

**建议裁决**：页面主标签用「日干」，首次出现时按契约 §17 的六问解释说明它在传统体系中亦称「日主」；`getTenGod` 永不返回 `'日主'` 的既有铁律不受影响。

### C12/C13 目录围栏与保存闭环字面对立（**最关键**）

- 目录现状：`bazi = in_review / internal / blocked / disabled`（`constants/tool-catalog.ts`）。
- `middleware/tool-availability.global.ts`：任何非 `approved+public+enabled` 的工具路由**一律重定向** `/tools/status`。
- 契约 §23.1：目标 `historyPolicy = create_allowed` 须"八字完成公开准入和历史能力验收后"。
- 交付规范 §3.2：「历史创建默认拒绝」，只有"工具获准创建历史 + 用户已登录 + 用户明确确认保存"三者同时满足才放行。
- 治理规范 §20.2：「`internal + enabled` 只允许授权内部验证，exposure 不能被 computePolicy 绕过」。

**矛盾实质**：R5 的交付物是"保存/历史/删除闭环"，但按目录字面状态，工具既不能计算也不能建历史，且 `/tools/bazi` 在真实浏览器里**根本打不开**。R4 没有这个问题（`/self-profile` 不是工具路由，真机可达）。

**建议裁决**（需用户确认，见 D3）：把"是否引入授权内部验证通道"作为 R5 的显式决定，三选一：

1. **保持围栏不动，真机只验收可达部分**：R5 的保存/历史/删除只做 API 级 + 组件级 + 服务层证据，真机只验证"路由仍被围栏到状态页"与不相干页面。诚实但弱于 R4 的验收强度。
2. **R5 引入"授权内部验证"通道**（治理规范 §20.2 明文允许 `internal + enabled`）：`bazi` 改为 `internal + enabled`，中间件对**已登录且被显式允许的账号**放行内部验证，`exposure` 保持 `internal`、`historyPolicy` 仍为 `disabled` 但由内部标志单独放行历史写入。风险：改动了 R1 的围栏语义，必须由回归测试锁死"普通访客仍进状态页"，并写清关闭方式。
3. **只在验收用临时非提交构建**：本地临时改写目录后构建、跑真机验收、记录差异与哈希，验收后还原，**提交物始终保持 `blocked/disabled`**。真机覆盖真实页面代码，但证据依赖"非提交构建"，需在验收文档中如实标注。

### C14 核心历法依赖的版本锁定要求与项目配置冲突

- 契约 §11.1：核心历法依赖必须**精确锁定**，不得使用范围版本。
- `package.json` 现为 `"lunar-javascript": "^1.7.7"`（范围版本）。
- 项目配置（`.Codex/project-config.md` 范围与禁止项）：**不修改 `package.json`**，除非单独计划经用户批准。

**建议裁决**：见 D11。注意 `package-lock.json` 已把实际安装版本固定为 `1.7.7`，所以**运行时可复现性当前是有保障的**；缺的只是 `package.json` 的声明形式。若用户不同意改 `package.json`，应在计划中把该偏差如实登记为"依赖声明为范围版本、锁文件已固定实际版本、契约 §11.1 未完全满足"。

### 8.1 D3 方案 B 的落地边界（防走偏约束）

1. **默认关闭**：判定依据来自环境变量允许列表；**未设置时判定恒为 false**，线上（`public_preview`）行为与今天完全一致。
2. **不产生公开语义**：`exposure` 保持 `internal`，`isToolPubliclyAvailable('bazi')` 必须仍为 `false`——顶栏导航、首页工具列表、公开 SEO、导出可见性**一律不变**。
3. **目录仍是单一状态来源**：允许列表是叠加在目录之上的**额外**授权条件，不是绕过目录的第二套开关（治理规范 §20.2「exposure 不能被 computePolicy 绕过」）。
4. **客户端判定不是安全边界**：中间件与服务端历史接口各自独立校验；直接调用接口必须同样被拒绝。
5. **必须回归锁死**：匿名 → 重定向状态页；已登录但不在允许列表 → 重定向；允许列表内 → 页面可用；环境变量缺失 → 谁都不放行；其余 10 个工具不受影响；已登录但不在列表直接调接口 → 拒绝。
6. **如实登记**：这是 R1 围栏语义的一次**扩展**，需在路线图 R5 段记录并引治理规范 §20.2 作为授权依据；同时它顺带修复 `zeji` 声明的 `internal + enabled` 从未生效这一长期不一致。
7. **不省 R6 的活**：R6 的公开门禁 16 项一项不减；方案 B 只是让 R5 能在真机上验收自己的交付物。
